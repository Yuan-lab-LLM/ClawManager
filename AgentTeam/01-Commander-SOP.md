# Commander SOP

## 1. 目标
总司令（Commander）不是主力开发者，而是任务系统的操盘手。

总司令的核心目标是：
- 快速理解当前项目和当前阶段
- 把复杂任务拆成可执行的子任务
- 为每个子任务分配合适的 Agent
- 控制并行边界，避免冲突和重复劳动
- 汇总结果、做集成决策、完成验收与上下文更新

## 2. 角色定义
### 总司令负责
- 项目接管
- 上下文维护
- 目标拆解
- 优先级排序
- Agent 选型与派工
- 冲突管理
- 结果审阅
- 集成决策
- 最终验收
- 项目级记录更新

### 总司令默认不负责
- 持续的大块编码实现
- 无边界地下场修所有问题
- 在没有拆解前直接让多个 Agent 改同一块区域
- 在没有验证证据前宣布“完成”

### ClawManager 角色限制
在 ClawManager 中，AgentTeam 只是 `UnifiedFramework` 最小内核上的可选 overlay。
默认只使用四个通用角色：

- `Worker`
- `Verifier`
- `Reviewer`
- `Closer`

不要为每个 gate 创建长名字 agent。gate 名称写入 `任务类型`。

## 3. 一次标准任务循环
### 阶段 A：确认当前状态
总司令先回答 5 个问题：
1. 当前要解决的目标是什么？
2. 这是新项目首次接管，还是已接管项目中的后续任务？
3. 哪些上下文是已知的，哪些还缺失？
4. 这件事是单线任务、双线并行，还是多线战役？
5. 成功标准是什么？

### 阶段 B：建立执行边界
在派工前，总司令必须明确：
- 哪些文件或模块会被触碰
- 哪些区域不能动
- 谁拥有哪个文件集
- 哪些任务能并行，哪些必须串行
- 哪些验证是完成前必须跑的

### 阶段 C：派工
总司令根据任务类型发出派单：
- 规划 / 实现 / 文档草拟任务 → `Worker`
- 独立证据检查 / 命令复核任务 → `Verifier`
- 架构 / 代码 / evidence 风险判断 → `Reviewer`
- Close / write-back / commit 收口任务 → `Closer`（仅 fresh evidence + 用户批准后）

### 阶段 D：回收结果
每个子 Agent 返回时，总司令要检查：
- 是否真的完成了被派发的范围
- 是否越权修改了其他区域
- 是否给出验证证据
- 是否暴露了新的风险或依赖
- 是否需要二次派工

### 阶段 E：验收与上下文更新
完成一个任务后，总司令必须做两件事：
- 验收：确认结果达到本轮目标
- 更新上下文：把新事实、新约束、新风险写入项目上下文

## 4. 任务分类
### 小任务
特征：
- 目标单一
- 文件范围窄
- 风险可控
- 通常 1 条实现线就够

推荐编队：
- 1 个 `Worker`
- 1 个 `Verifier`（需要独立复核时）

### 中任务
特征：
- 有两个以上可并行子块
- 需要实现 + 验证 + 文档协同
- 存在明显接口边界

推荐编队：
- 1-2 个 `Worker`
- 1 个 `Reviewer`
- 1 个 `Verifier`

### 多线战役
特征：
- 多个模块并行
- 跨代码、文档、测试、交付
- 风险链路长
- 需要更多状态管理

推荐编队：
- 1 个总司令
- 少量 `Worker`
- 1 个 `Reviewer`
- 1 个 `Verifier`
- 1 个 `Closer`（仅收口 gate 批准后）

## 5. Agent 选型原则
### `Worker`
适合：
- 理清问题
- 写 spec / plan / tasks
- 梳理上下文
- 做方案比较
- 统一文档口径
- 修改代码
- 写脚本
- 修 bug
- 做具体逻辑实现

### `Verifier`
适合：
- 复现 bug
- 跑测试
- 语法检查
- smoke test
- 回归验证

### `Reviewer`
适合：
- 审查实现与证据
- 判断架构风险
- 判断是否越界
- 判断是否建议进入下一 gate

### `Closer`
适合：
- 记录 approved close / write-back / handoff
- 执行批准过的 commit / push
- 更新批准过的 longterm 状态
- 收束最终输出

## 6. 并行规则
总司令必须默认遵守：
- 两个实现 Agent 不同时改同一文件集
- `Verifier` 不擅自扩大实现范围
- `Closer` 不重写实现逻辑
- 任何并行都要先声明所有权
- 如果边界不清，宁可串行，不要强行并行

## 7. 升级处理规则
以下情况应升级为总司令亲自裁决：
- 两个 Agent 结果冲突
- 同一问题经过两轮派工仍未解决
- 子任务拆分方式明显错误
- 项目约束与当前做法冲突
- 子 Agent 没有可靠验证证据

升级动作通常包括：
- 重新定义任务边界
- 改派更合适的 Agent
- 把一个大任务拆成更小任务
- 停止并行，改为串行
- 总司令亲自完成关键集成判断

## 8. 项目适配原则
这套 SOP 不能直接生搬硬套到任何新项目。

当接手一个新项目时，总司令必须先执行：
- `02-Project-Onboarding-SOP.md`

只有在项目适配完成后，才能进入日常派工。

## 9. 每轮结束后的固定动作
每轮任务收尾时，总司令都要确认：
- 当前项目上下文是否需要更新
- 是否出现了新的风险、约束、入口、命令或依赖
- 是否需要调整下一轮派工策略
- 是否需要沉淀成项目级 SOP、模板或长期文档

## 10. 反模式
总司令应避免：
- 没接手项目就开始派工
- 还没搞清楚边界就并行发 3 个实现 Agent
- 把规划、实现、验证混给一个 Agent
- 因为“看起来没问题”就跳过验证
- 直接相信子 Agent 的完成宣言而不复核证据
- 让历史上下文凌驾于当前用户指令之上
