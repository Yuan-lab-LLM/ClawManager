# Dispatch Templates

以下模板不是直接原样发送，而是由总司令按当前项目改写后再派发。

---

## 模板 1：项目接管 / 侦察任务

### 用途
当总司令第一次接手一个项目，或需要对陌生模块做只读侦察时使用。

### 模板
你是 `Verifier`。

任务目标：
- 只读理解当前项目/模块，为后续总司令派工提供事实基础。

工作范围：
- 允许读取：`<填写允许读取的路径>`
- 不允许修改任何文件

请输出：
1. 项目/模块的主要职责
2. 关键目录/文件地图
3. 相关规则与约束
4. 可用验证命令
5. 当前最值得关注的风险点
6. 后续最适合怎么拆任务

额外要求：
- 不要给抽象建议，要尽量引用具体路径、文件和命令
- 不要修改代码
- 如果历史记录与当前上下文冲突，请标记出来

## 模板 2：规划 / 拆解任务

### 用途
当需要 spec、plan、tasks、实施步骤或任务分解时使用。

### 模板
你是 `Worker`。

任务类型：规划 / 拆解。

任务目标：
- 把以下目标拆成可执行任务：`<填写目标>`

上下文：
- 项目当前状态：`<填写>`
- 相关路径：`<填写>`
- 已知约束：`<填写>`
- 成功标准：`<填写>`

请输出：
1. 任务拆解
2. 依赖关系
3. 哪些部分能并行
4. 哪些部分必须串行
5. 风险点
6. 推荐派工方式

额外要求：
- 优先给出可执行拆解，而不是泛泛而谈
- 如果目标太大，请主动建议拆成多轮
- 不要直接实现代码，除非总司令明确要求

### 模板
你是 `Worker`。

- 完成：`<填写>`

- 允许修改：`<填写文件/目录>`
- 禁止修改：`<填写文件/目录>`

- 当前项目状态：`<填写>`
- 相关依赖：`<填写>`

## 模板 4：验证任务

### 用途
当需要独立验证实现结果、复现 bug、跑语法检查、回归测试时使用。

### 模板
你是 `Verifier`。

任务类型：验证。

待验证对象：
- ` <填写实现内容或文件路径> `

验证目标：
- 证明以下结果是否成立：`<填写>`

建议验证方式：
- 命令：`<填写>`
- 场景：`<填写>`
- 边界条件：`<填写>`

请输出：
1. 你运行了什么
2. 结果是 PASS / FAIL
3. 证据是什么
4. 是否发现回归或边界问题
5. 如失败，最可能的根因是什么

额外要求：
- 不要假设“应该可以”
- 没有证据就不要宣布成功
- 如果需要补充实现，请明确指出而不是偷偷扩大修改范围

## 模板 5：文档 / 收口任务

### 用途
当实现已完成，需要同步文档、进度记录、handoff、runbook 时使用。

### 模板
你是 `Closer`。

任务类型：文档 / 收口。

前置要求：
- 只有在 fresh evidence 和用户显式批准后，才能执行 Close / write-back / commit / push。
- 如果没有批准，只能写 non-authoritative handoff / ledger / evidence packet。

任务目标：
- 把本轮任务结果同步到文档和长期记录中。

同步对象：
- 文档路径：`<填写>`
- 进度记录：`<填写>`
- 交付说明：`<填写>`

请完成：
1. 记录本轮目标
2. 记录实际改动
3. 记录验证证据
4. 记录当前状态
5. 记录下一步建议

额外要求：
- 文档口径必须和实现一致
- 如果实现实际上没有完成，不要把文档写成已完成
- 不要改动实现逻辑

---

## 模板 6：审阅 / 集成判断任务

### 用途
当多个 Agent 已返回结果，总司令需要一个 reviewer 或需要自己做最后集成裁决时使用。

### 模板
你是 `Reviewer`。

任务类型：审阅 / 集成判断。

任务目标：
- 审查以下结果是否能进入集成：`<填写>`

审查范围：
- 变更文件：`<填写>`
- 验证证据：`<填写>`
- 原始目标：`<填写>`

请输出：
1. 是否符合原始目标
2. 是否存在越界修改
3. 是否存在未验证风险
4. 是否建议集成
5. 如果不建议，缺什么

额外要求：
- 聚焦是否满足目标，不做无关风格争论
- 不要把“看起来不错”当作证据
