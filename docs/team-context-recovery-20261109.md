## 根因与适配

1. Team180/task389 的 10:20 催促，在 Hermes 原生日志中明确被忙会话的用户授权检查拒绝；原生内部事件还有排队边界。因此 Redis 收到/ACK 不能证明模型收到。适配入口校验当前 Team、成员、原发送者、工作和版本后，使用原生 `steer()`；不设置 `allow_gateway_control`，不改变普通会话授权，不中断工具或并发启动另一个模型。
2. 催促仅在原执行忙碌时适配。原生空闲时的漏回执恢复、普通成员消息、长上下文和 Leader 合法追问保留原路径。初始化中的原执行可以等待注入；已纳入请求的提醒不再次投递。记录 queued/submitted/request_included/ignored，后者是请求事实，不保证模型一定采纳建议。
3. OpenCode 的首次搜索服务选择是服务端 Form，不依赖打开页面才产生。无人处理约一分钟可得到 `Web search cancelled`。只为当前受治理、归属匹配的 Team 会话提供默认 Exa（可配置）；保留原生权限检查、禁用和普通会话确认，不写全局搜索选择。HTTP502仍是独立的抓取错误。
4. 后端观察串行消耗共享检查期限，导致健康成员轮流 `runtime_unconfirmed`。现在按授权范围对 Deployment 去重、有界并发，并在查询短暂失败时使用一分钟内的已确认库存；仍检查代数、Pod/镜像身份、绑定健康及独立协作心跳。过期或真实异常不能继续显示可用。前端防止重叠轮询和旧响应覆盖新状态。
5. Hermes 重启继承旧状态文件的 offline 标记。连接和心跳现在主动发布 online 与系统代数，不覆盖业务工作状态。
6. Monitor 仅将确实 running 且执行证据新鲜的下游视为推进中的依赖；waiting、完成、失败、旧证据不能遮掉根任务异常。原超时与有限恢复规则保留。新增原生交互等待和经过过滤的 API 错误诊断，不凭空判定成功，也不无限重试压缩。
