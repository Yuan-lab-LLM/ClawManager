# OpenClaw Lite pool updates and recovery

The Team distribution uses one image update entry point. A pool with no business instances, or only positively identified never-started instances, can change images even when its old Agent cannot start. An unhealthy Agent is not evidence that user data is absent; instance bindings, generations, migration records and native workspace state are inspected separately.

New instances waiting for a pool retain their identity, owner, Team association and files. A successful pool switch persists which pre-existing IDs were verified as never started, so the normal birth boundary does not prevent their first admission or subsequent restart. Existing instances without that proof still require the established data compatibility/migration path. Pro instances and isolated upgrade labs are outside the ordinary Lite replacement scope.

Before an ordinary pool change, the controller starts an owned validation Deployment with scheduling disabled. Its writable PVC, NFS, host and CSI mounts are replaced with ephemeral storage. The native Agent and a fixed validation Gateway must start using the same tenant proxy-policy preparation as ordinary Gateway creation. No provider call is made. Older Agents returning `starting` are observed through idempotent requests for the same Gateway identity until they confirm `running`. Validation workloads are stopped before final completion.

Images declaring personal upgrade-only workers or unsupported personal identity/authentication modes are rejected before a serving image is replaced. Older compatible images do not need new metadata fields; startup verification remains authoritative. Existing data-safe migrations retain their snapshots, per-instance recovery, isolation, scoped ownership and Team protections. Their independent recovery admission remains separate from ordinary shared-pool serialization.

For an unused pool, source Deployment UIDs, source image scope, rollback images, stage deadlines and execution progress are stored durably. Each original pool is switched and checked against actual Kubernetes members and fresh Agent identity. Ordinary instance admission stays paused until commit. If a switched target fails before business admission, the controller restores and verifies the recorded source image. A source already broken by a previous empty-pool failure can resolve to its saved predecessor image; verification is still required before reporting recovery. No database or workspace restore is implied by an image rollback.

Checkpoints and status changes reject stale controllers. Startup validation is bounded at five minutes; deployment switching/restoration is bounded per pool at ten minutes. Uncertain control-plane results and stuck validation cleanup end with explicit retained-data/needs-inspection errors rather than permanent `running` or a false recovery claim. Retrying creates a new operation and re-inspects current resources; historical failed operations are not rewritten.

The upgrade page displays validation, switching, verification, source recovery and temporary-process cleanup. A failed check is refreshed when retried. For failed empty-pool operations, “用填写的镜像恢复并重试” checks the currently entered target again. Select a compatible Team serving image, not a personal migration worker image.

Validation includes real MySQL checkpoint/admission/recovery tests, Kubernetes ownership/storage-isolation tests, native isolated 7.1 and Team 10.2 Gateway startup/config/stop tests, backend regression and the final image portal checks. Native startup is not a claim of model semantic or business Team-task acceptance.
