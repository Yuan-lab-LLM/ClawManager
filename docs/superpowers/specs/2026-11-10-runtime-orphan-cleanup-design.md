# Runtime 无绑定残留清理补充设计

用户已要求修复删除漏洞与现场清理缺口，并保留业务、项目和手动恢复能力。本设计在现有故障驱逐机制上补齐无 binding 场景。

## 删除与迁移的完成条件

普通删除、永久 reset 清理共用同一清理入口。无 binding 不再表示未执行：先核对 SQL 历史源、当前 Kubernetes assignment 和各代凭据，再允许执行资源清理；当前绑定正常停止释放后也重复核查历史源，最后才删除实例记录。证明缺失则保留 deleting 和具体源代次错误。从未发布且两个来源库存均为空的实例可正常删除。

代次切换在覆盖当前发布前保留对应停止源审计；新代次仅清除已完成旧操作的活动恢复标记，历史凭据和停止审计仍保留。凭据存在本身不能证明某个 Pod 执行过，也不能凭代次大小推断已停止。

## 无绑定旧 Pod 的恢复

复用 `POST /admin/runtime-pods/:id/evict`，模式 `orphan-recovery`，请求必须携带 `source_pod_uid`，无实例/目标选择。先预检，再确认执行。使用原管理任务表保存 `orphan_recovery` journal，不另建调度器。

只处理精确单副本、单 Pod、无有效 binding 的 Runtime controller。数据库已不存在的旧属主，或数据库 stopped/deleting 且身份、代次匹配的源可进入；running/creating、Team、升级或未核实外部写入阻止恢复。现存 stopped/deleting 源在登记恢复时占用持久生命周期保护，并与真实生命周期锁串行，防止同实例并发 Start/reset。恢复登记与 northbound／批量生命周期生产者共享准入锁，拒绝既有 queued/processing/batch 和等待替换的 reset；替换 reset 的创建、切换、清理也复用相同生命周期及工作区保护。

预检固定 Pod/controller/Node UID、Node boot、原始 PVC 身份和 helper 镜像。先暂停调度并锁定发布，保留旧 Pod 的专用 finalizer；只将这个 controller 缩为 0 并禁用，模板保留。必须观察旧 Pod 进入终态，再由节点 CRI 独立核验旧 UID 的全部执行者退出。之后仅修复匹配旧 UID 的受保护管理账本、退休可验证的旧发布，移除本操作 finalizer，事务提交任务完成与保护释放。保留项目/Git/PVC。

历史旧源没有 matching CM/可信账本时，可凭整个旧 Pod 的退出凭据退休该 Pod，但不能给没有源归属信息的代次凭据伪造审计。缺少信息仍有明确阻塞，不能直接清 SQL 或删除锁文件。

## 恢复与观测

任务按阶段持久化；普通重试沿用同一范围和固定镜像；同 Node UID 的已验证 reboot 可更新 boot 范围，已有成功凭据优先消费，不重复停止。不同 Node UID、源替换、当前发布变化都保留阻塞。执行者隔离前可取消，隔离后继续同一任务。

独立 Pod 退出凭据可完成匹配的旧手动/自动停止任务，不写假的 Agent ACK。退役记录保留在 SQL 审计中；心跳、健康检查与普通调度状态写入不能将其复活，列表立即排除已确认退役的 Pod。

UI 将数据库绑定数与现场残留、未知状态分开。Unknown 禁用普通驱逐，但保留独立故障恢复入口；服务端始终重新核验真实身份和业务保护。

## 验证

覆盖真实 SQL 删除/历史源、并发 Start、源/节点替换、发布竞争、凭据 CAS、阶段中断/重试/取消、节点 reboot、迟到心跳、四种 Runtime 与 PVC/健康邻居保护。浏览器检查桌面和窄屏的 UID、预检、确认及阻塞交互。独立审查后更新测试集群，使用产品 API 逐个恢复已核对的旧 Pod，并保存现场验收。
