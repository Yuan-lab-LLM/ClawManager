# Slot 回收、手动重置与扩容隔离设计

状态：待用户审阅；本文描述目标行为，不代表功能已经实现或发布。

## 目标与范围

用户要求：异常或未知的 slot、Pod 在新实例分配时视为已占用，不得因这些运行状态阻塞实例创建和 Pod 扩容；提供管理员手动重置 slot 的机制，强制终止指定 slot 的容器并解绑旧实例。如果实例已在其他 slot 运行，必须保留现有运行；如果实例仍期望运行、尚未在其他 slot 运行，则在确认旧执行退出后进入待调度，由 CM 重新调度恢复运行。

本设计同时覆盖停止、休眠、删除时的 slot 容器重置，以及重启退避对容量的影响。物理 slot 重置与实例重新调度分开管理，不调用会先停止再启动业务的实例重启 API。手动重置后，仍期望运行且没有其他当前执行的实例由 CM 自动恢复；普通停止、休眠、删除保持各自不自动恢复运行的语义。保留工作区、网站源码、Git、PVC 与 NFS 数据。

本轮只形成设计；不操作现场实例，不重启现场容器，不发布镜像。

## 已核对的现有实现

- `runtime_scheduler.go` 中两条自动扩容路径会在物理容量检查失败时标记整个 Deployment 的 `capacityUnknown`，并跳过该组扩容。未知运行状态与扩容配置可信度需要分开判断。
- `runtime_pod_scale.go` 的手动扩容快照要求存在近期上报的健康服务 Pod。所有源 Pod 运行异常时，缺少这个快照也会拒绝扩容。
- `runtime_scheduler_capacity_proof_test.go` 已覆盖可识别 quarantine 槽位的扩容，以及拒绝不兼容协议和不完整物理布局。新设计保留配置兼容性验证，扩展故障隔离范围，不直接删掉这些保护。
- 现有故障驱逐以当前实例 binding 为入口，并要求当前 binding 仍与故障源一致；现有无绑定残留恢复以整个旧 Pod 退役为范围。二者均不能直接充当迁移后单个旧 slot 的手动重置。
- `runtime_fault_slot_release.go` 已有精确旧容器退出凭据、保留账本核对及新 worker 释放流程；`runtimeeviction` 已有节点固定、容器固定的 CRI helper。优先复用这些能力和持久管理任务，不引入新的进程管理服务。

## 方案选择

采用“按 slot 隔离、按可信 Deployment 模板补容量、按旧执行身份重置”。单纯增加创建重试仍会反复命中异常源；重建整个 Pod 会扩大对同 Pod 邻居的影响；两者均不作为本问题的默认处理方式。

## 容量与调度

### 容量语义

只有已核实为空闲、身份匹配、worker 就绪且没有管理保护的 slot 才计入可分配容量。运行中、已预留、异常、未知、回收中、手动重置中、重启退避中的 slot 均视为占用。

Pod 状态异常或未知时，其可分配容量按零处理；在该状态重新核实前，不向其中分配新实例。若只确认某个 slot 异常，而 Pod 的必要管理和访问条件仍满足，则隔离该 slot，其他已核实空闲的 slot 可继续使用。不能通过强行把整个 Pod 标成 Ready 来达到这一点。

容量观测结果分别表达已核实空闲、不可用/占用、确实启动中的新增容量及诊断原因。数据库计数不是空闲证明，观测失败也不能升级为整个池永久禁止扩容。

### 扩容准入与计算

扩容以仍有效的已批准 Deployment 配置为依据，校验 Runtime 类型、控制器 UID、不可变镜像、协议、资源、安全配置、存储身份及升级来源。当前 Pod 的异常或未知运行状态不取消已有配置批准。

在没有健康源 Pod 时，使用持久化的已验证配置及当前控制器一致性核对，支持从该配置新增 Pod。缺少批准记录或出现真实配置漂移时，报告具体配置错误；不能根据未知现场猜测镜像、存储或身份。补齐该证明来源是实现的一部分，不能把健康源 Pod 依赖原样保留。

新增容量不足时，按实际可分配容量与待创建需求计算缺口。异常 Pod 仍计入现有副本与资源占用，但不提供可分配容量；需要在现有副本基础上增加足够的新副本，不能按理论总 slot 数误判已有足够容量。

只有身份明确、属于本次扩容、仍在启动期限内且没有终止故障的 Pod，才可计入等待中的新增容量。异常或未知 Pod 不能一直被当成即将 Ready，阻塞后续扩容判断。启动观察有期限，超时记录具体原因并进入有界重试；保留副本上限、并发上限和重试间隔，避免资源不足时无限扩容。

同类型、同配置池的扩容请求合并，自动扩容保持只增加副本的原子更新，不覆盖更新的人工容量。一个 Runtime 类型的异常不阻塞其他类型。真实升级、退役和缩容冲突按原范围检查，不能借状态隔离绕过这些操作。

创建流程先尝试其他可用 slot，再触发或等待扩容；不固定等待某个异常 slot，不因重复选中异常源直接将整个批次判定失败。界面区分等待容量、Pod 启动、异常占用、配置冲突和集群资源不足。

## 管理员手动重置 slot

### 操作入口和固定范围

运行时 slot 详情提供“强制重置 slot”。管理员先查看影响范围，再提交；预检显示 Runtime 类型、Pod 名与 UID、slot、容器 ID、已知旧实例/代次、实例当前所在 slot，以及是否只清理历史残留。未知属主允许按物理 slot 发起重置，不要求构造假的实例身份。

提交固定 Node UID/boot ID、Pod UID、容器名和精确旧 ContainerID；有可信旧分配时同时固定 worker epoch、assignment 摘要、Gateway、实例、用户及代次。有 binding 时固定 binding ID 和全部源定位字段。预检到执行之间发生身份变化，重新核验；旧请求不得转而重启该 slot 后来接收的新业务容器。

操作有单 slot 的持久隔离和幂等标识，不暂停整个 Pod 或整个 Runtime 类型。沿用持久管理任务记录阶段、操作者、固定范围、旧容器退出凭据、解绑结果与错误。

### 执行顺序

1. 原子登记目标 slot 隔离和固定源身份；与该 slot 的普通分配、回收、升级等冲突操作互斥。
2. 重新核对物理身份和源记录。通过节点固定的受控 CRI helper 强制终止精确旧容器，不能被旧 worker 的辅助进程清理错误无限挡住，也不以管理进程是否响应作为必要前提。
3. 获取可独立校验的旧容器退出凭据。未确认退出时不报告解绑完成；API 超时、Pod 名消失、restartCount 增加或新容器 Ready 均不能单独替代该凭据。
4. 仅退休匹配旧源的分配和发布，并条件解绑仍精确匹配的旧 SQL binding。同一事务检查当前运行和期望状态，为需要恢复的实例登记持久待调度意图；源执行已退出但解绑或恢复意图尚未成功保存时，保留进度，重试从该阶段继续。
5. 新容器由 kubelet 启动。新 worker 保持隔离，核对旧退出凭据并释放匹配的旧 slot 本地账本；确认新身份和空闲证明后才允许再次分配。

容器已自动替换时，原任务可以消费已经取得的旧退出凭据，但不得改绑新 ContainerID 后再次杀容器。没有足够证据时显示待核验，不猜测旧执行已退出。节点不可达时保持该 slot 不可分配，并允许其他容量继续提供服务。

未知属主重置采用单独的物理容器范围校验，不能通过削弱现有要求可信实例属主的 `runtimeeviction.Scope` 验证来实现。允许终止已固定的业务 slot 容器；未知的实例凭据、共享 NFS 锁和全局属主记录不能被推断或批量清除。若旧本地账本无法核实，新容器继续隔离并给出具体修复原因；不将容器重启成功冒充为 slot 已可复用。

### 解绑与新运行保护

清理以旧物理执行为对象，不以 instance ID 为唯一定位条件。

- 当前 binding 仍精确匹配选中的旧源：事务解绑该 binding；只有实例当前代次、运行定位和生命周期意图也仍匹配该旧执行时，才更新该实例的恢复状态。仍期望运行且没有其他当前执行或分配时，登记待调度并交给 CM 恢复，不能停留在 stopped；已有明确停止、休眠、删除意图时继续对应生命周期，不重新运行。不清除并发产生的新代次状态。
- 当前 binding 已指向其他 slot：保留该 binding；不修改实例状态、期望电源、代次、健康状态和恢复计数；只退休旧源和旧槽位残留。
- 同一实例、同一代次已在别的 slot 运行，也适用后一条；仅比较代次大小不够。
- 不按实例或代次整体撤销当前凭据、删除当前路由、抢占共享工作区锁或递归清理 NFS。需要退休的旧凭据、发布和写入记录必须有旧源归属；不能证明只影响旧源的操作保留为明确待处理项。
- 不向“实例当前 endpoint”发送 stop，不能因当前 binding 已变化就跟随到新 slot。所有停止请求始终固定旧 Pod UID 和旧 ContainerID。
- 清理完成后的迟到心跳、旧 Gateway 报告和重复任务不能重新建立旧绑定，也不能覆盖新运行的状态。

slot 重置不删除实例。若选中 slot 实际仍承载当前运行，预检明确说明会终止该运行；若已经迁移，预检明确说明只处理旧源。不存在可信旧 binding 时，不执行按 instance ID 删除绑定的兜底。

### 未在其他 slot 运行时自动恢复

对能够可信关联到实例、当前期望仍为运行且没有其他有效当前执行或待启动分配的手动重置，状态流转为：确认旧容器退出与必要写入者隔离 → 条件解绑并持久登记恢复 → 待调度 → 启动中 → 运行中。待调度阶段复用现有 `creating` 与恢复阶段的表达，不直接把实例标记为 running，也不为文案单独增加数据库状态枚举。

复用现有 CM 调度与持久恢复流程，在旧执行确认终止后只推进一次恢复代次。新 slot 可在其他 Pod 上；原 slot 仍重启退避或账本待修复时，不要求先修好原 slot 才能恢复实例。没有可用容量时，保持待调度并按本设计触发扩容；同一待调度意图的重试不能反复推进代次或产生第二份运行。

解绑和恢复意图登记在同一事务完成，CM 重启后继续；普通调度与恢复任务共享生命周期锁和条件更新。若发现当前已存在其他 slot 的有效 binding，无论是运行中还是启动中的分配，都保留该分配并由原调度继续，不再创建第二份恢复任务。只有确认当前分配失效后，才能沿其原恢复流程推进，不能仅凭“尚未 running”重复分配。

调度前再次检查用户的期望状态；在重置或等待调度期间发出的停止、休眠、删除请求优先，取消尚未执行的恢复意图。旧源退休凭据必须隔离到旧执行，不能因恢复到同一 Pod 的其他 slot 而封禁新运行。未知属主或已删除实例只清理选定物理 slot，不猜测需要恢复哪个实例。

恢复指 CM 按实例原有配置和工作区重新启动其受管运行。重置会终止用户自行启动的网站等业务进程；只有已纳入实例启动配置的业务才随之恢复，不承诺自动重建任意手动启动的进程。

## 普通停止、休眠、删除

保持各自业务语义，统一在释放 slot 前确认该容器的全部业务执行已经结束。正常清理先请求业务退出与必要刷盘；辅助进程清理失败时可进入受控容器终止分支，避免在到达容器终止之前反复卡住。

删除不启动业务；停止保留数据；休眠仍需满足对应 Runtime 的原生检查点和数据安全要求，不能以容器强停代替休眠完成。手动强制重置表示终止现场执行，不伪造休眠快照或原生优雅停止确认。

NFS/PVC 保留现有挂载与数据。重启后的 emptyDir slot 账本仍需对账，不能假设容器启动就等于全新业务环境。外部 writer 和存储故障另行核实，不能把容器退出解释为全部 NFS 写入者均已消失。

## Kubernetes 重启退避

54 环境当前为 Kubernetes v1.35.0，读取到 kubelet 退避上限 5 分钟。本设计不自动修改节点配置。slot 在退避期间继续按占用处理，创建可以使用其他空闲 slot 或新增 Pod。

重置任务分别展示“旧容器已终止/旧绑定已处理”和“等待新 worker、slot 尚不可用”；实例另行展示“待调度/启动中/运行中”。不能把旧 slot 尚不可用与实例恢复混为一件事，不因恢复较慢重复停止替换容器。最终 slot 可复用完成条件包含新 worker 与空闲证明，实例恢复完成则要求其新运行确认正常。

需要验证单 slot 重启时 Pod Ready、Service/EndpointSlice 与实际用户页面的影响，不能只证明邻居进程未被终止。运行中的其他 slot 的管理、网关和浏览器流量都属于保护范围。

## 验收与报告

所有测试、二进制与前端构建在 10.130.81.54 执行；本地仅源码、文档、无产物类型检查和浏览器校验。功能测试使用隔离资源，现场用户实例不作为故障注入对象。发布与 Runtime 镜像升级另行遵循 CM 原生流程。

必须覆盖以下可复现用例并保存断言、日志和浏览器证据：

1. 8 个 slot 中 1 个异常/未知、其余 7 个已满，创建触发新 Pod 并成功，旧异常保持隔离。
2. 一个 Pod 全部异常/未知，没有健康源 Pod；配置批准与控制器一致时仍能扩容，配置真实漂移时报告具体错误。
3. 一个 slot 异常、另一个已核实空闲，且 Pod 必要服务条件满足时，使用正常空闲 slot；Pod 整体未知时不向该 Pod 分配。
4. 批量创建、并发调度、已存在扩容请求、Pod 长期 Pending、CPU/内存不足：不重复抢异常 slot，不无限扩容，不覆盖人工副本数。
5. 手动重置终止用户自行启动的网站进程和 worker，其他 slot 的进程及实际访问持续正常，工作区数据保留。
6. 旧 slot 残留 instance A，A 已在其他 Pod/slot 运行：旧容器退出、旧残留清理，新 binding、代次、凭据、页面、健康状态保持有效；同时覆盖相同代次的新运行。
7. 无 SQL binding、实例记录不存在、属主未知、worker 不响应时的物理重置；缺少退出凭据时不虚报释放。
8. 预检后 slot 换属主/容器、解绑时 binding 改变：条件写不误删，新运行不被停止。
9. 双击提交、重复回调、CM/helper 中断重启、超时响应、容器自动替换、长时间退避：任务可续跑，不再杀新容器。
10. 旧心跳和发布迟到不能复活旧源；同类型/不同类型其他创建、真实升级和数据安全边界保持正确。
11. 正常停止、休眠、删除分别验证，失败阶段和界面状态一致；休眠证明失败不冒充休眠成功。
12. 管理员权限、预检影响范围、任务进度、错误与重试入口，以及桌面/窄屏下的真实浏览器交互。
13. 重置仍期望运行、没有其他 slot 执行的实例：旧执行确认退出后进入待调度，CM 在其他可用 slot 恢复运行；没有容量时自动扩容，原 slot 持续退避或隔离不阻塞恢复。
14. 旧源解绑与恢复意图保存的事务原子性、提交后 CM 重启、重复恢复回调：不丢失待调度任务，恢复代次只推进一次，不出现双重运行。
15. 其他 slot 已有启动中分配但尚未 running 时沿用原分配，不重复调度；重置期间或待调度期间用户停止、休眠、删除时不复活实例。
