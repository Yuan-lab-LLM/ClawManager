# Runtime 基础调度

用户已选择保留创建时扩容、实例闲置休眠及唤醒，并允许 Runtime Pod 自动缩容最低为 1。

## 日常调度

1. 创建及明确的启动/唤醒请求，将实例置为 `creating`。
2. 只向相同类型、存储兼容、通过现有身份校验的 Runtime 分配槽位。容量不足时扩展该类型现有的服务池；等待 Pod 就绪后走同一分配路径。
3. `running` 实例只同步绑定状态。缺少绑定时报告异常，不悄悄创建新进程。`error` 实例不再由周期扫描自动恢复。
4. 实例闲置休眠仍通过现有停止协议确认进程终止，再释放槽位。休眠实例的再次启动复用创建路径。
5. 自动回收只删除持续确认空闲的 Pod，每个普通服务 Deployment 至少保留 1 个；不迁移其他实例来腾空 Pod。下限同时在选取、计划、提交、执行处检查，避免旧排队请求继续缩到 0。
6. 普通分配不再查找历史睡眠 Deployment、匹配冷启动模板或执行 0→1 唤醒。

## 维护及升级

显式维护和 CM 原生 Runtime 升级继续使用现有持久化操作及安全校验，由独立循环执行；不能阻塞日常调度。日常循环不主动触发心跳故障迁移或自动恢复。历史恢复工具和升级旧池回收仍可供明确的管理操作使用，不删除其安全凭据。

不新增开关、表结构、通用工作流引擎或另一套调度器。现有类型隔离、生命周期锁、备份工作单元、升级保护、停止证明和数据持久化校验保持有效。

## 既有环境

本改造不会清理故障记录、强制释放未知写入者或绕开升级保护。已经为 0 且没有有效恢复凭据的池，仍需要通过 CM 明确处理；“最低为 1”是此后自动缩容的规则，不是假造旧池恢复授权。升级准备池及已退役池可保持 0，不受普通服务池自动回收下限影响。

## 验收

- 两个全空 Pod 回收到一个，最后一个保留；忙碌、未知状态和未确认停止的 Pod 不回收。
- 自动缩到 0 的新计划和旧待执行计划均被拒绝，不产生副本修改。
- 创建/唤醒可分配、可按类型扩容，某一类型扩容失败不跳过其他类型。
- 异常和丢失绑定不会引起自动重建或代际增加。
- 长维护/升级在独立循环运行；日常循环不调用这些操作，原生升级仍可推进。
- 测试仅在 10.130.81.54 构建执行；未请求发布时不变更当前集群。
