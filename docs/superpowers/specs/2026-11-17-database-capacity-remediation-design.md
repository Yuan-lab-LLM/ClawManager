# 查询、大表、存储冗余、Redis 增长与正确性治理设计草案

- 日期：2026-11-17
- 状态：用户已批准实施，第一批开发中；未发布、未迁移、未执行数据删除。
- 代码基线：ClawManager `acf8665a`。
- 规模：约 10,000 个受管实例，Team 数量较少；实例总数不等于在线或模型并发数。
- 本轮目标：解决查询慢、超大表、存储冗余、Redis 无限增长，并修复本次审查发现的统计、分页、游标和持久化错误。

## 1. 路线选择

推荐优先修正统计、分页和游标错误，同时优化查询；随后补齐可靠持久化与增量维护，再收敛在线数据量，最后按增长数据落实日志月表。每批可以独立验证和交付，核心预算、任务、调度和恢复事务保持原有一致性边界。

备选路线：只加索引和调参见效快，但不解决增长与冗余；一次性全面分库分片涉及跨库一致性、迁移和恢复，不能替代查询与保留治理。本轮不把租户分片作为前置依赖。

E1 首先修复展示费用和统计口径，并核对实际预算账本；不能据此直接声称已经重复扣款。历史错误汇总须提供可重建/对账路径，不改写原始扣费事实来迁就显示结果。

E4 必须区分审计写入与外部模型执行结果：模型已执行成功时，日志失败不能把它描述成未执行，也不能诱导没有业务幂等保护的重新调用。持久补偿不能以无界内存或无界 outbox 替代。

Runtime 通知条数上限、完成确认 TTL、投影失败持久重放已经存在，属于需要保持的行为，不作为尚未实现的错误重复整改。Team 消费者连接竞争属于后续规模验证项，当前没有证明它已经造成故障。

## 4. 查询慢

- 会话列表将过滤、稳定排序和分页下推数据库，先取得当前页，再读取本页必要的元数据。不得在每次翻页时返回全部会话。
- 为常用调用数、token、费用和最后活动时间维护可重建的会话汇总；增量更新必须使用持久身份去重，不重复累计重试、回填和状态修订。
- 管理员统计按实例/日期汇总读取，避免逐实例调用全量会话聚合。全局汇总与当前页读取分开核算成本，不能用页面总计触发另一遍全历史扫描。
- 审计列表在 SQL 中过滤、排序和分页；准确表达总数与查询时间范围，不把最近 1,000 条中的命中数当成全库总数。
- 调用和审计列表只读取展示字段。请求、响应和审计长正文通过详情入口读取。
- Trace 明细采用稳定游标，每页最多 200 条、整体响应最多 8 MiB；超大单条正文通过独立受限读取提供，不静默截断持久数据。
- 费用按明确调用关联或先预聚合再连接。构造同一 trace 多次调用、失败后成功和多条费用的回归，核对统计与原始费用总和。
- 基于实际 SQL 和执行计划选择复合索引；已有 `(instance_id, session_id, created_at)` 等索引必须纳入检查，不按候选清单盲目重复创建。

拟定查询策略：默认最近 30 天，同步查询最长 90 天，超长范围通过异步导出/归档查询。接口语义和页面时间范围需要一起迁移，不能悄悄改变历史可见性。

## 5. 超大表

- 首先采集主要表的数据/索引字节、增长率、最老时间、正文占比，以及慢 SQL 扫描行数；不以固定行数判断是否必须分片。
- 实现有租约、进度与暂停能力的维护任务，每批 500 行，小事务，单轮最长 30 秒；在锁等待、业务延迟或备份门禁下停止本轮。
- 已完成模型活动明细拟保留 7 天。仅处理 finished_at 非空且不承担恢复/幂等职责的记录，保留实例活动汇总。
- delivered outbox 拟保留至少 7 天；实际删除还必须确认下游业务完成、允许重放窗口闭合且不再依赖该行去重或恢复。
- 调用、审计、聊天、风险和 Team 终态历史拟在线保留 90 天；删除前归档并校验，归档拟保留 365 天。
- 调用、审计等高增长观测明细采用月表承载和整月归档，服务端控制月份路由、跨月分页与旧 ID 定位；核心预算账本、幂等墓碑和活跃任务不随日志拆表。
- 月表写入前预建和注册；新旧数据回填、增量追平、行与金额/token及正文摘要校验、灰度切读和回滚必须形成可执行作业。旧表不可在验证前删除。
- 物理独立观测库由实测 I/O、维护窗口和故障隔离需求确定；只换 schema 不算资源隔离。
- 删除行不承诺立即返还磁盘空间。大表空间回收单独评估维护窗口、额外磁盘和锁影响。

所有保留期限均为本草案建议，评审后才成为配置和删除规则；本轮不会据此清理现有数据。

## 6. 存储冗余

- 先区分内容副本和业务事实：调用/审计/聊天中重复保存的请求响应可共享受控正文引用，费用账本、调用元数据和恢复凭据不能只因内容相似而删除。
- 新写入的大正文放入现有对象存储，元数据保存摘要、大小、版本和引用；保留现有详情接口的权限检查，不暴露公共对象 URL。
- 去重范围限定同一授权和加密边界；跨用户/租户不共享可探测的内容身份。
- 正文拟快速访问 7 天、可取回 30 天；元数据与正文生命周期分开，正文过期后明确返回状态，统计仍可查询。
- 历史正文按批迁移，先写对象、校验内容与引用，再清理原 LONGTEXT；对象写入或校验失败保留源数据。
- 对象回收确认全部有效引用已经退出，并尊重迁移、备份和恢复门禁；孤儿对象与过期正文都有实际维护任务。
- 日志持久投递需要稳定事件身份、失败重试和有界积压；避免把相同大正文再次长期复制到 outbox。
- 生产全量备份 `.partial` 残留增加失活判定与有限回收；不删除仍在运行的 attempt。

## 7. Redis 无限增长

- 保留现有 Runtime 通知流 10,000 条严格限制；补充载荷大小观测、紧凑通知和读取批次/响应预算，业务健康上报不得因 UI 通知容量失败而失效。
- 公共 XREAD 增加 COUNT，公共 RESP 解析增加总字节、数组元素和嵌套深度预算。超预算返回明确错误，不能推进可靠事件游标或丢弃消息。
- Team 数量较少，可靠队列治理放在主要查询修复之后，但仍需覆盖累计历史增长。
- inbox 裁剪只越过所有必需消费组已投递且无 pending 的安全前缀；events 以已持久投影/重放承诺和持久游标为边界。维护操作不能只相信内存里的读取位置。
- 先修游标错误处理、幂等和维护协议，再启用裁剪。维护器须拥有有限权限，并同步 Runtime 的受管命令和固定 Lua 契约。
- 新任务投递采用原子条数/字节配额及背压；为已接受任务的终态、确认和错误处理保留额度。MySQL/PVC outbox 本身也需要容量上限和恢复状态。
- DLQ 先归档验证再回收；永久去重键只有在重放源退出窗口且持久幂等可用时回收，不能统一补 TTL。
- 删除 Team 后先撤销写入、收敛或明确终止任务，再由持久维护任务按精确前缀分批回收命名空间。
- 根据实测内存、客户端缓冲和 AOF 峰值配置 Redis maxmemory 与容器资源；保持 noeviction。严格限额上线前必须验证满容量下的可靠重试与终态收敛，不能只设置 maxmemory 等待 OOM 拒写。
- control/team 物理拆分根据消息实际负载及故障隔离要求决定，本轮不因实例总数直接强制增加 Redis 实例。

## 9. 验证与环境

- 本地仅做源码/文档编辑、允许的无产物类型检查和浏览器验证；测试、二进制、前端生产包与镜像构建安排在 10.130.81.54。
- 当前未连接集群。实际数据采样和验证使用受限只读查询及隔离测试资源，不能拿生产可靠消息做裁剪实验。
- 性能场景覆盖 10,000 受管实例、10%/30%/100%模型活跃场景和 90 天等效历史；调用频率和正文大小先实测，再确定具体造数规模。
- 常用列表 P95≤500ms、管理员汇总 P95≤2s作为拟定验收目标，同时检查扫描行数、返回行数、峰值内存和连接池等待，防止只靠缓存掩盖全历史扫描。
- 正确性覆盖并发写入、重放、失败重试、跨月、长正文、归档失败、维护中断、备份门禁和满容量恢复。
- E1～E6 每项均需对应的行为回归和验证证据；只通过吞吐压测不能代替错误修复验收。预算账本与展示汇总独立对账，保留原始业务事实。
- 月表/正文引用加入备份注册与清单；新布局在隔离目标恢复并核验成功后，才允许回收旧表和旧正文。
- 本任务不更新 AgentRuntime 镜像。若后续可靠消息协议需要升级 Runtime，仍须使用 CM 原生升级流程和不可变 digest。
