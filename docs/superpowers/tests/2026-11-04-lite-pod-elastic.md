# Lite Runtime Pod 自动缩至 0：实施与集群验证

日期：2026-11-04。测试节点：10.130.81.54；业务命名空间：`clawmanager-system`。本地只编辑、格式化及检查差异；测试、构建、镜像导入和更新全部在测试节点进行。

## 实现方式

由 CM 现有 leader 调度循环发现空闲 Pod，直接通过 Kubernetes API 调整 Runtime Deployment 的副本数。复用现有 `scale_in` 持久化任务及执行器；不引入额外伸缩组件。

1. Lite 实例沿用现有空闲停止逻辑。停止回执确认并释放绑定后，Pod 才可能成为回收候选。
2. 每 10 秒检查一次实际 Kubernetes / Agent 状态。Pod 连续空闲 60 秒，且没有实例绑定、槽位预占或未确认停止，才生成自动缩容任务。自动模式允许最后一个副本减至 0，现有手动缩容限制保持原样。
3. 先持久化操作并暂停候选 Pod 的新分配，保护仍承载实例的同池 Pod，再用 Deployment UID 和 resourceVersion 做条件更新。等待控制器确认原 Pod 删除后完成任务。不以心跳消失代替停止回执，不强制删除业务进程。
4. 保留 Deployment、PVC、工作空间和历史记录。记录自动休眠的操作标识、原模板、Deployment 身份、代次和持久化卷身份。
5. 用户调用现有启动接口时，优先分配现有可用容量；没有匹配容量时，只恢复具有有效自动休眠证明的池，先恢复 1 个副本。等待真实 Pod 注册后，再走原有镜像、存储、实例身份及升级策略校验。读取实例详情不会唤醒。
6. 管理员手动停用、模板或身份已变化的池，不通过自动休眠路径恢复。资源不足时沿用启动等待与失败处理，由用户重试。

适用于四类 Runtime 的普通服务池，包括已正式提交的升级目标池和自定义池。沿用 Lite 自动停止总开关。Pod 缩容不迁移仍在运行的实例。

## 验证中修正的问题

- 多个循环共用 leader 租约时，续租的 resourceVersion 冲突不代表租约被其他进程持有。原实现会因此清空空闲计时，导致长时间无法满足连续 60 秒。现在只有确认仍持有未过期租约时保留观察结果，续租失败的这一轮仍不执行调度；无法确认所有权时重新计时。
- 一个池正在缩容时，继续检查其他池的真实空闲状态，等待共享操作准入恢复后再提交，避免每回收一个池都清空其他池的计时。忙碌、绑定变化、库存不可用或检查中断仍会使对应观察失效。
- 不能为了记录原存储而把 Kubernetes 查询放到手动 Stop 意图持久化之前。已恢复原有“先保存 Stop 意图”的行为；完成的自动缩容日志可按原 Pod UID 证明手动停止实例的存储来源。后续没有绑定的 Stop 回执不能覆盖更早的有效来源。
- 从 0 恢复只按当前 Deployment 标记查找对应操作主键；不反复扫描并反序列化完整调度历史。
