# 多部署形态下的系统备份/恢复四人分工计划

> 合同版本：`system-backup-plan.v12`（2026-09-09）
> 本文负责产品范围、公共语义和验收口径。P0-0a 必须把本版本落为 OpenAPI、JSON Schema 和枚举文件；这些文件在仓库中存在并通过 parity test 前，本文只能称为“待冻结规范”，不能宣称机器合同已经冻结。`system-backup-restore-execution-readable-plan.md` 与 `system-backup-restore-d-role-steps.md` 只保留导航、分工和执行顺序，不得复制或新增公共语义。
> v12 是 breaking 勘误版：补齐可枚举的catalog record inventory/导入入口，修正ownership-resolution、finalization、cluster capture barrier、evidence GC和participant状态机；分离KMS与secret型KEK协议，冻结Redis TTL/对象时间点语义、日志持久化、capability cache、confirmation幂等和控制库安全余量；统一health聚合与监控新鲜度。v11及更早草案不得作为实现输入。

## 1. 执行摘要

P0 交付 Kubernetes/k3s 下的系统级备份、隔离恢复演练、生产目标只读 preflight/diff、手动 retention prune 和 Console 运维闭环，支持 `cluster`、`single-node` 两类数据面。P0 不执行在线生产恢复，也不实现 backup-agent 的配置、token、回调或任务执行。

系统采用两层设计：

- 数据能力层：六类业务数据分别声明范围、统计、备份策略、恢复策略和 verifier。
- 执行控制层：独立 `system-backup-controller` 负责持久化任务接管、K8s Job、maintenance gate、fencing、artifact 发布、恢复演练和 prune；API 进程只鉴权、校验并写任务数据库。

P0 固定区分三个结论：

1. backup `status=succeeded`：本次备份执行完成，必选 part、manifest/index/marker、verifier 和 staging cleanup 均得到允许结果。`acceptance`任务由 controller 直接条件写入签名 `_ACCEPTANCE`；只有技术检查全部通过但因明确的资格条件不满足时，才允许以 `local_acceptance=false` 完成为 succeeded 且固定 non-eligible，任何必选 part/verifier、完整性或清理失败仍必须 failed。`local_acceptance=true` 只有 `artifact_registered` 成功后才能 succeeded。`functional_test` 不写 `_ACCEPTANCE` 或 registration，也不要求 acceptance signer/catalog 可用。
2. backup `acceptance_eligible=true`：有效、create-if-absent 的外部 `artifact_registered` 是唯一灾备线性化点；它只能引用签名有效且 `local_acceptance=true` 的 `_ACCEPTANCE`。数据库终态 CAS 是该外部事实的本地不可变投影：append 成功后 controller 必须持续收敛为 `status=succeeded + acceptance_eligible=true`，不得再走可取消或失败分支；源数据库在二者之间永久丢失时，灾备端仍以 catalog record 为权威。后续删除、损坏或密钥失效只修改 `artifact_usable`/promotion health，不回写历史资格。
3. 当前安装 promotion：必须使用终态eligible、演练开始时`artifact_usable=true`的artifact完成对应恢复演练并取得drill `acceptance_eligible=true`；该drill必须使用`cleanup_policy=delete-on-success`且cleanup已succeeded，创建promotion时源artifact仍为`acceptance_ready=true`、drill evidence health为healthy。每个安装只维护与自身`orchestrator+deployment_profile`相符的一条活动baseline；四矩阵汇总属于发布验收证据，不作为单个安装的运行时readiness条件。

恢复演练是数据级隔离恢复，不默认复制完整 Console/API/runtime 服务栈。生产恢复执行属于 P1，并且在引入不会被业务数据库覆盖的独立 control journal 前保持不可用。

## 2. 范围和部署形态

### 2.1 六类业务数据

| 业务域 | manifest 字段 | owner | 数据范围 |
| --- | --- | --- | --- |
| 用户 | `users` | A | 用户、管理员、quota、企业认证配置和认证 Secret/ref |
| 实例 | `instances` | B | 实例元数据、运行态、OpenClaw 配置、workspace 和实例内 skill |
| AI Gateway | `ai_gateway` | A | 模型、调用、成本、风险、聊天和 AI 专用审计 |
| Teams | `teams` | C | Team、成员、任务、事件、workflow ledger 和相关 Redis 状态 |
| 资源管理 | `resources` | D | 系统镜像、出站例外、安全扫描和通用管理审计 |
| Skill Hub | `skill_hub` | C | Skill 元数据、绑定、materialize job 和对象存储内容 |

`openclaw_config_*` 归实例域；`system_backup_*`、maintenance lock/lease 属于控制面，不形成第七类业务 verifier。

### 2.2 部署维度

- `orchestrator`：P0 为 `kubernetes|k3s`；P1 才增加 `docker-compose|bare-metal`。外部数据源不是 orchestrator，另以 `datasource_topology=embedded|external` 表示；P0 只接受 `embedded`，`external` 返回 `unsupported_datasource_p1`。
- `deployment_profile`：复用 `CLAWMANAGER_STORAGE_PROFILE=cluster|single-node|legacy-nfs`。Backup 的 source profile 只能由当前安装配置派生，API 不接受客户端覆盖；drill/preflight 的 `target_deployment_profile` 在 P0 只接受 `cluster|single-node`。P0 遇到 `legacy-nfs` 必须同步拒绝创建并返回 `unsupported_profile_p1`，Console 只展示 P1 提示。artifact 写入配置固定称为 `artifact_target_config`；drill/preflight 的隔离目标连接、credential ref 和资源位置固定称为 `restore_target_config`，两者使用不同 tagged union/schema，不得再用含义不明的 `target_config`。
- `runner_type`：P0 固定为 `kubernetes`；P1 可增加 `agent`。

| 入口 | profile | P0 执行方式 | 强一致前提 |
| --- | --- | --- | --- |
| Kubernetes/k3s multi-node | `cluster` | controller 创建独立 Job；CSI/object/Redis checkpoint 后归档到外部 artifact | workload quiesce ACK + 不可变 source checkpoint |
| Kubernetes/k3s HostPath | `single-node` | Job 绑定 storage node，在 gate 内完成不可变 staging | 相关 runtime 全部停止、写入排空、staging 在最大停写时间内完成 |
| Docker Compose/bare-metal | `single-node\|legacy-nfs` | P0 仅展示 `unsupported_runner_p1` | P1 backup-agent |
| Kubernetes/k3s legacy NFS 或外部数据源拓扑 | `legacy-nfs\|cluster\|single-node` | P0 仅展示 `unsupported_profile_p1\|unsupported_datasource_p1` | P1 capability/runner 扩展 |

### 2.3 P0/P1 边界

P0 必须完成：

- 公共机器合同、系统表 migration、schema object ownership、审计/redaction、request ID、错误合同、状态机和功能开关。
- 独立 controller Deployment/ServiceAccount/leader lease，以及 controller DB claim、maintenance gate、mutation lease 和 fencing。
- P0-0b 移除官方部署中的 `clawmanager-app-cluster-admin` 绑定，以现有 runtime-manager 权限为基础补齐显式最小权限；未完成前不得宣称 API/controller 已形成权限隔离。
- 流式、加密、原子提交的artifact、按purpose签名记录、provider-native精确写grant、外部recovery catalog及灾备catalog import；六类统计和verifier；数据级隔离恢复演练。
- 生产目标只读 preflight/diff、手动 prune、告警、四种真实部署矩阵验收。
- 使用已有依赖；不得运行时下载工具或自行安装开发依赖；测试产物必须清理。

P1 才实现：

- backup-agent 配置、token、签名、任务获取/下发、事件/完成回调、取消和重试。
- Docker Compose、bare-metal、external datasource 端到端执行。
- `system_backup_schedules`、自动 prune。
- 独立 control database/journal、`system_restore_runs` 和受控生产恢复执行。

## 4. 公共术语、状态和资格

### 4.1 任务状态

- backup 完整枚举：`pending|preparing|ready_for_capture|acquiring_gate|capturing|validating|publishing|finalization_unknown|canceling|succeeded|failed|canceled`。正常路径为 `pending -> preparing -> ready_for_capture -> acquiring_gate -> capturing -> validating -> publishing -> succeeded`；只有持久化 `can_cancel=true` 的活动状态可进入 `canceling`，尚未持久化可能成功的不可逆外部写意图时可进入 `failed`，`canceling` 只能进入 `canceled|failed`。Manifest、`_COMMITTED`、`_ACCEPTANCE` 任一 final PUT 或 catalog append 的external-action已以`request_sent`提交、因而请求可能已发出，但在`deadline_at`前仍无法权威判定结果时，必须以CAS进入`finalization_unknown`：该状态`can_cancel=false`，禁止新的create/append finalization写，只允许根据唯一unresolved external-action row做Stat/Open/catalog精确判等，以及执行credential撤销、participant resume、staging/resource cleanup等安全收尾。同一backup任一时刻最多存在一个`request_sent|provider_unreachable`的finalization action；违反该约束为`coordination_invalid`。判成present后仅当该action已经是本purpose最后一个外部写（functional-test的marker，或acceptance的catalog registration）才可完成其余纯本地/安全收尾并succeeded；若后面仍有尚未持久化的必需finalization写，则不得越过deadline补发，完成安全收尾后以`failed/deadline_exceeded`结束，已经committed且技术完整的core仍按第4.2节决定functional readability。判成absent/conflict按action映射失败。若provider长期不可用，任务可停留于此并持续告警。`artifact_registered`确认成功后只允许幂等收敛到`succeeded`。
- drill 完整枚举：`pending|preflighting|provisioning|restoring|normalizing|verifying|canceling|succeeded|failed|canceled`。
- preflight 完整枚举：`pending|running|canceling|succeeded|failed|canceled`。
- artifact verify 完整枚举：`pending|running|canceling|succeeded|failed|canceled`。
- prune 完整枚举：`planning|dry_run_created|executing|partial_failed|succeeded|failed|expired`。只允许 `planning -> dry_run_created|failed`、`dry_run_created -> executing|expired`、`executing -> partial_failed|succeeded|failed`；`partial_failed -> executing`，以及仅当原item计划已冻结、至少一项仍为`delete_failed`且run不存在validation/capacity/confirmation/conflict类不可重试失败时允许`failed -> executing`。candidate枚举/持久化在planning中完成：每个artifact固化对象删除item，仅当它存在`artifact_registered` ID/hash时才同时固化后置`catalog_tombstone` item；retry只能重跑原candidate集合中的未成功item。Planning/capacity/validation/confirmation/conflict失败不可复活，必须新建dry-run；删除执行deadline导致的failed可按原计划retry。
- Prune run 的 `started_at` 在进入 planning 时写一次；`execution_started_at/execution_finished_at` 记录每次 execute/retry 窗口，历史窗口另写 operation；`finished_at` 只在 `succeeded|expired` 或不可重试 failed 时写入。`partial_failed` 和 `artifact_delete_failed` 的 failed 是可重试 settled 状态，retry 不清除已有时间和 item结果；API/Console必须结合`retryable`显示，不得把所有`failed`一概称为不可逆终态。Operation 的 `started_at` 在首次 controller claim、`finished_at` 在 `succeeded|failed` 时写入且不得改写；confirmation issue是同步纯数据库mutation。
- 取消：可取消任务进入 `canceling -> canceled|failed`。Backup 取消与发布分界的本地线性化点，是在 `publishing` 内以单条 CAS 写入 `can_cancel=false + commit_started_at`；它不等于第 4.3 节的灾备资格线性化点。CAS 后 controller 才能通过最小权限 provider adapter 发出绑定精确 final key、checksum、content length、expiry 和 conditional-create 条件的 finalizer request。Cancel CAS 先成功时不得发出 request；commit CAS 先成功时 cancel 返回 HTTP 409。自定义签名对象不作为对象存储能够校验的第二道写凭据。
- `can_cancel` 是所有 task 基础表中的持久化非空字段，并与 `status/row_version` 在同一 CAS 中更新。其真值固定：backup 从 pending 到 publishing 且 `commit_started_at` 为空时为 true；commit CAS 后、`finalization_unknown`、canceling 和全部终态为 false。Drill/preflight/artifact verify在所有正常活动状态均为true；取消CAS与写任务终态的CAS竞争，前者成功则进入canceling并阻止终态写，后者成功则`can_cancel=false`且cancel返回409 `state_conflict`。这些任务创建的资源或只读check result本身不提前关闭取消窗口，安全停止和资源保留按第4.1、12节处理。HTTP cancel读取到false时，仅backup且`commit_started_at`非空返回409 `commit_started`，其他非可取消状态返回409 `state_conflict`。
- Drill/preflight/artifact verify 的 cancel 以 operation 账本加任务 `row_version/can_cancel` CAS 为线性化点；CAS 成功后撤销新建外部资源的权限、停止 Job、释放 artifact lease，再写 `canceled/canceled_by_actor`。Drill 已创建的资源按失败现场保留并等待显式 cleanup，不在 cancel 路径猜测删除。Job 无法在 cancel deadline 内确认停止则任务 `failed/runner_failed` 并保留资源；preflight/verify 没有资源 inventory 时也必须先证明只读 Job 已停止再释放 lease。
- `canceled_by_shutdown` 只由官方部署 lifecycle hook 在管理员明确执行受控停机时创建普通 cancel operation；它仅能取消当时 `can_cancel=true` 的任务。Commit CAS 完成、provider request 已发出或 registration 已形成的任务继续收敛，不因 Pod termination 写 canceled。
- 终态记录不可复活。`retryable=true` 只表示可复制原始请求、使用新的 idempotency key 创建新任务，并写 `retry_of_public_id`；旧key在主记录/response仍处于control-metadata保留期时返回原资源，response已压缩但compact tombstone仍在时按第6.1节返回410且绝不创建新动作。Controller leader/DB claim丢失本身不是任务失败：只要安全证据仍完整，新owner必须透明接管；若因此无法证明checkpoint、fence或外部结果，使用`coordination_invalid`，若仅因无人接管超过绝对deadline则使用`deadline_exceeded`。Backup controller 仅能在 source capture 前对瞬时基础设施错误增加 backup attempt；drill、preflight、artifact verify 的自动 attempt 使用第 6.2 节各自的前置条件。Seal 后 publish Job 因接管而重建或 multipart 续传仍属于同一 attempt，不得重新读取 source 或递增 attempt。

drill 正常路径为 `pending -> preflighting -> provisioning -> restoring -> normalizing -> verifying -> succeeded`，preflight 和 artifact verify 正常路径均为 `pending -> running -> succeeded`；`canceling` 只属于取消分支。任一活动正常状态可进入 `canceling|failed`。所有终态必须同时写 `finished_at`，失败/取消必须写确定的 failure category；backup 的 `finalization_unknown` 必须保持 `finished_at=NULL/failure_category=none/retryable=false/can_cancel=false` 并写 `attention_reason=external_result_unknown`。`status`、`pending_reason`、`attention_reason`、`finished_at`、`retryable`、`can_cancel`、`failure_category` 的组合约束进入数据库 CHECK/parity test。Task status 是对外权威业务阶段；attempt 只记录某一 phase 的一次执行单元，Job observation 只记录该执行单元的观察结果。合法映射由机器合同冻结，任一活动 attempt 必须属于当前或紧邻下一 task phase，attempt 终结不会绕过 task CAS。Prune、operation、attempt、artifact、cleanup resource 和 promotion 各自使用独立 CHECK/transition CAS，并分别固定终态、failure 和时间字段组合，不能仅靠应用代码校验。自动 attempt 不改变任务主状态语义，每次 attempt 必须保存独立历史记录。

### 4.2 子流程状态

- `artifact_state=staging|committed|deleting|delete_failed|deleted|corrupt`。允许转换为 `staging -> committed|deleting`、`committed -> deleting|corrupt`、`corrupt -> deleting`、`deleting -> deleted|delete_failed`、`delete_failed -> deleting`；`deleted` 为不可逆终态，`corrupt` 不可恢复为 committed 但仍可在 retention/hold 规则允许时删除，其他转换拒绝。controller 验证 `_COMMITTED`、manifest 和 index 完全匹配后，必须在单一数据库事务中以 task/attempt/row-version CAS 完成 `staging -> committed`，同时保存 immutable locator/version、三者 checksum 和数据库时间 `artifact_committed_at`；事务失败不改变远端对象，接管者先读取并判等远端 marker 后重做同一 CAS，内容冲突则 `artifact_conflict`。失败/取消的未提交 prefix 必须先进入 `deleting`，由安全 cleanup 或 orphan-GC 收敛到 `deleted|delete_failed`，不能永久停在 `staging`。artifact 生命周期与 backup 执行状态分离，backup status 不再包含 `expired`。
- `artifact_usable=true|false`只表示本地backup artifact当前是否技术可读、可解密并可用于新建functional drill/preflight，不代表其可用于acceptance。`staging`初始化为false；进入`committed`后、源backup终态CAS前仍为false。源backup终态时，只要committed core完整、全部必选part的传输/integrity/redaction/secret-policy检查通过且不存在core object conflict，就初始化为true；发生在core提交和staging清理之后的Acceptance签名、Acceptance写入或catalog登记失败不把它改为false。`deleting|delete_failed|deleted|corrupt`必须为false。本地backup来源的drill/preflight创建须在同一事务中检查源backup已终态、`artifact_state=committed AND artifact_usable=true`后取得read lease；acceptance drill或`production_readonly` preflight另外要求`acceptance_eligible=true`且第4.3节全部当前依赖组为healthy。查询时派生`acceptance_ready=artifact_usable AND acceptance_eligible AND artifact-access/KEK/signature/catalog/evidence/attestation health全部healthy`，不另存第二个可漂移布尔值。Functional模式不因catalog、attestation或acceptance signing服务暂时不可用而被禁止，但结果固定不能promotion/execute。
- `artifact_unusable_reason=none|not_committed|finalization_pending|deleting|delete_failed|deleted|corrupt|provider_unavailable|credential_unavailable|kek_unavailable|evidence_unavailable|verification_inconclusive`；签名或catalog问题只影响`acceptance_ready`/promotion health，不影响functional readability。usable=true 时必须为 `none`；`staging` 必须为 `not_committed`；已 committed 但源 backup 未终态时必须为 `finalization_pending`。多项原因同时存在时，主 reason 按 `corrupt > deleted > deleting > delete_failed > kek_unavailable > credential_unavailable > provider_unavailable > evidence_unavailable > verification_inconclusive > finalization_pending > not_committed` 固定选取，全部观测原因写 check results。已 committed artifact 的暂时原因在相同 immutable version通过full verify且对应读取依赖恢复后可恢复；永久原因、`finalization_pending`和删除中状态不可由health verify恢复。
- 上述`artifact_state/artifact_usable`字段属于本地backup；catalog import使用只读派生字段`import_usable`和闭集`import_unusable_reason=none|verification_pending|catalog_tombstoned|corrupt|acceptance_invalid|provider_unavailable|credential_unavailable|kek_unavailable|signing_key_unavailable|catalog_unavailable|evidence_unavailable|verification_inconclusive`，不使用staging/deleting/delete_failed/deleted语义。Import创建后、首次full verify完成前固定为`false/verification_pending`。主reason优先级固定为`catalog_tombstoned > corrupt > acceptance_invalid > signing_key_unavailable > catalog_unavailable > kek_unavailable > credential_unavailable > provider_unavailable > evidence_unavailable > verification_inconclusive > verification_pending`；前3项为永久原因。创建drill/preflight和取得lease时要求`import_usable=true`，并对由registration ID确定的唯一tombstone key取得强一致Stat或版本化不存在证明；普通404只能令结果unknown，不得以无界分页或重复404证明“没有tombstone”。本安装不得通过health或prune改写外部artifact生命周期。
- eligibility reason code为`eligible|functional_test|task_not_succeeded|artifact_not_committed|required_part_failed|required_verifier_failed|staging_cleanup_failed|consistency_not_strong|disqualifying_warning|target_not_external|target_risk|attestation_invalid|kek_not_recoverable|catalog_unavailable|source_backup_not_eligible|source_artifact_unusable|manifest_drift|isolation_invalid|evidence_incomplete`；true时数组必须恰为`["eligible"]`，false时不得包含`eligible`且必须至少有一个可重算disqualifier。`_ACCEPTANCE.local_reason_codes`闭集为`eligible|consistency_not_strong|disqualifying_warning|target_not_external|target_risk|attestation_invalid|kek_not_recoverable`；`_ACCEPTANCE`只由技术必选检查全部通过的acceptance任务创建，不得包含task terminal、required part/verifier、完整性、redaction、staging cleanup、catalog、source drill或isolation原因。上述被排除原因只能进入任务failure/check或顶层eligibility reason。两处都保存排序去重数组及JCS hash。

Local acceptance 决策只允许以下三类结果，避免把技术失败误写成 non-eligible success：

| 技术必选检查 | 资格条件 | 结果 |
| --- | --- | --- |
| 任一 required part/verifier、完整性、redaction 或 staging cleanup 失败 | 任意 | `status=failed`，不写 `_ACCEPTANCE`/registration |
| 全部通过 | bounded/weak、disqualifying warning、same-cluster、attestation/KEK 等资格条件不满足 | acceptance 可 `succeeded + local_acceptance=false`；functional-test `succeeded`，两者均 non-eligible |
| 全部通过 | 全部资格条件通过 | 写 `local_acceptance=true`；只有 registration 成功后 `succeeded + acceptance_eligible=true` |
- `cleanup_status=not_started|pending|running|succeeded|failed|partial_failed|retained`，不覆盖drill主状态；逐资源`cleanup_failure_code=none|deadline_exceeded|provider_unavailable|permission_denied|identity_mismatch|checksum_mismatch|ownership_unknown|residual_data|internal`。允许 `not_started|retained|failed|partial_failed -> pending`、`not_started -> retained`、`pending -> running`、`running -> succeeded|failed|partial_failed`；进入pending必须由自动delete-on-success claim或新的显式cleanup operation驱动。全部计划资源均未安全删除为failed，至少一项成功且至少一项失败为partial_failed，零个需删除且所有intent均为absent时为succeeded；`retain-always`在任务终态写retained；失败或取消且未收到显式cleanup时保持not_started。
- `task_purpose=acceptance|functional_test`；仅适用于 backup 和 drill，默认 `acceptance`。Preflight 不使用资格术语，改用 `preflight_mode=production_readonly|functional_test`，默认 `production_readonly`：前者要求 source 在创建及取 lease 时均为 acceptance-ready，后者允许使用任一当前可读 source，但报告只能用于人工比较，不能作为 promotion 或未来 restore execute 的前置。artifact verify 不使用上述字段，其目的由 `verification_scope=health|full` 表示。部分 part、同域 target 或 non-eligible source 只允许显式 `functional_test`，并在 API/Console/manifest 中持续显示，不能 promotion。
- `task_type=backup|drill|preflight|artifact_verify`；attempt `phase=capture|secret_capture|publish|restore|normalize|verify|preflight`。合法矩阵固定为 backup→`capture|secret_capture|publish`、drill→`restore|normalize|verify`、preflight→`preflight`、artifact_verify→`verify`，禁止用 nullable 字段猜测类型。加密是 capture 流式写 sealed staging 的实现步骤，不再伪装成 task status 或独立 attempt phase。
- `pending_reason=none|global_capture_queue|kill_switch|dependency_backoff`，只在 `status=pending` 时允许非 `none`；`attention_reason=none|external_result_unknown` 只在 backup `finalization_unknown` 时允许非 `none`，两者都不等于 failure category。
- `operation_type=cancel|cleanup|ownership_resolution|provider_proof_register|finalization_resolution|manual_hold_update|config_update|promotion_create|promotion_revoke|catalog_scan|catalog_import|prune_execute|prune_retry|artifact_health_reconcile|orphan_gc|control_metadata_gc|evidence_gc`；confirmation issue 是纯数据库 mutation，不创建异步 operation。Operation 状态只使用 `pending|running|succeeded|failed`，不能复用 task status。后台 operation 使用 `actor_type=system` 和由 target+调度窗口派生的幂等键。`config_update|provider_proof_register|manual_hold_update|promotion_create|promotion_revoke`是同步纯数据库operation；`provider_proof_register`只登记经验证证明。`finalization_resolution`只能引用其产生且仍有效的evidence，不接受人工文本结论。有效provider-signed proof本身就是provider不可在线读取时的权威输入；缺proof、proof失效或不能满足第9.1节能力组时拒绝并保持原状态，不能把“再连一次provider”作为人工resolution的隐藏前置。
- `operation_target_type=backup|backup_staging|external_action|drill|restore_resource|preflight|artifact_verify|catalog_scan|catalog_import|prune_run|promotion|matrix|system`；已有资源的target public ID必须与类型匹配。`promotion_create`在新记录产生前固定以`matrix`为target，identity为服务端派生的`origin_installation_id+matrix_key`；创建成功后operation另存`result_promotion_public_id`。Catalog scan在同一事务创建`scs_`状态行并以其为target；`catalog_import`创建前以`system`为target，成功后保存`result_catalog_import_public_id`；`config_update`固定以`system`及origin installation ID为target并保存result config version；`provider_proof_register`只允许以`external_action|backup_staging|restore_resource`为target并保存`result_evidence_public_id`；其他`system`只允许没有单一资源目标的后台GC。
- attempt `status=preparing|running|sealed|succeeded|failed|canceled`；只有 backup capture/secret-capture attempt 可进入 `sealed`。attempt 终态不可复活，同一任务重建 Job 但不重新读取 source 时仍是同一 attempt。Backup 的 `capture` 与 `secret_capture` 是同一 attempt number 下的两个协调单元，必须全部 ready 后才允许拿 gate、全部 sealed 后才能签发一张聚合 capture certificate；任一失败都终止本次 capture，禁止只提交成功子集。
- backup staging resource `lifecycle=creating|absent|ready|sealed|deleting|deleted|delete_failed|ownership_unknown`；后台允许 `creating -> absent|ready|sealed|ownership_unknown`、`ready -> sealed|deleting|ownership_unknown`、`sealed -> deleting|ownership_unknown`、`deleting -> deleted|delete_failed|ownership_unknown`、`delete_failed -> deleting|ownership_unknown`；仅经成功的ownership-resolution operation另允许`ownership_unknown -> absent|ready|sealed`。`absent|deleted`为成功终态；`creating -> sealed`仅用于已以immutable version和checksum登记的remote manifest candidate。它是独立的一对多资源行，不嵌在 attempt 行。每个 staging resource 创建前先持久化 `sbs_` public ID、计划 locator、owner task/attempt/phase UID 和 expected marker。`ownership_unknown` 不得自动删除或直接转为`deleted`；管理员以expected row version和provider证明恢复为absent/ready/sealed后，再按需要新建cleanup operation走deleting。逐资源 `cleanup_result=not_started|running|succeeded|failed` 通常只允许`not_started -> running|succeeded|failed`、`failed -> running`、`running -> succeeded|failed`，其中未进入running而直接succeeded只用于权威证明intent从未创建。Ownership resolution另允许在同一CAS把failed按结论改为absent+succeeded，或改为ready/sealed+not_started；之后存在资源的清理必须由新operation从not_started进入running。其他failed重试必须由新的cleanup operation以row-version CAS驱动，succeeded不可复活。组合固定为creating/ready/sealed→not_started+failure none、deleting→running+none、absent/deleted→succeeded+none、delete_failed/ownership_unknown→failed+非none，其中ownership_unknown只能使用同名code。Backup cleanup成功只从全部资源的权威终态聚合，不另存可漂移字段。
- External action `target_type=backup|prune_item`，`action_type=manifest_put|marker_put|acceptance_put|catalog_registration_append|catalog_tombstone_append`，`state=request_sent|provider_unreachable|confirmed_present|confirmed_absent|conflict`。合法组合固定为backup→前四类、prune-item→`catalog_tombstone_append`。每次不可逆请求必须先在同一事务中创建独立action row并直接以`request_sent`提交；该状态表示发送意图已持久化，不证明网络请求真的离开进程。task/operation只引用action public ID，不在主行复制action state。`request_sent|provider_unreachable`为unresolved，`confirmed_present|conflict`为不可逆终态；`confirmed_absent`只允许在dispatch deadline已到、已满足不存在性能力组及consistency window后写入，表示本generation最终权威证明未创建；deadline前观测到absent必须保持unresolved并重发相同请求，不能提前终结。Backup action的`confirmed_absent`终结任务：前三类object action映射`finalizer_request_unavailable`，catalog registration映射`catalog_unavailable`，并按第4.2节保留已形成的committed core/usable事实。Prune tombstone action的`confirmed_absent`使item为`delete_failed/catalog_tombstone_failed`，仅允许显式`prune_retry`在精确key、完整canonical bytes及逻辑action hash不变时递增`dispatch_generation`并转回`request_sent`。Credential envelope可随generation重新签发，envelope expiry/signature不进入业务request hash。
- restore resource `lifecycle=creating|absent|created|deleting|deleted|delete_failed|ownership_unknown`；后台只允许 `creating -> absent|created|ownership_unknown`、`created -> deleting|ownership_unknown`、`deleting -> deleted|delete_failed|ownership_unknown`、`delete_failed -> deleting|ownership_unknown`；仅经成功的ownership-resolution operation另允许`ownership_unknown -> absent|created`。`absent|deleted` 为成功终态。管理员提交provider外部证明、期望row version和结论后仍须使用新的cleanup operation，禁止直接把未知资源标成deleted。
- `consistency_class=strong|bounded|weak`，取所有必选 part 的最低值。
- `artifact_compatibility=supported|compatible_with_warnings|unsupported`。
- `report_invalid_reason=none|artifact_unusable|manifest_drift|target_ref_drift|target_schema_drift|capability_expired|evidence_unavailable`；`report_valid=true` 时只能为 `none`。多项失效同时存在时按枚举中从左到右（跳过 `none`）选择主 reason，全部原因写 report checks。
- artifact lease `holder_type=drill|preflight|artifact_verify|health_reconcile|prune`，`purpose=read|verify|delete`；read/verify lease 可并存，delete lease 与任何其他 lease 互斥。
- maintenance gate `gate_state=idle|acquiring|held|releasing`；participant使用`running|pausing|paused|resuming|error`，`resume_result=none|succeeded|forced|failed`，`participant_failure_code=none|heartbeat_lost|pause_failed|resume_failed|forced_resume|generation_conflict|deadline_exceeded|internal`。这些状态和结果的转换只能按第8节执行。
- 核心 event type 为 `task_status_changed|attempt_started|attempt_finished|gate_changed|participant_changed|artifact_committed|artifact_health_changed|external_action_changed|evidence_changed|log_persistence_changed|provider_capability_changed|dependency_health_changed|catalog_scan_changed|catalog_record_changed|cleanup_changed|ownership_resolved|prune_changed|promotion_changed|operation_finished`。只有核心事件参与状态/验收；扩展诊断事件使用 `diagnostic.<owner>.<name>`，其中owner/name均为1..64字符小写ASCII `[a-z0-9_-]`且完整type不超过160字符；reader必须保留但不得据此改变状态或eligibility。
- `target_risks`的资格相关核心码是闭集：`source_overlap|same_failure_domain|artifact_credential_source_dependent|kek_source_dependent|signing_key_source_dependent|catalog_source_dependent|attestation_missing|attestation_expired|conditional_commit_unavailable|transport_unverified|broad_egress|provider_capability_degraded`。任一项存在都禁止`dr-ready-external`和eligibility；扩展会改变资格判定的核心风险码必须升级合同版本，纯诊断信息进入namespaced details，不扩展核心枚举。
- `source_overlap|transport_unverified|conditional_commit_unavailable|broad_egress` 在创建前已由静态检查或有效 capability cache 确认时 hard reject 为 `backup_target_risk_rejected`；任务创建后因 DNS、证书、provider capability、egress policy或source inventory漂移才发现时任务必须failed且不得publish。其余风险允许显式创建`functional_test`同域备份，但必须展示warning、固定non-eligible，且不能作为promotion baseline。任何层都不得把hard-reject风险降级成warning，也不得把非原子对象发布标记为committed。

### 4.3 资格判定

backup `acceptance_eligible=true` 必须同时满足：

- 外部有效`artifact_registered`已成功create-if-absent；本地控制数据库可用时，其投影必须最终为`status=succeeded`、`acceptance_eligible=true`、`artifact_state=committed`。本地CAS暂时失败不否定已经形成的外部资格事实。
- `_ACCEPTANCE`与manifest/marker checksum、staging cleanup evidence和本地验收结论完全一致，签名有效且`local_acceptance=true`；registration精确引用其checksum。
- 本attempt的加密staging已按owner UID/marker验证删除；无法证明清理完成时不得写`local_acceptance=true`或registration。
- `consistency_class=strong`，不存在 data-integrity、consistency 或 unsupported-evidence warning。
- target 为 `dr-ready-external`，通过同源排斥检查，并有管理员 failure-domain attestation 审计。
- artifact read credential、CA trust bootstrap、验签public key bundle和该artifact的签名`artifact_registered` catalog record均可在不依赖源集群Secret/网络的灾备环境解析，并固定到不可变ref/version/hash。
- KEK 不依赖源集群单点，能在隔离环境按记录的 key id/version 解密。

drill `acceptance_eligible=true` 必须同时满足：

- source artifact必须满足二选一：本安装源backup已终态eligible且创建时`artifact_usable=true`；或已持久化的catalog import通过record/acceptance签名、artifact full verify并派生`import_usable=true`。两者都要求manifest/acceptance/catalog checksum未漂移；`functional_test`可放宽历史eligibility但不能promotion。
- 导入、归一化、六类 restore verifier 和控制面 verifier 全部通过。
- 隔离目标、resource inventory 和证据链完整。cleanup 成功、失败或保留不改变已经完成的 verifier 结论。
- Catalog import来源的acceptance drill，其target profile必须等于`artifact_registered`中的origin profile；该drill可证明灾备可恢复性，但不能直接成为当前安装promotion，后者只接受当前安装本地backup及其drill。下一段关于“source backup”和promotion identity的约束仅适用于本地backup来源。
- 不同安装之间没有共享artifact lease，catalog import不能阻止origin installation执行prune。因此catalog-import来源的drill/preflight必须只读取registration固定的immutable object versions，并在首次读取前及写终态前各执行一次最新强一致tombstone Stat；任一对象版本消失、两次之间出现有效tombstone或最终检查unknown时不得成功。已经完成的历史drill结论不回写，但新任务创建必须使用import当前health。

当前安装的 `matrix_key=k8s-cluster|k3s-cluster|k8s-single-node|k3s-single-node` 必须由实际 `orchestrator+deployment_profile` 唯一派生，其中 `kubernetes` 规范映射为 `k8s`；API 不接受客户端指定不匹配值。Acceptance drill 的 target profile 必须等于源 backup/source installation profile；跨 profile drill 只允许 `functional_test`。每个安装/`matrix_key` 最多一条 `record_status=active` 的 promotion，并通过唯一约束加事务 CAS 原子 supersede；完整记录状态为 `active|superseded|revoked`。安装启动时若检测到实际matrix改变，controller必须在接受新任务前以system operation把旧matrix active记录CAS为`superseded/reason=matrix_changed`并解除其derived hold；若以后切回旧matrix也必须重新promotion。Promotion只是当前安装的本地运行时事实，不写recovery catalog；记录包含backup/drill public ID、manifest/acceptance checksum、`artifact_registered` ID/hash、资格判定hash、drill证据ID/hash、审批actor和时间。创建时必须验证drill的source backup就是所提交backup，二者均eligible且matrix一致，再以expected-active CAS原子激活。CI/release四矩阵汇总使用独立签名证据包。查询时从权威artifact、credential/CA、KEK、signature、catalog、evidence及attestation记录派生七项`healthy|degraded|unknown|stale`健康值，不回写promotion缓存；最近检查超过`promotion_health_max_age_seconds`时固定为`stale`。`current_health=healthy|degraded|unknown`由七者派生：全部healthy才为healthy，任一degraded/stale为degraded，否则为unknown。当前matrix无active baseline时输出`baseline_present=0`并令`backup_recovery_readiness=false`；该业务指标只进入overview/metrics/alerts。活动baseline对artifact及其依赖版本形成promotion hold。

七项promotion/acceptance依赖的权威来源固定为：artifact读取事实取本地backup/import行及最近full/health check；artifact credential与CA两类记录聚合为一个artifact-access组；KEK、signature、catalog、evidence和attestation各为独立dependency-health组。每条health row必须绑定artifact/import、promotion或以`owner_target_type=system`表示的installation owner及immutable dependency identity/version；数据库只保存`observed_health=healthy|degraded|unknown`，对外的`stale`只由数据库当前时间超过`expires_at`派生。创建acceptance drill/preflight/promotion时在同一数据库consistent read中选择每类identity唯一最新有效row，再按上述七组聚合；缺行或同版本出现相互冲突结果固定为unknown并拒绝准入，禁止从Prometheus、进程缓存或当前默认config补值。

Promotion create必须在单一事务中锁定源backup、drill和当前matrix active row，复核源artifact仍为committed且`acceptance_ready=true`、drill为`cleanup_policy=delete-on-success AND cleanup_status=succeeded`、drill evidence health为healthy、checksum/`prune_guard_version`未漂移，再写新active、supersede旧记录并递增backup的`prune_guard_version`；cleanup尚未settled、失败或`retain-always`一律返回409 `state_conflict`且不创建promotion。Prune的delete CAS使用同一guard，因此二者只有一个能成功。健康随后退化只改变派生readiness和普通row version，不改prune guard、不回滚历史drill或自动选择另一条baseline。

P0 发布验收另外汇总四个相互独立测试安装的 redacted promotion evidence；汇总包由 CI/release 流程签名并校验四个 matrix 均通过，不写入任一普通安装的 `system_backup_promotions`，也不要求单个安装持有另外三种部署形态的 baseline。

### 4.4 Warning 与失败分类

warning 分为 `data-integrity-warning|consistency-warning|operational-warning|unsupported-evidence-warning`。只有不影响数据正确性的 operational warning 可保留 eligibility。每个 warning code 必须在 verifier registry 中唯一绑定 category、适用 part/check、是否 disqualifying 和默认 message template；未登记 code 按 `unsupported-evidence-warning` 处理，使 local acceptance 结论为 false，但在技术必选检查均通过时任务仍按第 4.2 节真值表以 `succeeded + non-eligible` 结束，不得含糊地改成 task failed。

### 4.5 并发和互斥矩阵

| 操作 A | 操作 B | P0 规则 |
| --- | --- | --- |
| backup capture | backup capture | 全局互斥；后一个保持 pending，不提前拿 gate |
| backup encrypt/upload/publish | 下一次 backup capture | 允许；前一个使用 capture certificate，不再依赖全局最新 fencing token |
| drill | drill | 目标 namespace/DB/prefix 不同即可并行 |
| backup publish/finalize | prune 同一 artifact | 禁止；源 backup 非终态时不能成为 candidate |
| drill/preflight/artifact verify/health reconcile | prune 同一 artifact | 互斥；活动 read/verify lease 阻止进入 candidates |
| drill/preflight/artifact verify/health reconcile | prune 不同 artifact | 允许 |
| config update | 已创建任务 | 允许；任务只使用持久化 config snapshot |
| schema migration/应用 rollout | backup capture | 双向互斥；migration runner 和 rollout 都必须检查 maintenance gate |
| orphan-GC | 活动 task/attempt | 禁止；只有 claim、Job 和 heartbeat 都过安全窗口才可清理 |

`conflict_active_job`只用于请求已指定并能在创建事务中确认相同restore target identity存在活动drill，或controller发现同一task/attempt identity下存在内容不匹配的活动Job；返回409且不创建新任务。全局backup capture与provider并发上限一律创建后排队，使用`global_capture_queue|dependency_backoff`，不得在不同handler中有时409、有时排队。

同一artifact的互斥通过数据库`system_artifact_leases`实现：drill/preflight在同一事务中确认本地backup已终态且`artifact_state=committed AND artifact_usable=true`，或catalog import已完成full verify且`import_usable=true`，然后对对应source type/ID插入read lease；artifact verify/health reconcile对同一source identity插入verify lease，本地backup还要求已终态且committed。Backup来源lease的首次取得、释放或过期接管必须在锁定backup行的同一事务中递增`prune_guard_version`，单纯heartbeat续租不递增。prune只接受本地backup，要求其已终态、没有活动finalize/publish Job且不存在活动lease，随后插入delete lease并把状态CAS为`deleting`；catalog import永不被本安装prune。一旦本地artifact进入`deleting`，禁止新lease。任务终态、取消、超时和controller接管都必须按数据库时间释放或续租lease，禁止采用“先查询再删除”的两步检查。

### 5.2 覆盖规则

- registry `object_type=table|view|trigger|routine|mysql_event`，`data_classification=public|internal|confidential|secret`，`backup_strategy=mysql_dump|metadata_only|exclude`，`restore_strategy=restore|normalize|reference_only|exclude`。`excluded_reason=platform_bootstrap|derived_runtime_state|external_unmanaged|unsupported_p0|sensitive_never_backup`，仅当 strategy 为 exclude 时必填；其他自由文本只作不超过1024 UTF-8字节的redacted explanation，不参与门禁。
- registry 覆盖所有上述对象；字段包含 object type/name、owner、category、data classification、backup strategy、restore strategy、verifier 和 excluded reason。新增对象若未分配或使用 `unsupported_p0` 且影响任一必选业务能力，P0 eligibility 必须失败，不能只记 operational warning。
- `system_backup` category的表固定`backup_strategy=metadata_only`、`restore_strategy=reference_only`：schema canonical metadata进入manifest/control evidence，但其DDL和数据行都不得进入MySQL dump。恢复目标先由当前版本migration runner预建空控制表，再只恢复业务对象；历史artifact reader负责把业务schema映射到受支持目标版本，不能执行或覆盖源控制表DDL。该规则由dump allowlist/denylist双向测试。
- 静态扫描 embedded migrations，集成测试查询 `information_schema`；`unassigned` 非空时任何 P0 gate 均不得完成。
- P0-0b 为当前 repository ensure-only 的 risk、chat、security-scan 等表补齐 migration，并移除构造器 DDL；restore verifier 不得调用 migration 或 `ensureTable(s)`。
- schema 来源只有 embedded application migrations；允许的例外仅为安装程序的 database/user bootstrap，以及 migration runner 创建 `schema_migrations` bookkeeping table。
- 官方四套 YAML 的 MySQL init 只保留最小 bootstrap 或同源生成物，禁止手工复制部分业务 schema。
- compatibility 记录 embedded filename+content 的 `migration_catalog_hash` 和规范化 `information_schema` 的 `schema_hash`；applied filename 列表作为可诊断字段直接进入 manifest，不再维护语义重叠的第三个 hash。
- `schema_hash` 不引入新的 SQL parser 依赖。Canonical input 按 object type/name 排序：table 使用 `information_schema` 的列、规范化类型、nullable/default、charset/collation、主键/唯一/普通索引和外键；view/routine/trigger/event 记录 server version、SQL mode、对象名/类型和数据库返回的原始 definition SHA-256，只统一换行符，不改大小写、空白、字符串、quoted identifier 或 DEFINER。Dump 内原始 definition checksum 负责传输完整性；restore verifier 单独检查对象存在、可编译及 DEFINER 重写策略，不把 source/target 的文本 hash 相等当作语义等价。算法和版本号进入机器合同与 manifest。
- migration runner 在执行任何 application migration 前读取 maintenance gate；存在 capture 时等待或失败。应用 rollout preflight 必须确认没有 active capture，避免启动新 Pod 时绕过 gate 修改 schema。

## 6. P0 数据模型

### 6.1 任务基础字段

backup、drill、preflight、artifact verify 共享以下任务字段：

`id`、`public_id`、`origin_installation_id`、`task_type`、`actor_type`、`actor_id`、`endpoint`、`idempotency_key`、`request_hash`、`request_id`、可选 `retry_of_public_id`、`status`、`pending_reason`、`attention_reason`、`can_cancel`、`config_version`、`config_snapshot_json`、`retryable`、`failure_category`、`failure_message`、`heartbeat_at`、`row_version`、`controller_owner`、`controller_lease_expires_at`、`next_reconcile_at`、`deadline_at`、`started_at`、`finished_at`、`created_at`、`updated_at`。`deadline_at=created_at+task_deadline_seconds` 并包含排队和 kill-switch 等待时间，不因接管或开关切换延长；关闭期间 controller 仍可用纯数据库 CAS 把已过 deadline 且未开始外部动作的任务终结为 `failed/deadline_exceeded`。若 deadline 前已发出可能成功的 final key PUT 或 catalog append 且结果未知，deadline 到达时必须进入 `finalization_unknown`，之后只通过唯一unresolved external-action row做只读判等，不能以超时伪造终态。`started_at` 在任务首次离开 pending 时只写一次；`finished_at` 只在终态写入。当前 attempt/progress 均从 attempt/check/event 查询派生，不在任务行双写缓存。

任务创建的唯一幂等约束固定为 `(origin_installation_id, actor_type, actor_id, endpoint, idempotency_key)`；后续 mutation 使用 `system_backup_operations` 的同形约束，不能复用任务创建字段。`actor_type=admin|system`，`actor_id` 非空，浏览器管理员使用十进制 user ID，系统任务使用固定 `system:controller`。`endpoint` 使用 OpenAPI operation ID，不使用原始 URL。`request_hash` 对业务请求 DTO 应用默认值、移除`request_id|strong_auth_proof`及机器合同明确列出的其他传输/认证字段后，按 JCS canonical JSON 计算；provider-proof registration中的provider-signed proof属于业务payload，不能移除。缺省与 `null` 是否等价由字段 schema 决定，不允许 handler 自行处理。Strong-auth proof和幂等账本必须绑定同一个request-hash算法及合同版本。

`system_backup_operations`是第4.2节operation type的幂等权威账本；artifact verify本身是独立task create，其cancel才使用operation账本。Operation状态为`pending|running|succeeded|failed`；记录operation public ID、target identity、可选且互斥的result resource public ID或result config version、endpoint、actor scope、idempotency key、request hash、关联external-action IDs、claim/row version、HTTP status、redacted response ref/hash、failure、`deadline_at`和时间。只有`config_update`允许result config version且必须填写，其他产生新资源的同步operation填写匹配类型的result public ID，不产生新资源者两项都为空；数据库CHECK拒绝其他组合。异步operation的deadline从operation `created_at`起算，不因排队或接管延长；同步纯数据库mutation必须在请求deadline内完成且不创建pending operation。API在同一数据库事务中写audit intent与task/operation创建记录；任一写入失败均不产生资源。纯数据库mutation可在该事务内直接写terminal operation和audit result；凡涉及外部动作，API只返回pending operation。每类多步骤外部操作必须使用已有权威明细：cleanup用resource lifecycle、prune用item/external-action、catalog import用record/evidence、promotion仅为数据库CAS；P0不提供无法持久化step结果的通用“只重跑未成功步骤”。失败operation使用新key和明确的专用重试语义，不能泛化继承旧action。

幂等保留语义固定为：只有task/operation/resource创建或同步mutation的权威事务提交后，scope/key/request hash/response才成为幂等事实；在该事务之前返回的认证、授权、格式、限流、依赖未就绪或row-version/state校验错误不占用key、不创建动作且不消费strong-auth nonce，调用者可在外部条件恢复后用原key重试相同body。Prune confirmation按第13节是例外：proof已验证后即使candidate漂移，也在单一事务中消费nonce、保存failed response并占用key，防止同一确认事实重用。主task/operation与完整response仍在时，同scope/key且同request hash返回原HTTP status和资源；明细或response已GC但compact tombstone仍在时，同hash返回410 `idempotency_expired`并返回原public ID/terminal摘要，异hash仍返回409 `idempotency_conflict`，两者都不创建动作。含`system_backup.destructive`权限要求的已提交mutation，其compact tombstone在installation生命周期内永久保留；其他已提交key的tombstone至少再保留一个control-metadata周期，`delete_after`后才允许删除并重新使用该key。SDK/Console每次新意图必须生成新UUID key，不得依赖过期后复用。

Operation转换固定为`pending -> running|failed`、`running -> succeeded|failed`；pending/running/succeeded必须`failure_category=none`，failed必须使用第4.4节非none category，API-only code不得落入该字段。Deadline到达时，尚未形成外部副作用的pending/running operation以`failed/deadline_exceeded`终结；已有resource/item intent的operation必须先把所有归属本operation的活动明细收敛到可接管的`created|delete_failed|ownership_unknown`等稳定状态，再写operation终态。已有unresolved external-action时不得伪造失败结论：operation可记录`failed/deadline_exceeded`，但action及target继续由system reconcile只读判等并阻止冲突新动作；prune item使用第13节专用收敛/retry规则。`finished_at`只在operation终态写一次，后续target收敛写新的system operation/event，不改写旧operation。

P0 migration 创建上述 backup/catalog-import/attempt/staging-resource/job-observation/external-action/evidence/evidence-chunk/log-chunk/dependency-health/provider-capability/source-writer-check/catalog-scan-state/catalog-record/strong-auth-nonce/compact-tombstone/drill/resource/preflight/artifact-verification/check-result/event/alert-state/operation/config-version/installation-state/prune/prune-item/artifact-lease/promotion/maintenance lock/mutation-lease/participant 表，不创建 `system_backup_agents`、`system_backup_schedules` 或 `system_restore_runs`。所有 mutable resource、item和operation必须有row version；所有 FK 删除策略、唯一键、非空、JSON checksum、状态组合 CHECK 和 keyset 索引由同版本 DDL 而不是应用默认值定义；nullable identity 参与唯一键前必须规范化为非 NULL 哨兵 hash。Drill detail 的 resource inventory 摘要查询时从权威 resource 表生成。

自动 attempt 规则按task/phase固定：backup只有整个capture Job-set尚未取得gate、任一单元均未读取source且没有staging resource进入sealed时，才可因瞬时依赖失败递增attempt；只要capture或secret-capture任一单元已经读取source，整组失败必须终结任务，禁止用新attempt拼接不同快照。Sealed input上的publish重建只递增Job generation。Drill只在尚未创建任何外部resource intent前、preflight/artifact verify只在尚未取得有效远端结果或形成check result前，才可因`dependency|transient_provider`自动增加attempt；否则终结任务，由用户创建新任务。Attempt转换固定为`preparing -> running|failed|canceled`、`running -> sealed|succeeded|failed|canceled`；只有backup的`capture|secret_capture`允许进入`sealed`，其余phase使用`succeeded`。Preparing/running/sealed/succeeded必须`failure_category=none`，failed必须为非none非取消category，canceled必须为`canceled_by_actor|canceled_by_shutdown`。同一attempt number下任一capture单元失败/取消时，controller必须取消其他单元并把尚未终结的同组attempt全部收敛到failed/canceled，不允许部分seal进入publish。

External action转换固定为：API/controller在真正发请求前，以单一事务生成并持久化完整canonical payload bytes、逻辑action hash、action key、条件和首个dispatch deadline，直接创建`state=request_sent/dispatch_generation=1`；事务提交后才能调用provider。`request_sent|provider_unreachable`只能经同一action key的权威读取转为`confirmed_present|confirmed_absent|conflict|provider_unreachable`。`confirmed_present`必须完整bytes判等后继续任务；`confirmed_absent`只有在dispatch deadline已到，且provider capability group已证明强一致Stat，或取得绑定root/key/checkpoint/version且可验签的不存在证明，并且consistency window已过时成立；不满足能力时保持unresolved而不得猜测absent。`conflict`按artifact/catalog conflict终结。Dispatch deadline前允许为同一逻辑action重新签发短期credential envelope并重复原生幂等请求；payload、final key、条件和action key不得改变。Deadline后禁止写，只能读取判等；backup action按第4.1节进入`finalization_unknown`直到判成present/absent/conflict，prune tombstone action判成absent后只可由显式retry在相同payload下递增dispatch generation并取得新deadline。

Evidence storage转换固定为：小于等于8 KiB且通过schema/redaction的内容在单一事务中直接创建`inline`；外置内容按`pending -> ready|write_unknown|write_failed`、`write_unknown -> ready|write_failed`推进。引用保护解除且保留期结束后，`inline|ready|write_failed|delete_failed -> deleting -> deleted|delete_failed`；inline进入deleting时在同一事务删除密文payload并保留最小envelope/checksum，外置对象则必须先确认远端删除再置deleted。`pending|write_unknown`只能对登记的content-addressed key、content/object checksum/size及chunk-root做权威Stat/Open判等；相同内容置ready，不存在且原加密staging仍在、owner deadline未到时可重发同一内容，冲突置write_failed并以`checksum_mismatch`终结owner任务。Owner deadline到达时仍为pending/write_unknown则owner以`evidence_incomplete`失败且禁止继续写，system reconcile只读判等：若后来确认present则置ready并作为未引用orphan等待GC，满足不存在性能力组和consistency window后才可置write_failed；不得复活owner。只有inline/ready evidence可被check/report/promotion引用；owner终态事务必须同时确认所有required evidence均inline/ready，否则以`evidence_incomplete`失败。Inline evidence不可转外置，也不得在删除payload后继续声称inline/ready。

Evidence type/owner合法组合由同版本schema锁定：provider presence/absence proof只属于external-action，ownership proof只属于backup-staging/restore-resource，provider deletion receipt只属于backup-staging/restore-resource/prune-run，catalog scan receipt只属于catalog-scan，failure-domain attestation只属于backup/promotion/system，job log chunk只属于四类task owner，promotion release bundle只属于promotion，capability snapshot只属于system，cleanup result只属于backup/backup-staging/drill/restore-resource/prune-run；verifier report属于task/catalog-import/catalog-record/prune-run/promotion/system，diagnostic可属于任一已登记owner。其他组合在写row前`validation_failed`，不得依赖读取端忽略。

Catalog scan转换固定为`pending -> running|failed|incomplete`、`running -> succeeded|failed|incomplete`、`incomplete -> running`；`catalog_scan_failure_code=none|inventory_schema_invalid|permission_denied|snapshot_expired|provider_unavailable|signature_invalid|identity_mismatch|checksum_mismatch|record_conflict|deadline_exceeded|internal`。Pending/running/succeeded必须failure=none，failed/incomplete必须非none；回到running时在同一CAS清回none。API事务创建pending行；controller首次取得pending claim时只写一次`started_at`，取得并验证snapshot/checkpoint后才在同一CAS填入其identity/expiry并转running，取得过程的确定失败或超时分别走pending→failed/incomplete。每次进入incomplete写`last_interrupted_at`，只有succeeded/failed写一次`finished_at`。Deadline到达时仍未claim才转incomplete/deadline_exceeded。`succeeded`只表示provider生成的不可变inventory manifest或provider snapshot token所固定的keyset已读到EOF、页链/count/root验证通过、所有发现记录已幂等物化到catalog-record表、该snapshot没有`validation_state=pending`记录且ready receipt已登记，只有该状态刷新last-success；普通S3 ListObjects分页即使逐请求强一致也不视为snapshot。单个外部record的schema/签名/identity/checksum无效只把对应catalog-record置invalid并触发告警，不伪装成可导入记录，也不阻止其余完整keyset形成succeeded discovery receipt；外层snapshot/inventory签名、identity、页checksum/root无效或相同external key出现冲突bytes才使scan failed。`failed`表示确定失败且不可在原scan续跑；`incomplete`只表示deadline、暂时provider错误或snapshot临近过期导致未到EOF，不能作为完整发现证据；P0没有catalog-scan cancel API。Scan detail failure到operation failure的固定映射为：inventory schema→`validation_failed`，permission→`permission_denied`，snapshot/provider/deadline分别→`catalog_unavailable|catalog_unavailable|deadline_exceeded`，signature/checksum→同名category，identity/record conflict→`catalog_conflict`，internal→`internal_error`。暂时中断且仍可恢复时catalog-scan operation保持running；Incomplete仅在原snapshot/checkpoint仍有效且operation剩余时间足够时可CAS回running续扫，否则operation以对应failure终结、保留历史scan行并允许用新幂等键创建新scan。崩溃遗留running由claim/row-version接管，snapshot过期则转incomplete。任何时刻同一catalog ref version最多一个`pending|running` scan。

### 6.3 installation ID

- 官方部署首次安装时创建 `clawmanager-installation-id` Secret；应用和 controller 只读挂载。它是稳定标识而非认证凭据。
- Secret 对象、metadata 和挂载配置不进入 deployment resource payload 或 secret bundle；其 ID 值会按合同进入任务记录、manifest 和 artifact prefix，因此不得承载敏感信息。
- 新灾备环境必须生成新 ID；历史任务保留原 `origin_installation_id`，新任务不能命中历史幂等键。

### 6.4 数据库时间、事务和角色

- controller claim、maintenance lock/lease、confirmation、retention cutoff、eligibility decision和promotion/capability/evidence freshness全部使用数据库UTC时间及微秒精度；外部observed timestamp只作证据字段。
- DB claim 使用单条条件更新：row version 匹配且 owner 为空、为自身或 lease 已过期时才成功；每次推进状态同时递增 row version。禁止先 SELECT 再无条件 UPDATE。
- API DB role：业务读写和任务创建/查询、mutation lease；无 K8s Secret 数据读取权限。
- controller DB role：系统备份任务、events/audit、claim、gate/lease、resource inventory；不直接读取业务明文 Secret。
- backup Job DB role：业务表/schema object 只读和 mysqldump 所需最小权限，不允许 DDL/DML。
- drill restore Job DB role：只写系统创建的临时 database；不能写生产 database。
- verifier DB role：临时/目标 database 的 SELECT 和必要 `information_schema`，任何 DDL/DML 权限均不得授予。
- 具体 GRANT 清单、事务隔离级别和 MySQL/MariaDB 版本兼容性进入 P0-0a 机器合同与 RBAC/permission 测试。
- 所有声明需审计的Admin mutation和敏感导出必须先持久化redacted audit intent；失败则fail closed。外部动作完成后追加result；未知结果必须按external-action row或权威resource/item状态核实，不能盲重放。长任务terminal CAS与audit result同事务；若外部eligibility线性化点尚未形成，cancel CAS可按`can_cancel`竞争；commit CAS或`artifact_registered`形成后必须拒绝cancel并只收敛安全终态。普通轮询只记低基数访问指标；P0中manifest及被标记为敏感的registered evidence下载属于敏感导出。
- Redaction 在写 DB、event、audit、manifest 或外置 evidence 前执行；正确性证据无法安全 redaction 时任务在 publish 前 `failed/redaction_failed`。只读 API 对既有不安全内容必须拒绝返回并写 `redaction_failed` audit/metric，不得把原文放入错误消息。Job log 单行 redaction 失败时丢弃该行并写结构化诊断事件，不单独改写已终态任务。
- `audit_logs` 中系统备份自身的 append-only intent/result 是 maintenance gate 的明确例外：它们不取得业务 mutation lease，只允许插入，不允许修改或删除既有行。MySQL backup checkpoint 固定其事务 snapshot position，cutoff 后新增的系统备份审计不属于本次 artifact；verifier 校验 snapshot position 和最大已纳入 audit ID，不能要求 gate held 期间 audit 表物理静止。

`control_metadata_capacity_bytes` 默认10737418240（1 GiB..1 TiB），表示本模块控制表、索引和本地evidence envelope的软容量预算，不包含业务库其他表和外部evidence对象；另派生`control_metadata_safety_reserve_bytes=max(67108864,ceil(capacity*0.05))`。数据库物理可用空间必须大于软预算加安全余量；数据库不支持可靠表级size时使用migration登记表集合的`information_schema`估算并标记estimate。保存配置时必须满足capacity大于当前占用加安全余量且至少覆盖large-smoke产生证据的2倍。占用达到`capacity-reserve`后拒绝新的backup/drill/preflight/verify/catalog-scan/import/prune-dry-run和promotion create为503 `not_ready`，但为audit/nonce、cancel、cleanup、finalization/ownership resolution、provider proof、hold保护、promotion revoke及已开始任务收敛保留余量。若连安全余量也耗尽，所有需要新增控制记录的Admin mutation统一503 `not_ready`、controller禁止发起新的外部写并立即critical；但participant/watchdog resume、已签发临时身份撤销和external-action只读判等必须继续尽力执行，数据库恢复后以原generation/action identity补记结果，不能因控制库满而无限停写或延长凭据。不得通过删除destructive tombstone腾挪。

P0 正式部署默认 `staging_capacity_bytes=21474836480`（1 GiB..1 TiB）、`max_artifact_bytes=17179869184`（1 MiB..900 GiB）、`max_index_bytes=536870912`（1 MiB..8 GiB）、`max_plaintext_buffer_bytes=67108864`（1 MiB..256 MiB）、`max_source_items=5000000`（1..100000000）、`minimum_capture_throughput_bytes_per_second=52428800`（1 MiB/s..1 GiB/s）、`source_size_safety_factor=1.25`（1.0..2.0）。配置保存和任务 admission 同时要求 `staging_capacity_bytes >= ceil(max_artifact_bytes * 1.10) + max_index_bytes`；明文缓冲超过上限即 `capacity_exceeded`，绝不回退到磁盘明文。Single-node inventory 必须按part定义source size、dump/framing/index开销和估算误差；在拿 gate 前同时证明估算不超过剩余容量，并使用同一node、storage class/root、加密/压缩参数在过去24小时内完成的受签名throughput probe所得P10下界，而非管理员声明值，验证 `estimated_ciphertext_bytes/measured_p10_throughput <= 0.8*quiesce_max_hold_seconds`。配置的minimum仅是最低准入线，probe低于它或证据过期均返回`not_ready`；容量不足返回`capacity_exceeded`。Large-smoke 至少保留 2 倍估算 headroom。缺失或小于 fixture 需求时 acceptance 创建返回 `not_ready`。除`job_log_chunk`外，`evidence_retention_seconds`不得短于artifact retention；日志payload固定使用独立`logs_retention_seconds`且不得作为check/report/promotion的required evidence。`control_metadata_retention_seconds`承担task/operation完整response与明细、strong-auth nonce、standard compact tombstone和evidence registry envelope的最低保留，不再设置独立idempotency-tombstone retention，且不得短于artifact/evidence/logs retention和`strong_auth_max_age_seconds`中的最大值；destructive compact tombstone按第6.1节永久保留，不受该时长触发删除但计入容量预算。历史 credential/CA/KEK/evidence/signing/catalog/attestation/provider-proof issuer key版本必须覆盖 `protected_until_timestamp`。`alert_profile=production|development` 默认 production；告警threshold schema和默认profile由机器alert registry版本化，数值调整产生新的config/registry revision，不升级artifact/API breaking version。

并发和只读负载默认值固定为：`max_concurrent_drills=1`（1..10）、`max_concurrent_preflights=2`（1..20）、`max_concurrent_artifact_verifications=1`（1..10）、每类 `max_pending_tasks=100`（1..1000）。同一 restore target identity 的 drill 永远互斥；同一 provider 的并发还不得超过 capability snapshot 声明的上限。生产 preflight 默认 `query_timeout_seconds=30`（5..300）、`provider_qps=20`（1..200）、`max_scan_bytes=10737418240`（1 GiB..100 GiB）、`max_scan_items=1000000`（1,000..10,000,000）；达到任一预算即终止为 `failed/capacity_exceeded`，不得以部分扫描生成可用于执行的 valid report。部署可在范围内调低默认值，调高必须同时更新 immutable config snapshot 和容量验收证据。

## 7. 独立 Controller、Runner 和任务接管

### 7.1 权限边界

- `system-backup-controller` 使用独立 Deployment、ServiceAccount 和 leader-election Lease 名称，不复用 `clawmanager-app` ServiceAccount。
- P0-0b 必须删除四套官方 YAML 中的 `clawmanager-app-cluster-admin` ClusterRoleBinding，并为应用现有 runtime/sync 能力补齐可审计的显式 verbs；只新增独立 controller 而保留该绑定不算权限隔离完成。
- API 进程的 ServiceAccount 不具备创建 system-backup Job、namespace、PVC、snapshot 或读取备份 Secret data 的权限。
- controller ClusterRole 只包含创建任务 namespace/受限 RBAC、Job、PVC、VolumeSnapshot 和读取必要状态；namespace 名称前缀、label 和允许的 Role 模板必须再由 ValidatingAdmissionPolicy/部署准入策略限制，因为 Kubernetes RBAC 不能按资源名称限制 create。Job 使用每任务 ServiceAccount，只访问本任务资源。
- Kubernetes RBAC 只能限制 Secret 对象，不能限制对象内单个 key。Controller 和通用 capture/publish Job 均不读取业务 Secret data；独立 secret-bundle collector SA 只对机器合同展开后的明确 `resourceNames` 拥有 `get`，不得 `list/watch`，并在内存中按 key allowlist 取值、校验读取前后 UID/resourceVersion 未漂移后写入任务专属加密 at-rest staging。若版本漂移则 `secret_bundle_failed`，不得静默读取最新值。把 volume `items` 投影误当作 key 级 RBAC、或让 controller 复制明文 Secret 的实现不得通过安全验收。
- `kubectl auth can-i`/SubjectAccessReview 负向测试必须证明 app SA 不能执行上述备份控制动作，并证明通用 Job SA 不能读取/枚举 Secret、跨任务 namespace 或创建 RBAC；secret-bundle collector SA 只能 get 机器合同展开后的 resourceNames，不能 list/watch 或读取未登记 Secret。
- Controller及所有任务镜像必须使用不可变digest并进入release SBOM/签名验证；Pod默认`runAsNonRoot`、只读root filesystem、drop all capabilities、`seccompProfile=RuntimeDefault`、禁止privilege escalation并设置CPU/内存/ephemeral-storage requests与limits。确需HostPath/CSI权限的例外按具体Job模板、路径和capability登记，不能给通用SA或通用镜像提权。若节点/运行时无法在无capability条件下为配置的明文上限提供足够memlock，只有capture/secret-capture模板可按机器capability probe增加`IPC_LOCK`，并同时限制locked bytes、禁用swap/core dump、保持non-root和禁止其他capability；集群Pod Security不允许该例外时acceptance返回`not_ready`，不得静默使用可换页明文。

NetworkPolicy使用角色化allowlist：API只访问MySQL/Redis、外置evidence只读endpoint及现有业务依赖；controller只访问MySQL、Kubernetes API、artifact target/KMS/catalog/evidence write-delete endpoint/status relay；capture Job只访问业务数据源、DNS、任务状态relay、不可变staging和下一段按KEK variant选择的唯一key-acquisition endpoint；secret-bundle collector只访问Kubernetes API、DNS、状态relay和staging；publish Job只访问staging、artifact target、DNS和状态relay；drill/preflight/verify Job使用各自目标清单并访问状态relay，不直接取得evidence-store credential。原生NetworkPolicy只承诺L3/L4限制；外部FQDN或Kubernetes API path限制必须通过已声明能力的CNI/egress proxy实现，能力不存在时不得在验收中声称已限制。任何角色出现`0.0.0.0/0`或等价全出口均产生`broad_egress`，acceptance与functional-test都必须hard reject；P0不提供管理员例外。

Capture Job的key-acquisition出口按KEK variant互斥生成：`external-kms`只允许对应GenerateDataKey endpoint，`external-secret`只允许精确secret provider endpoint，`k8s-secret`只允许Kubernetes API且SA仅能get系统KEK的精确resourceName、不得list/watch或读取业务Secret；secret型variant因第9.4节限制只能用于functional-test。未使用的两类endpoint必须deny。

### 7.2 双重接管

- Kubernetes Lease 决定哪个 controller replica运行 reconcile loop。
- 每条任务通过数据库条件更新获取 `controller_owner + controller_lease_expires_at + row_version`；maintenance lock 不承担 controller claim 职责。
- 失去 controller lease 时停止推进并允许新 leader 接管；Job 在 live-source capture 完成前必须持续验证 fencing token。
- Job 名称包含 task/public ID 和 attempt；AlreadyExists 时必须校验 installation、request、config version、attempt 和 labels，禁止盲目复用。

### 7.3 分离 Runner 接口与两阶段执行

机器合同只冻结能力接口，不在主计划复制语言签名：BackupRunner 提供 environment detect、capture job-set prepare/authorize/checkpoint/seal 和 publish create；DrillRunner/PreflightRunner 分别创建隔离恢复与只读检查 Job；JobObserver 提供 status/result/log page、cancel 和 resource cleanup。`_ACCEPTANCE` 由 controller 的 provider adapter 直接条件写入，不创建独立 Job。Go/TypeScript 的具体方法签名由同版本合同生成或 parity test 锁定。

`RunnerJobStatus=pending|ready|running|succeeded|failed|canceled|unknown`；`unknown` 只表示 observer 暂时无法确认，不得据此推进任务。`RunnerJobResult.exit_classification=success|user_canceled|deadline|permission|capacity|dependency|integrity|coordination|transient_provider|permanent_provider|internal`，并由机器合同固定映射到 failure/retryable；结果包含 task/attempt identity、job UID/generation、phase、schema version、checkpoint/result hash、时间和 redacted evidence IDs。Checkpoint `type=mysql_transaction|redis_rdb|redis_scan_window|csi_snapshot|object_version_copy|gate_staging`；capture certificate 由 controller 签名并绑定 installation/task/attempt/fencing token、排序后的全部capture Job UID/generation/phase、全部 checkpoint hash、全部capture阶段staging resource UID/location hash、capture completed time 和 expiry；发布阶段才创建的remote manifest candidate不在签名输入中。签名 key purpose 固定为 `capture_certificate|acceptance_record|catalog_record`；每个 purpose 必须使用不同 key ref/version 和不同实际 key material，并同时使用独立 domain separator，禁止跨用途验签。Key rotation 保留仍被 artifact/catalog 引用的验证 key；签名 key 确认被攻陷时，P0保守地把该版本对应的signing dependency health写为`observed_health=degraded/health_reason=key_compromised`并要求人工恢复，不使用无法证明的 `compromise-at` 回溯切分。

Backup Job-set 流程固定为：

1. `PrepareCaptureJobs`至少创建一个不具备业务Secret读取权限的普通capture Job，以及需要secret bundle时创建一个独立secret-capture Job；后者使用第7.1节的专用SA，二者不能合并Pod或共享SA。每个Job完成镜像拉取、只读源挂载和依赖preflight，并按第9.4节KEK variant取得绑定task/attempt/phase、KEK id/version和encryption context的短期key-acquisition身份：`external-kms`调用GenerateDataKey，secret型provider只读取精确不可变version并以AES-256-KW包装本Job随机DEK。身份均不得拥有unwrap/decrypt/admin、artifact target或catalog权限；每个Job使用独立part DEK并只持久化wrapped DEK，禁止跨Pod传递明文DEK或KEK。身份最晚在`capture_abort_at + 60s`过期，capture结束时controller逐身份撤销并确认；任一撤销无法确认都阻断publish并告警。
2. 全部capture Job通过controller内置的mTLS status-relay接口分别报告`ready_for_capture`。Controller只有在机器合同要求的Job集合、phase和staging intent全部齐备且ready后，才把task推进到`ready_for_capture`；任何Job失败或超时均取消同组其他Job且不取得gate。
3. controller 获取 gate、排空 mutation/workload participants，取得 fencing token。
4. controller 为每个ready Job在数据库 observation row中写入绑定其identity的单次command slot和同一fencing token；各Job以mTLS身份读取并校验后捕获自己的source，旧generation不得取得command。
5. capture按profile分支但使用同一结果合同。`cluster`在gate内只建立能隔离后续读取的source checkpoint：MySQL开启并固定一致性snapshot transaction、Redis生成不可变RDB/AOF副本、CSI创建只读snapshot、对象存储在writer暂停期间完成有界全量List并冻结排序后的精确key/version清单；缺任一能力不得strong。Controller交叉验证全部checkpoint和清单hash后即可先resume participant，Job随后只从这些已隔离视图流式压缩、AES-GCM加密写staging，不能回读当前live view。`single-node`没有独立快照能力的part必须在gate内完成全部加密staging并seal后才resume。Secret-capture在两种profile下都必须在gate内完成版本双读、加密和seal。SIGKILL/OOM下不宣称执行应用级擦除，安全性依赖禁用swap/core dump、通过mlock或等价不可换页能力probe和短生命周期隔离；probe失败时acceptance任务在capture前返回`not_ready`。
6. 各Job只向status-relay报告带resource UID、source checkpoint、冻结清单hash、ciphertext checksum和token的结果，完成后关闭源连接、尽力覆盖进程内明文DEK并把staging seal为只读。Controller从Kubernetes/CSI、数据源只读checkpoint API及已CAS入库的Job result交叉验证，不得只信relay自报；全部必选capture/secret-capture单元和staging均sealed后，`SealCapture`生成绑定完整Job/capture-resource/checkpoint集合及gate barrier的聚合certificate。Cluster只有在全部隔离checkpoint已验证后由controller执行的正常resume才允许发生在staging seal之前；任何watchdog forced resume都使当前attempt的capture certificate不可签发，已签发则立即标为不可用于publish。Single-node和secret-capture在全部required staging seal前不得发生任何resume；任一profile无法证明checkpoint/seal先于其允许的resume时均不得seal。稍后才创建的remote manifest candidate不属于该certificate。
7. controller通过`CreatePublishJob`创建无源数据权限的publish Job。该Job只取得upload credential，provider policy把它限制为artifact prefix中明确列举的非final对象，以及独立remote staging root中唯一的manifest candidate key；`manifest.json`、`_COMMITTED`、`_ACCEPTANCE`和catalog均显式deny。Controller在写candidate前先创建`type=remote_manifest_candidate/lifecycle=creating`的staging resource intent。Publish Job在gate外上传加密part/index，生成不超过256 KiB的canonical redacted manifest bytes并条件写candidate，最后报告immutable version/checksum/length，由controller登记后CAS为sealed。
8. controller的provider adapter使用仅能读取该candidate key的一次性credential取得manifest bytes，校验schema/JCS/checksum/length后，在`publishing`内以单条CAS写`can_cancel=false + commit_started_at`。CAS成功后按第6.2节把candidate的精确bytes复制进manifest external-action row，再使用最小权限finalizer credential条件写`manifest.json`；确认成功后把candidate staging resource CAS为deleting，使用精确delete grant删除并验证后置deleted。Controller随后生成`_COMMITTED` canonical bytes、先持久化marker action再条件写marker。Candidate删除失败或未知时不得写marker，按staging lifecycle接管并最终失败为`staging_cleanup_failed`或进入ownership resolution。短期credential envelope可以续签，但final key、完整bytes和逻辑action hash不可改变。
9. controller验证marker后把artifact CAS为committed，结束publish Job、删除全部staging resource并持久化cleanup evidence。Purpose为`acceptance`时，controller生成并签名canonical `_ACCEPTANCE`，在任何网络写之前把完整signed bytes持久化进acceptance action，再通过provider adapter conditional-create，不创建Acceptance Job。若`local_acceptance=true`，controller同样先冻结并持久化完整signed `artifact_registered` bytes，再向外部catalog create-if-absent；record必须同时包含acceptance-record和catalog-record两个signing key identity，该成功append是最终eligibility线性化点。此后只允许幂等写本地`succeeded/eligible`投影。Local acceptance为false时不写registration并以non-eligible succeeded结束。`functional_test`不写`_ACCEPTANCE`或registration。尚未持久化action且签名或catalog直到deadline仍不可用时，以`failed/signing_key_unavailable|catalog_unavailable`结束；action已持久化但结果未知时进入`finalization_unknown`。已存在相同bytes为幂等成功，可证明不存在时为相应dependency failure，内容冲突为`artifact_conflict|catalog_conflict`。

Status-relay是controller Deployment暴露的有界内部mTLS接口，不是独立服务、消息队列或第二个持久化系统；command slot、accepted sequence和result hash的唯一权威仍是数据库observation row。它只承载小型command/status/progress/result envelope，不承载manifest、payload、日志或index。Command slot只能由controller写、对应Job读；Job不能写command或自行签发token/certificate。除secret-bundle collector为读取allowlisted Secret而显式投影短期受众受限token外，Job均`automountServiceAccountToken=false`。Relay mTLS identity绑定installation/task/attempt/phase/Job UID/generation和短expiry；消息携带严格单调sequence及body hash，controller以DB CAS接受，重复sequence仅在body hash相同情况下返回原确认，跳号或同sequence异hash拒绝。无需再叠加逐消息应用层签名和前序hash链；最终capture certificate负责对完整结果集签名。镜像调度或拉取耗时不得计入quiesce hold。

本地capture staging resource必须是attempt/phase专属、可跨对应capture/publish Job接管的PVC或受控single-node目录；remote manifest candidate则是同attempt专属的精确provider key/version，两类资源共用第6.2节的inventory和cleanup状态机。所有持久化part在capture时已完成流式压缩与AES-GCM加密，明文只允许存在于已通过不可换页能力probe的有上限进程内存，不落持久卷。创建前写独立`creating` intent；权威查询证明未创建时CAS为`absent`，创建后登记UID或immutable version、location hash及owner marker，seal后本地资源只读挂载给publish Job。未seal失败/取消在resume完成后逐项清理；已seal资源保留到publish确定结束且不得超过`staging_retention_seconds`。远端marker校验成功后，controller在backup终态前按UID/owner marker或精确key/version删除并验证全部staging已为`absent|deleted`；任一无法证明删除时任务`failed/staging_cleanup_failed`，但技术完整的committed artifact仍可供显式functional_test。Cleanup成功后，只有acceptance任务才写签名`_ACCEPTANCE`，并且仅当`local_acceptance=true`时append `artifact_registered`。Append成功即形成灾备资格，controller将record ID/hash与本地终态投影在同一CAS保存；DB CAS失败持续重试，不得改判failed或接受cancel。Create-if-absent超时后按external-action row Stat/Open判等；manifest/index/marker等core对象冲突使artifact不可用，`_ACCEPTANCE`或catalog冲突只使acceptance readiness degraded，二者均立即告警。Manifest只保存可重算资格输入；promotion不参与backup资格。

Staging orphan-GC 只处理 attempt claim/Job/heartbeat 均超过安全窗口、没有活动 publish、且 UID/owner marker 与 intent 完全匹配的资源。无法证明 ownership 时只告警；GC 结果写 attempt cleanup、event 和 audit。密文上传 prefix 的 orphan-GC 仍按第 13 节独立处理：这里的“commit marker 缺失”专指 `_COMMITTED`，不能替代 owner marker/UID 的所有权证明。

### 7.4 数据模块接口

P0-0a 为每个业务 owner 冻结三类小接口：`Collector.Capture(ctx, CaptureRequest) (PartResult, error)` 只写任务 staging；`Normalizer.Normalize(ctx, RestoreTarget, NormalizationPolicy) (NormalizationResult, error)` 只在 restore 写权限阶段运行；`Verifier.Verify(ctx, ReadOnlyTarget, VerifyRequest) (VerifierResult, error)` 只接收只读目标。`PartResult.status=completed|failed|canceled`，不另造 warning 状态，warning 放结构化数组；必选 part 不允许 skipped。请求统一包含 task/attempt/phase identity、config snapshot、deadline 和取消信号；结果统一包含 schema version、part/category、checkpoint、统计、warnings、已登记evidence IDs和 failure category。跨域依赖只能通过 registry `depends_on` 引用，模块不得直接修改其他 owner 的结果或任务主状态。

## 8. Maintenance Gate 和一致性

### 8.1 Gate 协议

- 所有可能修改六类业务数据、workspace、Redis、对象或 schema 的 service/worker 操作都必须持短期 mutation lease或属于可整体暂停并 ACK 的 participant，不限于“高风险操作”。Lease acquisition 与 gate acquisition 必须锁定同一 scope 的唯一 gate row：mutation事务先以数据库当前读 `SELECT ... FOR UPDATE` 锁 gate row、确认`idle+generation`后插入lease再释放；controller也先锁同一row、确认无新lease条件后执行`idle -> acquiring`。锁顺序固定为 gate row → lease rows → business row，隔离级别和死锁重试策略进入机器合同。禁止用无锁子查询、事务快照或先查询再插入模拟互斥。Lease 记录 operation identity、generation、不可超过配置上限的 TTL 和 heartbeat；超时只表示所有权失效，不等于旧写入已经停止。
- Strong acceptance 配置必须维护 append-only source-writer registry，并把 version/hash 固化进任务 config snapshot：列出所有数据库账号、Redis 客户端身份、对象 prefix writer、workspace/runtime writer 和 DDL/migration 身份，并为每项提供 lease/participant/拒绝策略。Preflight 对实际 MySQL GRANT、Redis client、bucket policy、运行态 inventory 和审计 writer 集合做完整差集；发现未登记写身份或登记身份无法观测时，acceptance 任务必须在拿 gate 前失败为 `writer_registry_drift`。显式 functional-test 可在证据完整时降为 bounded，完全不可观测则 weak；不得得到 strong。
- Source-writer check row的`expires_at=checked_at+artifact_health_interval_seconds`，且只能供完全相同的config/registry version使用；后台探测失败必须原子写unknown原因，不能延长上一条clean结果。`last_success_at`只在完整差集为clean时刷新。
- 数据库 mutation 必须在提交业务写的同一事务内再次确认 lease 未过期且 generation 未变化。对象/workspace 等不能与控制库共事务的写入必须由 participant pause 覆盖，或在每次可见性发布前验证 lease；失去 lease 后立即停止且不得发布。Controller 只有在所有旧 generation lease 主动结束，或对应 participant 明确 ACK 已中止后才能进入 `held`；仅等待 lease TTL 过期不能获得 strong，无法证明停止时任务失败或降为 bounded。
- controller 以 CAS 执行 `idle -> acquiring` 并递增 generation，从此拒绝新 lease；等待旧 generation 的 lease 和 workload participant ACK 排空后，执行 `acquiring -> held` 并递增 fencing token。
- 正常释放为 `held -> releasing -> idle`，保留 token 数值；新 owner 获取时再次递增。
- acquisition timeout默认60秒，lock TTL默认900秒；`quiesce_max_hold_seconds`是不可续期的绝对上限，不能用heartbeat无限延长停写。机器合同必须保证lock TTL大于controller heartbeat failure window；capture abort和participant resume按第6.5节同时受task deadline与absolute hold约束，前者固定至少提前`watchdog_safety_margin_seconds`。配置或任务剩余时间不满足关系约束时拒绝进入gate。
- 超过 acquisition timeout 返回 `quiesce_timeout`；超过 absolute hold deadline 终止捕获、释放/过期锁并使任务失败。
- participant状态机固定为`running -> pausing -> paused -> resuming -> running|error`；pause阶段确定失败允许`pausing -> error`，`error -> resuming`只能由同generation的controller恢复操作或watchdog触发。开始新gate generation前，上一generation的全部participant必须已回到running且`resume_result=succeeded|forced`；controller随后在同一CAS递增generation，并把新generation的`resume_result/participant_failure_code`重置为`none/none`后才允许`running -> pausing`，历史forced-resume事实保留在event/audit。正常resume成功写`running/succeeded/none`；forced resume成功写`running/forced/forced_resume`；`resume_result=failed`时observed state必须为error并写其他非none failure code。ACK必须包含participant ID、generation、最后完成mutation/offset和时间，上一generation的ACK不得复用。SealCapture只接受当前generation且没有forced-resume事件的证据：single-node及secret-capture要求其seal时间早于正常resume开始；cluster允许`resume_result=succeeded`，但必须证明全部隔离checkpoint已在正常resume开始前验证完成且后续只读取这些冻结视图。Publish commit CAS必须再次确认该generation此后也没有forced-resume事件，避免已签发certificate绕过晚到的安全事实。
- 无论 capture 成功、失败、取消、controller 换主或 absolute deadline 到期，都必须进入 resume。恢复顺序固定为 storage/runtime writers → worker consumers/schedulers → API mutation gate；每项幂等记录结果。
- controller 失联时 participant watchdog 以数据库 gate expiry 和 generation 为准自动 resume；不能只依赖原 controller 回调。Controller 下发同一 generation 的 `capture_abort_at` 和较晚的 `participant_resume_at`：capture Job 到前者必须先关闭源连接并永久拒绝该 attempt seal，participant 到后者才允许恢复。为避免数据库同时不可用导致无限停写，participant 在成功读取两个 DB deadline 时同时启动只用于安全恢复的本地 monotonic watchdog；DB 持续不可达超过 `watchdog_db_unavailable_grace_seconds` 且 resume deadline 到达时执行幂等 resume。恢复 DB 后必须写 `forced_resume` 事实；SealCapture和publish commit CAS都必须确认没有forced resume、capture完成时间早于abort deadline且所有participant仍属于同一generation，任一条件无法证明即失败并使已签发certificate不可用。该 watchdog 不能授予锁所有权或签发 fencing token。部分 resume 失败使 backup failed、`failure_category=quiesce_resume_failed`，并触发 `critical` 运维告警。

### 8.2 Quiesce 参与者

必须登记并 ACK：

- API/service：用户、实例、workspace、Teams、Skill Hub、模型/风险/资源管理等写路径，包括 shared workspace 路由。
- worker：SyncService、RuntimeScheduler、Skill materialize worker、Team consumers/outbox。
- runtime：可能直接写 workspace、Redis、对象存储的 runtime agent/Pod。
- schema：应用 migration、管理员 DDL 和 rollout 期间禁止开始 strong backup。

route 扫描只发现遗漏，真正保护必须在 service/worker/runtime participant。每个写路径必须明确采用“事务内 lease 再校验”或 participant pause；未声明写路径测试失败。无法暂停且可能跨数据源写入的 participant 会使任务失败或降为 bounded，不能获得 eligibility。系统备份自身 append-only audit 的例外按第 6.4 节处理。

### 8.3 一致性判定

- `strong`：所有跨源写入在逻辑 barrier 后停止；MySQL transaction snapshot、Redis RDB/AOF、CSI snapshot、object version/copy 或 gate 内完整 staging 均有不可变 checkpoint。
- `bounded`：有起止时间、逐项 checksum，但逐 key/object/file 读取点不同，例如共享 Redis SCAN。
- `weak`：捕获时来源可变化或缺少可验证 checkpoint。

`backup_cutoff_at` 是 gate held 后建立的逻辑 barrier；每个 part 另外记录 `captured_at`、checkpoint 类型和 source position。不能用相同时间字符串伪装真正的跨源原子快照。

## 9. Artifact、加密和灾备等级

### 9.1 BackupArtifactStore

接口必须流式支持 `Put/Open/Stat/List/Delete/DeletePrefix/Preflight`、cursor 分页、multipart、幂等删除和显式 commit marker；禁止把大 artifact 全量读入内存。

Provider capability持久化`status=supported|degraded|unsupported`，查询/指标另派生`capability_state=supported|degraded|unsupported|unknown`：命中当前精确provider/ref且未过期的行复用status，缺行或过期固定为unknown。每行`expires_at`取`checked_at+artifact_health_interval_seconds`与probe credential/CA已声明的有限有效期之最小值；明确无expiry的不可变ref不缩短该窗口，但ref无法解析或已过期时不得产生supported。Supported只由完整正向probe产生；deterministic API/版本不支持才为unsupported；暂时provider/credential/响应问题为degraded，均使用第6.2节`capability_reason_code`闭集。创建准入只接受所需能力组中每项effective state=supported，其他三种均fail closed。Capability code在P0是下述完整闭集，未来增加code必须升级兼容合同。每项结果包含provider role、capability code、observed_at、expires_at、provider version和reason code。Artifact、catalog与evidence provider分别评估，禁止把catalog append或evidence delete能力挂到artifact provider。Artifact code为`conditional_create|checksum_bound_request|scoped_upload_credential|scoped_read_credential|scoped_delete_credential|multipart_resume|object_checksum|version_listing|delete_marker_listing|strong_read_after_write|tls_verified`；catalog code为`conditional_create|checksum_bound_request|scoped_read_credential|scoped_append_credential|strong_read_after_write|provider_snapshot_listing|inventory_manifest_listing|versioned_absence_proof|tls_verified`；evidence code为`conditional_create|checksum_bound_request|scoped_read_credential|scoped_write_credential|scoped_delete_credential|object_checksum|strong_read_after_write|versioned_absence_proof|tls_verified`。Evidence写、读、删credential必须三分，且只作用于独立保留root；可以与artifact/catalog使用同一物理S3服务，但root、policy和typed ref必须独立。`checksum_bound_request`必须由真实provider请求证明key、checksum/content-length、expiry和conditional-create约束，不能用应用内路径检查代替。不存在性能力组满足`strong_read_after_write`下的强一致精确Stat，或`versioned_absence_proof`任一项即可。完整发现能力组满足以下任一项：`provider_snapshot_listing`返回覆盖整个keyset且有效至扫描deadline的不可变snapshot token；或`inventory_manifest_listing`返回provider生成、带生成时间/范围/count/checksum且对象版本固定的不可变inventory manifest。普通ListObjects分页、重复两次相同List或只有单页强一致均不属于该组。只有当前操作所需能力组整体不满足时才hard reject，不能把组内备选项逐项设为必需。

- S3-compatible artifact provider必须探测conditional create、checksum-bound request、分离的read/delete/upload-issuer credential、multipart、versioning、list versions/delete markers、精确Stat和checksum metadata；catalog provider单独探测read/append credential、conditional create、上述不存在性能力组及完整发现能力组；evidence provider单独探测read/write/delete credential、conditional create、对象checksum及不存在性能力组。Manifest、`_COMMITTED`与`_ACCEPTANCE`分别使用精确create-if-absent request；缺少当前路径的硬能力组时同步preflight reject，执行阶段漂移则任务失败且不得发布。仅需要精确record ID的受限import可在没有完整发现能力组时工作，但不能完成P0灾备完整发现验收。
- PVC/local只可作为仓库内测试fake验证接口和故障注入，不属于P0公共`artifact_target_config`、正式部署或验收矩阵；staging PVC/HostPath与artifact provider是不同概念。
- Versioned bucket 的 Delete/DeletePrefix 必须删除属于该 artifact prefix 的所有 version 和 delete marker，并分页复查；只得到当前 HEAD 404 不代表 prune 完成。

Artifact prefix 固定为：

```text
<root>/<origin_installation_id>/<backup_public_id>/<attempt_no>/
```

Manifest candidate不在artifact prefix内，固定为`<root>/_clawmanager_staging/<origin_installation_id>/<backup_public_id>/<attempt_no>/manifest.json`；`_clawmanager_staging`是provider policy保留根，不能作为业务source或正式artifact prefix。Candidate必须登记为backup staging resource并在marker写入前删除。

已 committed prefix 永不覆盖。multipart 只在同一未提交 attempt 内按 ciphertext checksum 续传；终态失败后人工重试创建新 backup ID。

### 9.2 Artifact target tagged union

- `artifact_target_config`在P0固定为必填discriminator `type=s3`且`additionalProperties=false`；未知type返回`validation_failed`，不得把测试fake暴露为生产配置。`restore_target_config`由第12节单独定义，二者不得共享wire schema。
- S3：`endpoint`、`region`、`bucket`、`prefix`、`path_style:boolean`、`tls={verify:true,ca_ref?}`、`read_credential_ref`、`delete_credential_ref`、`upload_credential_issuer_ref`。三个 ref 必须解析为不同最小权限 policy：read 只读已提交对象，delete 只删指定 artifact version/prefix，issuer自身只允许controller workload identity调用，并分别签发绑定task/attempt/action、对象闭集、checksum/content-length和deadline的短期grant；publish身份只能取得非final上传及manifest-candidate写grant，controller finalizer身份只能取得该candidate精确read/delete及final key create-if-absent grant。任一身份都不能请求超出模板的grant；单一全权`credential_ref`非法。Endpoint 必须是无 userinfo/query/fragment 的 `https` URL；HTTP 或关闭证书校验一律按 `transport_unverified` hard reject。私网/loopback/link-local 和 DNS 解析结果按部署 allowlist 校验，连接后还要校验证书 hostname 与实际 peer address。Prefix 规范化后不得为空、为根或与 source/reserved prefix 重叠。
一个 default config 只绑定一个 artifact target。URI、凭据和 KEK 只保存 typed ref；不再使用含义不清的 `backup_target_uri_ref`。

Secret/ref 机器合同固定为 tagged reference，而不是自由字符串：K8s 使用 `{provider:"k8s-secret",namespace,name,key,resource_version}`；artifact credential 的外部引用使用 `{provider:"external-secret",resource_id,key_version,auth_ref}`；KEK 使用第 9.4 节的 provider 闭集。Namespace、provider、resource ID 和 auth_ref 必须命中部署 allowlist，API 不接受 URI userinfo、内联 credential、通配 namespace 或省略资源版本的 acceptance 配置。每个 artifact 固化可解析的 credential/CA ref version；这些历史版本的保留期不得短于 artifact retention，活动 promotion 引用期间不得删除。轮换后新任务只用新版本，旧版本缺失时置 `credential_unavailable`、使 `backup_recovery_readiness` degraded，并禁止用当前配置悄悄替换历史身份。

`target_class=dr-ready-external|same-cluster-copy`，等级规则：

- `dr-ready-external`：artifact与源bucket/PVC/namespace/集群故障域解耦，管理员attestation已审计，且artifact read credential、CA bootstrap、验签public key bundle、recovery catalog和`external-kms` KEK均可在源集群失效后取得。
- `same-cluster-copy`：S3 bucket/prefix与源处于同故障域，或KEK只能从源集群取得；只允许functional_test。
- S3满足全部外部条件才为`dr-ready-external`，否则为`same-cluster-copy`；任何source bucket/prefix或保留控制路径重叠仍按`source_overlap` hard reject。

系统执行可验证的endpoint/bucket/PVC/namespace同源排斥；`target_failure_domain_id`来自配置中append-only故障域registry，attestation是管理员对该稳定ID的声明，不得描述成系统能完全自动证明，也不得通过改显示名创建新的恢复点分组。Attestation必须绑定artifact target config hash、artifact credential/CA ref version、KEK ref/version、acceptance/catalog signing key ref/version、catalog provider/ref/version、故障域ID、签署actor、签署/过期时间；任一绑定身份变化后自动失效，旧任务仅保留历史快照。

### 9.3 目录和发布协议

最小内容如下；`_COMMITTED`及其前面的文件构成committed core。`_ACCEPTANCE`是仅由acceptance任务在进入succeeded前追加的post-commit文件，functional-test不创建它：

- `artifact-index.json`
- `restore-metadata/envelope.json`
- `secrets/secret-bundle.enc`
- `mysql/**`
- `redis/<source_id>/**`
- `objects/index.jsonl.enc`、`objects/parts/**`
- `workspace/index.jsonl.enc`、`workspace/parts/**`
- `deployment/resources.yaml.redacted`
- `control/evidence.json.enc`（redacted control-evidence sidecar）
- `manifest.json`
- `_COMMITTED`
- `_ACCEPTANCE`（post-commit；仅acceptance任务必需）

顺序固定：冻结 capture context 并计算 `capture_context_hash` → capture 期间流式分片压缩/加密 → 固化 source checkpoint/certificate → artifact index → final redacted manifest → 对“不含自身 checksum 字段”的完整 manifest 计算 SHA-256 → `_COMMITTED` → controller 验证 marker → staging cleanup → controller 条件写 `_ACCEPTANCE`，local acceptance 为 true 时再写 `artifact_registered` → backup 终态 CAS。Manifest schema 禁止定义 `manifest_checksum` 或最终 `acceptance_eligible` 字段；前者写marker、controller check result/external-action observation和数据库，后者只写任务终态记录，post-commit acceptance record仅保存其形成前已确定的本地资格输入与结论。`capture_context_hash` 已承担加密解释的冻结职责，不再维护语义重叠的 `manifest_core_hash`。

- manifest 的 `commit_marker` 只记录 path 和格式版本，不保存 marker checksum。
- `_COMMITTED` canonical JSON 固定包含 backup public ID、schema version、manifest checksum 和 artifact-index checksum。
- marker checksum 计算后只存controller check result、external-action observation和backup数据库行，避免自引用环；publish Job result不包含由controller后续生成的marker checksum。
- `_ACCEPTANCE` 使用 create-if-absent canonical JSON，由 controller 固定生成并直接写入；unsigned payload包含 backup/attempt identity、manifest/marker checksum、staging cleanup evidence ID/hash、`local_acceptance=true|false`、排序后的 local reason codes、decision time、config version 和 acceptance-record signing key id/version，外层`signature`按第3节规则计算。Local acceptance 只计算 artifact/consistency/target/cleanup 等已确定输入，不包含 catalog 或数据库终态。完整对象checksum存数据库、audit和后续registration；它不反向进入manifest/index/marker。已存在但内容不匹配返回`artifact_conflict`。
- artifact index 覆盖所有 encrypted payload、envelope 和 sidecar，不包含自身、manifest、marker 或 post-commit acceptance record。
- 正式读取、functional drill/preflight和prune先要求marker、manifest和index相互匹配；acceptance drill还必须验证`_ACCEPTANCE`签名、`local_acceptance=true`以及checksum匹配的有效`artifact_registered`，并以强一致Stat或版本化不存在证明确认其确定性tombstone key不存在。当前安装promotion另外要求本地backup数据库投影已收敛为eligible；catalog-import不能成为当前安装promotion。灾后数据库不可用时以create-if-absent对象、target version history和外部签名catalog验证，不依赖本地promotion记录。

Recovery catalog 是独立于源业务数据库和源集群 Secret 的 append-only、create-if-absent 签名对象集合。`catalog_provider=s3`，并必填`discovery_mode=provider_snapshot|inventory_manifest|known_record_only`；测试可使用file fake但不进入公共配置。`known_record_only`只能支持已知record ID的精确读取，不能完成P0完整发现或四矩阵验收。配置以typed provider指向预置的外部catalog root，并分别包含只读`read_credential_ref/version`、只允许该root下create-if-absent的`append_credential_ref/version`及在前两种mode下读取provider snapshot/inventory manifest的只读ref；各ref不得拥有delete/overwrite权限，append与read不得复用。记录类型固定为：

- `artifact_registered`：仅在 `_ACCEPTANCE.local_acceptance=true` 后写入；record ID 在发出 append 前按 `sbr_ + lowercase(RFC4648-base32(first_160_bits(SHA-256(UTF8(JCS(["artifact_registered",origin_installation_id,backup_public_id,attempt_no]))))))` 确定生成、无 padding，并与 canonical bytes hash/action key 一起先持久化。记录包含 origin installation/matrix、artifact immutable locator/version、manifest/marker/acceptance checksum、credential/CA identity、KEK id/version、灾后 bootstrap identity、acceptance-record signing public-key id/version、catalog-record signing key id/version 和数据库 decision time；其 create-if-absent 成功是 backup eligibility 唯一灾备线性化点。
- `artifact_deleted`：prune删除成功后写入的tombstone，引用`artifact_registered` ID/hash、prune run、冻结candidate hash、首次把artifact CAS为deleted的数据库时间和首次execute actor。完整signed bytes必须在首次append前写入对应prune item/external-action；retry actor和retry operation只进入audit，不改变tombstone payload。

两类记录都不得包含可重放credential。Registration key固定为`registrations/<record_id>.json`，tombstone key固定为`tombstones/<artifact_registered_record_id>.json`。相同key/相同canonical bytes为幂等成功，不同bytes为`catalog_conflict`。完整发现要求第9.1节完整发现能力组：每次扫描固定provider snapshot token或不可变inventory manifest，完成一次全量keyset分页，以页序号、首末key、页checksum链接形成rolling hash；逐页把合法registration/tombstone幂等写入`system_backup_catalog_records`，到EOF后在同一consistent read中复算record count/hash，匹配后才登记receipt并把scan置succeeded。固定snapshot不重复扫描同一页；无完整发现能力时只能按已知record ID精确import，overview必须标记full discovery unsupported，且不能完成P0灾备矩阵验收。灾备管理员可从catalog-record分页API选择已发现、验签有效且未tombstone的registration，再提交其ID/hash创建import，不需要预先从源安装取得ID。Tombstone不存在使用第9.1节不存在性能力组；普通404、连续两次404或最终一致List均只能记为unknown。P0不自动删除或压缩provider中的外部catalog记录；本地扫描inventory按第13节受控GC，不能据此删除外部对象。Catalog signing key确认泄露时，把该key version签发的本地record置`validation_state=invalid/catalog_record_failure_code=key_compromised`；acceptance signing key泄露则保留catalog签名判定，但对应signing dependency health置degraded。两类事件都把引用该key version的现有catalog import置`import_usable=false/import_unusable_reason=signing_key_unavailable`，禁止新import/acceptance并立即告警。隔离演练必须仅凭catalog scan/inventory、catalog import、灾备预置bootstrap和artifact完成发现、读取、验签与解密，并证明源集群网络及凭据不可用。
- object key、workspace path、UID/GID、自定义 metadata 和其他可能敏感的 index 内容必须加密；公开 artifact index 只保存密文 path、size、SHA-256 和 framing 信息。任何明文 sidecar 必须有字段级 redaction schema。

### 9.4 加密和明文临时数据

- 默认 envelope encryption + AES-256-GCM；每片随机 nonce，AAD 包含 schema version、backup ID、attempt、path、part index 和 `capture_context_hash`。Capture context 在读取源数据前冻结的只是 path 编码/分片命名规则与 part 顺序，不要求预先知道实际扫描得到的 path 列表；实际 path 逐项进入对应 chunk AAD 和加密 index。Context 还包含 schema/算法、任务/attempt 和 DEK envelope identity，不包含晚到 checkpoint、checksum、warning 或终态字段；其 canonical 字段集进入机器合同和最终 manifest。
- 每个 capture phase/part 的 wrapped DEK、算法、nonce/tag、KEK id/version 和 ciphertext checksum 分别写入 envelope entries；明文 DEK/KEK 永不跨 Job 传递或进入 artifact。
- Secret bundle 使用独立 part/AAD。低熵 Secret 只记录存在性、resourceVersion 或备份专用 HMAC，不记录裸 SHA。
- 所有dump/workspace/secret采用流式压缩后加密写staging；持久化明文一律禁止。工具确实需要seek时只能使用有上限的内存临时文件，超过上限`capacity_exceeded`，不能回退到磁盘明文。
- 失败证据只能保留 ciphertext、redacted index、Job 摘要和清理结果，不得保留明文 staging。
- eligible artifact 的 KEK 必须具有源集群外的 key id/version 解析和恢复证明；只挂载源集群 K8s Secret 时最多为 `same-cluster-copy`。

加密 framing 在机器合同中固定 magic/version、header length、chunk index、plaintext/ciphertext length、nonce、tag 和 checksum 的字节序与上限；AAD 使用长度前缀编码，禁止字符串直接拼接。每个 chunk 的 nonce/envelope metadata 必须与ciphertext以临时文件+fsync+原子rename或等价事务方式一起提交到任务专属加密staging；接管只复用metadata/ciphertext两者checksum和owner identity均匹配的chunk，无法证明一致时使用新nonce重新加密并覆盖未提交attempt。进程内明文区在正常seal/异常处理路径尽力擦除；SIGKILL/OOM不宣称执行擦除，正式acceptance依赖启动时通过的no-swap、core-dump disabled、内存上限及实际lock/unlock配置上限字节的probe；需要`IPC_LOCK`时必须使用第7.1节的专用模板例外并进入RBAC/Pod Security负向测试。

KEK provider固定为`external-kms|external-secret|k8s-secret`，并使用不同闭集协议：`external-kms`必须提供GenerateDataKey/Decrypt、encryption context绑定和task-scoped identity撤销；`external-secret|k8s-secret`必须提供精确不可变32-byte KEK version，capture Job用`AES-256-KW`包装随机DEK，短期读取身份只允许该version且在capture后撤销，KEK只存在于受保护内存。P0只有`external-kms`可用于acceptance；`external-secret|k8s-secret`统一最多`same-cluster-copy/functional_test`，不再因外部secret存在灾后auth path而升级eligible。所有variant都必须记录不可变key version并保留至artifact及hold到期；轮换不得删除仍被committed artifact引用的版本。

备份内容 HMAC 与cleanup owner marker HMAC使用两个独立、带版本的key ref，均不得复用KEK/DEK。数据库只保存HMAC和key version，外部marker可保存随机token；比较时以常量时间重算HMAC。Cleanup HMAC key不进入业务artifact，丢失或版本不可用时自动cleanup必须fail closed为`cleanup_unsafe_target`；只能通过第12.2节经审计的ownership-resolution API及其外部不可变证明恢复，不允许绕过数据库CAS直接执行人工删除。

## 10. Manifest 和 Verifier

Manifest 顶层至少包含：schema/app/git/version 时间、origin installation、orchestrator/profile/runner/purpose、migration catalog hash 和 schema hash、target class/risks/attestation、KEK recovery 摘要、consistency、提交前已知的资格输入与 disqualifier codes、backup parts、artifact-index checksum、marker path、control-evidence sidecar ref/checksum、secret policy、schema object coverage、必要且 redacted 的 config recovery parameters 及其完整 snapshot hash、六类业务摘要、warnings。Manifest 不包含自身 checksum、staging cleanup 结果或最终 `acceptance_eligible`；API 可以把数据库中的终态资格与 manifest DTO 并列返回，但不得伪装成 manifest 原字段。

Manifest 在 artifact index 和 capture certificate 完成后一次性 canonical 生成，生成后任何字段不得修改；晚到 operational warning 和终态资格只写数据库 events/audit。加密 AAD 只引用预先冻结的 `capture_context_hash`；capture context 任一字段变化都必须重新加密，不能修改后沿用旧 AAD。

Compatibility判定固定为：未知major、必要part/check不可理解、目标引擎版本不在矩阵或需要destructive/down migration为`unsupported`；语义相同为`supported`；仅additive/诊断差异为`compatible_with_warnings`。V1 P0 writer只生成当前版本，reader验证当前与上一compatible fixture；一旦未来存在仍受保护的breaking历史artifact，发布门禁必须先引入对应reader方案。不得仅凭`schema_hash`相等判定兼容。

Verifier 结构固定：

```json
{
  "category": "users|instances|ai_gateway|teams|resources|skill_hub|control_plane|artifact|catalog|isolation|cleanup|prune|promotion",
  "mode": "backup_validate|restore_validate|preflight_diff|artifact_health|artifact_full|catalog_import|cleanup_verify|prune_verify|promotion_validate",
  "checks": [{"id":"registry-id","status":"passed|warning|failed|skipped","skip_reason":null,"expected":{},"actual":{},"evidence_ref":"string","warning_code":null,"check_classification":null,"failure_category":"none"}]
}
```

Verifier不持久化与checks重复的顶层status/warnings/errors；查询时按checks唯一派生aggregate。前七个category用于数据/控制面verifier，后六个用于相应运维检查；机器registry必须为每个`target_type+mode`列出唯一允许category集合，例如cleanup只允许`cleanup_verify/cleanup`、prune只允许`prune_verify/prune`，禁止实现自行复用backup mode。Check/warning code来自同版本registry，且每个check的`expected/actual`都有closed JSON Schema和redaction classification。`status=passed|warning|failed|skipped`；skipped reason闭集为`optional|not_applicable`，非skipped时必须为null。Failed check必须填写第4.4节`check_classification`及非none failure category，其他status两字段分别为null/none；registry固定两者映射。聚合顺序为failed > warning > passed > skipped；P0必选category不允许全部skipped。`system_backup_check_results.target_type=backup|drill|preflight|artifact_verify|catalog_import|promotion|cleanup|prune_run`；event target type使用同一闭集再加`catalog_scan|catalog_record|operation|system`。

P0 必选 part 为 `mysql|redis|object_storage|workspace|deployment_resources|secret_bundle`。即使 allowlist 为空也必须生成可验证的空 secret bundle。部分备份只允许测试并强制 non-eligible；必选 part、六类业务 verifier 或 backup 控制面 verifier failed 时任务 failed。`skipped` 不得用于掩盖 P0 必选数据。

## 11. 各数据源固定策略

### 11.1 MySQL

- 默认 `mysqldump --single-transaction --routines --triggers --events` 等价策略，并显式记录工具/Server 版本、charset/collation/timezone/SQL mode、binlog/GTID。
- strong 前检查所有必选业务表为事务型引擎，并在 gate 内禁止 DDL；发现非事务表或外部 DDL 能力时不得 strong。
- 合同固定 GTID purged、DEFINER 重写/拒绝、view/routine/trigger/event 权限、FK、auto_increment、max packet 和大表进度策略。
- core table dump 失败 hard fail；不支持的 schema object 必须进入 compatibility，不得静默丢失。
- Drill MySQL 在导入前固定 `event_scheduler=OFF`，禁止网络外联以及 `FILE|SUPER|SYSTEM_USER|CREATE FUNCTION|INSTALL PLUGIN` 等可执行/宿主权限；restore adapter 必须把 table/data 与 routine/trigger/event 定义分段，先导入数据，再按 normalization registry 重写/拒绝 DEFINER 并静态校验可执行对象，最后才创建允许的 routine/trigger。P0 drill 永不启用 event，任何未登记 event/UDF/plugin 或导入阶段触发外联都以 `normalization_failed` 终结。

### 11.2 Redis

- 每个source显式声明`topology=dedicated_instance|shared_keyspace`、`capture_mode=rdb|aof|scan_dump`、connection ref、DB和必选prefix/keyspace；合法矩阵固定为dedicated→`rdb|aof|scan_dump`、shared→`scan_dump`。
- RDB/AOF 仅允许 ClawManager 独占实例，并只能恢复到专用临时 Redis。
- shared keyspace 强制SCAN/DUMP，保存key type、源Redis server time、逐key captured_at、PTTL及由二者计算的绝对`expires_at`、序列化payload checksum、stream/group可恢复摘要和捕获窗口，最多bounded。`ttl_restore_policy=preserve_absolute|restart_remaining`；acceptance固定`preserve_absolute`，恢复时已到期key不写入，未到期key使用`expires_at-target_server_time`设置剩余TTL。`restart_remaining`只允许functional_test并使用捕获时PTTL重新计时。源/目标Redis与controller数据库时间的最大两两偏差超过任务snapshot中的`redis_clock_skew_seconds`时任务失败`preflight_failed`，不得把负TTL截断后冒充通过。
- Redis Cluster/Sentinel、无法满足命令 ACL 或无法枚举必选 keyspace 时，创建阶段已由静态/cached capability 确认则返回 `not_ready` 且不创建任务；执行阶段才发现则任务 `failed/preflight_failed`。不得返回未定义的 `unsupported` category。
- source 去重使用 connection ref identity 或专用 HMAC fingerprint，不把含凭据 URL 写入 manifest/log。

### 11.3 对象存储

- P0 恢复当前可见对象及必要 metadata，不承诺完整版本历史或 delete-marker 历史。
- Strong capture要求对象源支持version ID，且所有该prefix writer均已pause；在gate内完成有界全量分页并冻结按key排序的精确`key+version_id+size`清单及root hash，resume后只按该清单复制immutable version。若分页不能在hold内完成、对象无version ID、List期间keyset漂移或只能在resume后读取当前对象，则本part最多bounded；未知删除/新增不得静默忽略。清单超过`max_source_items|max_index_bytes`为`capacity_exceeded`。
- index 记录 key、size、SHA-256、etag、version ID（可得）、last modified、content type 和必要 metadata。
- “必要metadata”闭集为`content_type|content_encoding|cache_control|content_disposition|content_language|expires|user_metadata_allowlist`；未知用户metadata默认不恢复并产生disqualifying warning，单对象metadata canonical JSON最大16 KiB。
- eligible 时必须实际流式计算内容 SHA-256；只有 multipart ETag/size 的任务可成功但 non-eligible。
- 远端 mirror 必须已把对象内容复制到 artifact failure domain；只记录生产 URI 不算备份。

### 11.4 Workspace

- 路径统一为规范化相对路径和 `/` 分隔；绝对路径、`..`、root 外 symlink、解包逃逸 hard fail。
- index 固定记录 file/dir/symlink/hardlink 类型、mtime、mode、uid/gid、大小和 checksum；支持 sparse/hardlink 的能力必须记录。
- xattr/ACL 无法恢复时 warning 且 non-eligible；socket/device/FIFO 默认排除并记录，不能作为普通文件解包。
- socket/device/FIFO存在时固定产生`unsupported-evidence-warning`并使`local_acceptance=false`；在其他技术检查通过时任务按第4.4节以succeeded/non-eligible结束，functional-test可继续。Symlink/hardlink目标、xattr和ACL allowlist由workspace registry逐项定义，未知项不默认放行。
- cluster 从 CSI snapshot 创建只读 PVC 后归档；snapshot 必须继续导出到外部 artifact。
- single-node 必须停止相关 runtime 并在 gate 内完成 staging；超出容量或最大停写时间失败，不静默降级为正式证据。

### 11.5 Deployment resources 和 Secret

- P0 只保存结构、镜像 digest、ConfigMap、Service、Ingress、PVC/snapshot、ServiceAccount/RBAC 等 redacted 清单，不默认 apply。
- cluster-scoped CRD/Longhorn 对象仅登记必要引用和 excluded reason；ClawManager 任务状态不得复用 Longhorn SystemBackup CRD。
- JWT、LDAP、模型、runtime、Team 等非数据库 Secret 按显式 allowlist 进入 encrypted bundle；KEK 和 installation ID 永不进入 bundle。
- Secret registry 逐项冻结 `source identity/key、required、restore_action=stub|disable|restore_external_ref、target identity mapping、max bytes`。P0 不提供 `restore_value`；bundle 中的生产值只用于完整性/灾备可读性验证，drill 永远物化随机 stub、disabled config 或不可重放 external ref。Acceptance 要求 required key 在 capture 前后 UID/resourceVersion 一致；新增或缺失 required key 使 `secret_bundle_failed`，不得由 normalizer 猜测。真实生产值恢复属于 P1 受控生产恢复合同。
- redaction 使用 schema-aware sensitive registry + 默认拒绝未知 Secret 字段，再补 URI userinfo/query 处理；只按字段名包含 `key/token` 的启发式不能作为唯一保护。

## 12. 恢复演练、Preflight 和 Cleanup

### 12.1 恢复演练

固定顺序：commit/envelope/checksum/schema 校验 → 隔离目标校验 → provision → MySQL → object → workspace → Redis → Secret/运行态/控制面归一化 → 切换 SELECT-only → 六类 verifier → 控制面 verifier。

- 默认创建专用 namespace、临时 MySQL、临时 Redis、workspace PVC 和带 drill owner 的 object prefix；不启动完整 Console/API/runtime。
- Job 只挂载恢复专用 Secret、artifact read credential 和 KEK ref；生产外联 Secret 只能在内存中验证，drill 中物化随机 stub 或 disabled config。
- normalizer 明确清除 `instances.access_token`、agent bootstrap/session token、external access token/password、gateway alias、模型/LDAP/Team 外联 Secret，禁用旧 agent/runtime binding。
- normalizer 使用与 schema object registry 同版本的 normalization registry，逐表声明 `preserve|reset|disable|drop` 及 verifier。除上述 Secret/binding 外，outbox、scheduler、materialize/scan job、外发事件、workflow ledger cursor 和其他可重放工作项必须显式登记；新增可执行状态字段未登记时 acceptance drill 失败，禁止依赖手写清单默认放行。
- `system_backup_*`、artifact/mutation lease、maintenance lock/participant 的表结构进入 schema catalog，但其数据行不进入可恢复 MySQL payload；需要保留的历史摘要、event/audit checksum 和 promotion evidence 进入 manifest 引用的独立 redacted control-evidence sidecar，不计作第七个业务 part。Normalizer 必须验证临时 database 中这些控制表为空，不执行逐行“改为 inert”的状态迁移，也不把源控制历史导入当前 drill/controller。
- normalizer 完成后销毁 restore 写凭据并结束 restore Job；verifier 使用独立 Job/ServiceAccount 和只含 SELECT/必要 `information_schema` 权限的新连接。仅在同一进程中切换代码 adapter 不算权限切换；verifier 发生 DDL/DML 或仍可取得 restore credential 时立即失败。

`restore_target_config` 是独立 tagged union，必填 discriminator 为 `type=managed_drill|existing_readonly_preflight`，两种 variant 及所有嵌套对象均 `additionalProperties=false`：

- `managed_drill`：P0 的 `cluster_ref/version` 必须精确等于当前安装 cluster identity，不支持远端 cluster 控制面；必填 `namespace_parent_ref`、隔离 object target ref/version、每类 create/delete credential ref/version 和 `network_policy_profile=strict`。Controller内置status-relay的service identity/CA version来自不可变task config snapshot，不允许调用者覆盖。存储绑定使用嵌套 tagged union：cluster 为 `{type:"csi",storage_class_ref,version}`，single-node 为 `{type:"hostpath",registered_node_id,registered_root_id,version}`。namespace、database、keyspace、prefix 和 root 最终名称只由服务端根据 task ID 派生。
- `existing_readonly_preflight`：必填目标 `cluster_identity`、namespace、MySQL server identity+database ref、Redis instance identity+DB/keyspace ref、object endpoint identity+bucket/prefix ref、workspace volume identity+root、每类 read-only credential ref/version和 `network_policy_profile=readonly_strict`；禁止包含 create/delete credential。

P0 不接受可执行命令、内联 credential、自由 URI或其他 `network_policy_profile`。上述 typed ref、identity canonicalization和 source-overlap 比较算法进入机器合同。

Isolation 使用两道 hard gate。第一道在任务创建和 provision 前检查 planned identity：服务端派生的 namespace/database/keyspace/prefix/root 不属于生产或 reserved 集合，全部 credential scope 不含生产写权限，provider read-only preflight 确认远端 identity 不重叠；失败时同步返回或异步终结为 `isolation_invalid`，且不得创建资源或写目标数据。通过后先写 resource intent，再允许创建空资源。第二道在首个 restore/normalization 写入前检查 observed identity：namespace owner label/annotation、K8s UID、数据库/Redis/object/workspace provider identity 和 reserved marker 必须与 intent 完全匹配；不匹配时不得写数据并保留资源等待安全 cleanup。Drill/restore/normalizer/verifier Job 固定 `automountServiceAccountToken=false`，不得访问源 Kubernetes API；状态统一通过第 7.3 节 relay 上报。单消息最大 64 KiB、每任务 10 QPS；relay 暂时不可用按 dependency backoff，超过 task deadline 为 `deadline_exceeded`。NetworkPolicy 默认拒绝生产 CIDR/service DNS、源 Kubernetes API 和未登记外部 endpoint，只允许 artifact/KMS、status relay 及本次演练资源。`isolation_invalid` 同时作为 failure category 和 eligibility reason，进入机器合同、事件、指标及负向测试。

本安装新建的backup/drill/controller记录只存在于本安装控制数据库；灾备安装可从外部catalog创建独立`catalog_import`资源，但不得导入或伪造源安装task/control行。Control-plane verifier校验控制表行已从业务dump排除、control-evidence sidecar完整且redacted、恢复目标控制表为空；P1若需要导入历史，必须按第12.4节定义独立merge流程，P0不预埋状态转换。

### 12.2 Resource inventory 与 cleanup

- P0 cleanup 权威 `resource_type=namespace|volume_snapshot|mysql_instance|redis_instance|redis_keyspace|object_prefix|workspace_root`。专属 namespace 内的 Deployment/StatefulSet/Job/Service/ConfigMap/ServiceAccount/RBAC/Secret/NetworkPolicy/PVC 只进入有界 diagnostic inventory，由 namespace owner UID 和删除收敛统一管理，不逐项建立第二套 cleanup 状态机。Pod、PV 和 VolumeSnapshotContent 属于 controller/CSI 派生资源，仅记录 observed ref/owner chain；P0 不直接删除 PV/VSC。只有 provider 明确声明资源由本任务直接创建、提供 namespace 外不可变 owner marker及独立 UID/version时，才可在后续合同版本升级为 cleanup authority。未知类型只能保留和告警。
- drill在本安装控制数据库中先为namespace及每个namespace外权威resource以CAS写入`creating` intent（包含resource public ID、provider idempotency key、预期安全名称和位置hash），再逐项创建；创建成功后更新UID/version、owner marker HMAC并CAS为`lifecycle=created`。Namespace内Job/workload/PVC等子资源只允许在namespace intent已created且第二道隔离门准备完成后创建，写有界event/diagnostic inventory而不新增权威resource行。Provider必须按idempotency key查询权威资源创建结果，使controller可在“创建成功、登记未完成”的崩溃窗口接管。
- P0 的 MySQL drill 默认使用任务 namespace 内系统创建的独立 MySQL workload/PVC，其所有权由 namespace/workload/PVC UID 与 inventory 联合证明，不对共享 MySQL server 执行裸 `DROP DATABASE`。外部 provider 只有提供数据库外的不可变 owner tag/version 时才允许自动删除；marker 不能只写在将被恢复覆盖的目标 database。
- cleanup 只处理 inventory 中 `lifecycle=created|delete_failed` 的资源。若 intent 停在 `creating`，接管者必须先按 provider idempotency key 查询：能证明资源不存在则 CAS 为 `lifecycle=absent`；能恢复匹配 UID/version/owner marker 则补登记并 CAS 为 `lifecycle=created`；结果不确定则置 `ownership_unknown` 并告警，不能把它当作“未创建”跳过。缺少合同标记的可选资源不失败。
- `cleanup_policy=delete-on-success|retain-always`。默认 `delete-on-success`：drill 终态 CAS 写入 `succeeded` 时必须同时把 cleanup 从 `not_started` 写为 `pending`，随后由独立 cleanup claim 推进 `pending -> running -> succeeded|partial_failed|failed`；失败和取消保留为 `not_started`。`retain-always` 在任务终态 CAS 同时写 `cleanup_status=retained`。Cleanup 不复活或改写 drill 主状态；但只有`delete-on-success`且cleanup已succeeded的acceptance drill可创建promotion，避免未清理明文资源在cleanup竞态窗口内成为baseline。
- 失败/取消现场以及`retain-always`成功后保留的现场只能由管理员显式执行cleanup；endpoint接受`cleanup_status=not_started|retained|failed|partial_failed`并以新operation驱动到pending。二次drill必须使用新ID和新目标。
- Artifact schema 保留 `_clawmanager_internal/**`，业务源出现该保留路径时 preflight 拒绝。Object/workspace marker 写入此保留空间；Redis 使用随机 control prefix；marker token 只保存专用 HMAC/随机摘要，避免和业务 key 冲突。
- 每个存在的资源分别校验控制库 inventory、namespace label/annotation、K8s UID、object/workspace reserved marker 和 Redis control key；任一信息不一致返回 `cleanup_unsafe_target`。
- 创建外部资源必须使用已持久化的 intent/idempotency key；登记失败即停止后续步骤。Orphan-GC 只处理能够通过 provider 查询恢复 intent、UID/version 和 owner marker 的资源；不能证明所有权时告警并保留，绝不猜测删除。
- cleanup先停止namespace内任务workload并等待派生Pod消失，再按intent删除namespace外Redis/object/MySQL/workspace资源和由本任务显式创建的VolumeSnapshot，最后按UID/owner marker删除专属namespace并等待namespace内资源级联收敛。PV/VolumeSnapshotContent只观察CSI owner chain和回收结果，不由P0直接delete；`delete-on-success`只有在PVC删除且CSI/provider证明承载明文恢复数据的PV已回收、删除或安全重置时才能settled succeeded。`retain-always`只能保持`cleanup_status=retained`，不能作为delete-on-success成功证明或promotion前置。到cleanup deadline仍存在明文残留介质时至少为`partial_failed`（没有任何安全删除成功则failed），对应resource写`cleanup_failure_code=residual_data`、check/operation failure写`cleanup_unsafe_target`，并把引用该drill的evidence health置`degraded/cleanup_residual_data`直至外部处置证明登记成功。空prefix、根路径、默认/生产namespace、裸DB index和无marker目标必须拒绝。
- 清理失败只更新 cleanup status/step result、warning、event 和 audit，不覆盖已经完成的 drill verifier 结论。
- 若 cleanup 失败原因为 UID/version/owner marker 不匹配、`ownership_unknown` 或其他会否定原 resource inventory/isolation evidence 的事实，不回写历史 drill eligibility，但必须立即把引用该 drill 的 active promotion `evidence_health` 派生为 degraded、`backup_recovery_readiness=false` 并告警；纯 provider 暂时删除失败不影响 evidence health。
- 显式 cleanup 必须带 idempotency key，使用独立 cleanup claim 和 row-version CAS；同key重放返回原operation，不同key在已有pending/running cleanup时返回409 `conflict_active_job`及该operation public ID，且不占用新key。前一 cleanup 为 failed/partial_failed 时，管理员可对同一 endpoint 使用新 idempotency key，并传 `retry_of_operation_public_id` 只重跑未成功步骤。资源已不存在时，只有本系统先前保存的provider deletion receipt明确绑定历史UID/version，或第14.2节登记的强一致/版本化absence proof同时绑定resource public ID、location和历史UID/version，才可记为幂等成功；普通404或只能证明“当前名称不存在”的响应返回`cleanup_unsafe_target`并进入ownership resolution。
- Cleanup HMAC key/version丢失时，ownership-resolution可由具有`system_backup.destructive`权限且完成近期强认证的管理员提交provider外部不可变证明。`ownership_proof_type=kubernetes_uid|csi_snapshot_handle|s3_versioned_marker|mysql_provider_resource_id|redis_provider_resource_id|workspace_volume_uid`，`observed_state=absent|present_unsealed|present_sealed`；issuer必须来自配置中的trusted provider registry，证明绑定resource public ID、location、UID/version、当前observed state、issuer identity/ref/hash、issued_at和expires_at，不接受自由`manual_attestor`。Backup staging只接受absent→`absent`、present_unsealed→`ready`、present_sealed→`sealed`；restore resource只接受absent→`absent`或present_unsealed→`created`，对restore提交present_sealed为400 `validation_failed`。后续新的cleanup operation可使用未过期proof替代HMAC校验，但仍须重验location/UID/version，且两类资源都不能直接标为deleted。

### 12.3 生产 preflight/diff

- P0 只读，不注册生产 restore execute API。
- Preflight只使用全局create路由，source为`source_artifact_type=backup|catalog_import` tagged union。`preflight_mode=production_readonly`时，本地backup要求终态、`artifact_usable=true`且`acceptance_ready=true`，catalog import要求full verify完成、`import_usable=true`并以不存在性能力组确认tombstone不存在；`functional_test`只要求当前可读，但报告固定不得用于promotion或未来execute。不提供语义重复的资源下便捷create路由。
- P0只读权限矩阵固定为：MySQL `SELECT`及读取所需`information_schema`视图；Redis连接握手`AUTH|HELLO`、standalone可选`SELECT`和数据命令`SCAN|TYPE|PTTL|DUMP`，禁止写/admin命令；S3兼容API只允许目标prefix的List/Head/Get及读取固定version；workspace只读挂载；K8s只允许schema registry登记kind/namespace上的get/list。TLS握手和provider原生身份交换不算数据权限；增加任何数据命令、verb或scope必须升级权限合同并补负向测试。
- 创建请求只同步检查本地 schema、引用格式、静态 allowlist、controller readiness 和未过期的 capability cache；这些确定性前置缺失返回 503 `not_ready` 且不创建任务。任何需要连接目标或挂载资源才能确认的权限/能力检查都在任务创建后执行；目标ACL明确拒绝使任务`failed/permission_denied`，读取超时或远端能力检查失败使任务`failed/preflight_failed`，不能因handler与Job的实现差异降级成skipped/pass。
- 所有 SELECT、SCAN/DUMP、List/Head/Get 和 workspace 遍历必须受 immutable config snapshot 中的 query timeout、provider QPS、扫描 bytes/items 和总 deadline 约束；查询使用低优先级/只读会话并在取消或预算耗尽时主动关闭连接。预算耗尽固定为 `capacity_exceeded`；ACL明确拒绝固定为`permission_denied`；网络超时、限流或远端能力检查无法完成才使用`preflight_failed`。
- diff 输出六类 count/checksum/摘要、缺失 Secret/ref、对象/workspace/Redis 差异和高风险覆盖项，不输出完整敏感行。
- `restore_target_config_hash` 和 `diff_hash` 使用 JCS；hash 必须包含 target deployment profile、typed refs 的 resource/key version、目标 schema hash 和 capability snapshot。GET detail 只做有上限的 freshness 检查，根据 source artifact usability/manifest/acceptance checksum、当前 ref version、目标 schema hash、capability snapshot expiry 和 evidence availability 标记 `report_valid=true|false` 及闭集 reason；不在读取时重跑完整 diff。任一输入漂移或证据不可用后旧报告失效，执行方必须新建 preflight。

### 12.4 P1 生产恢复硬前置

活动 `system_restore_runs` 和 fencing journal 不能存放在将被覆盖的业务数据库。P1 enable 前必须提供独立 control database/journal，定义 control-evidence sidecar 的选择性导入、ID 冲突、来源标记和当前 run 保留策略；不得从业务 dump 恢复原始活动控制行。未满足时 execute 始终返回 unavailable。

## 13. Prune 和 artifact 健康

- `retention_seconds`使用第6.5节统一默认值；非时间配置`minimum_recovery_points`为min/default 1、max 100。Failure-domain registry每个稳定ID还包含`matrix_key`和`recovery_required=true|false`；minimum/shortage只对当前required域计算，故required域即使零恢复点也必须输出shortage，不能因查询结果没有group而消失。`alert_profile=production`或部署`SYSTEM_BACKUP_REQUIRED=true`时，当前matrix至少一域必须required，且其目标必须能判为`dr-ready-external`；否则config保存返回422 `backup_target_risk_rejected`。改为非required经过安全降配后，历史artifact仅继续受retention、manual/promotion hold保护，不再永久保留N份；active promotion对其引用artifact的derived hold仍独立生效。P0 对每个 required `(origin_installation_id,matrix_key,target_failure_domain_id)` 从历史终态 `acceptance_eligible=true AND artifact_state=committed` 的 artifact 中按committed time/public ID选最新 N 份组成 protected set，选择不依赖当前`artifact_usable`、credential/KMS/provider或health freshness；因此暂时不可读、unknown或stale的历史合格恢复点仍受保护。`corrupt|deleting|delete_failed|deleted`不计入保底，分组少于N时把该组所有仍committed且历史eligible的artifact全部保护并输出shortage。Functional-only、corrupt、non-eligible及protected set之外的过期artifact才可按其余规则删除。不得用同profile但不同orchestrator的恢复点互相补足。Cutoff固定为数据库时间`artifact_committed_at < now-retention_seconds`，等于边界不删除。所有可提交artifact的target config都必须解析出非空、来自append-only registry的稳定failure-domain ID，`same-cluster-copy`也不例外；该ID写backup索引。
- `system_backups` 增加 `manual_hold` 和可选 reason/actor/time；当前 promotion baseline 的引用形成独立的 derived hold。管理员手动保留或被任一活动 promotion 引用的 artifact 永不进入 prune candidates。Manual hold 通过 API 显式设置/解除；promotion hold 只能通过创建新 baseline 或撤销 promotion 记录改变，两者可同时存在、互不覆盖。
- Manual hold 只能修改源 backup 已终态且 artifact 为 `committed|corrupt|delete_failed` 的记录；`deleting|deleted` 返回 `state_conflict`。解除 hold 后若该 failure-domain 分组将没有配置要求的 recovery point，必须要求 `system_backup.destructive`、近期强认证和非空 reason，并在响应中明确不会立即删除、仅允许后续独立 prune dry-run 重新评估。
- dry-run 候选仅包含源 backup 已终态、artifact state 为 `committed|corrupt`、超过 retention、没有活动 publish/finalize Job、无 active drill/preflight/artifact-verify lease、无 manual/promotion hold 且不是上述保底恢复点的 artifact。Planning和execute必须在同一事务算法中重算每个分组的protected set；任何health/dependency unknown不得改变历史eligible保护资格。`corrupt`永远不计作保底恢复点，但删除前仍须满足hold/lease规则。
- candidate hash 绑定排序后的 candidate public ID、backup terminal status/finished_at、artifact state、immutable URI/version、manifest/index/marker/acceptance checksum（不存在时显式 null）、bytes、hold/lease 摘要、prune-item plan hash、config version 和`prune_guard_version`；禁止使用会被health/last-checked刷新触发的通用row version。Execute仍须在锁定artifact/lease/active-promotion行的同一事务中重算全部guard输入并CAS递增guard。
- Dry-run创建响应和GET detail只返回run/candidate摘要。进入`dry_run_created`后，管理员审阅分页item，再调用confirmation endpoint；请求必须带idempotency key、`expected_prune_run_row_version`、`system_backup.destructive`和近期强认证。API在单一数据库事务中重查candidate未过期、写audit intent/result、消费strong-auth nonce并生成随机128-bit `confirmation_id`，将其与actor、candidate hash、cutoff、config version和`expires_at=min(now+confirmation_ttl,candidate_expires_at)`绑定，返回HTTP 200。该ID不是签名secret，不需要response encryption；同key重放返回相同ID和状态。首次execute使用独立idempotency key，在同一事务中校验并消费confirmation、重查完整集合、恢复点下限和lease，再把候选CAS为`deleting`。任一漂移仍提交failed operation和consumed事实，但不修改artifact，返回`confirmation_invalid`；必须创建新dry-run。Candidate过期后run转`expired`。
- Prune item转换固定为`planned -> deleting`、`blocked_by_delete -> planned`、`deleting -> deleted|delete_failed`、`delete_failed -> deleting`；另仅在所属execute/retry operation deadline到达时允许`planned -> delete_failed/item_failure_code=deadline_exceeded`。Blocked/planned/deleting/deleted必须`item_failure_code=none`，delete_failed必须非none，重试进入deleting时在同一CAS清回none。每次`deleting`同时写claim、row version和operation ID；controller/operation claim接管后对同一immutable version执行权威Stat/List：已不存在则CAS为deleted，仍存在且deadline未到则继续同一删除，结果unknown则保持deleting并backoff。Operation deadline到达时，所有仍为planned或deleting的本operation item必须CAS为`delete_failed/item_failure_code=deadline_exceeded`，不得留下无owner的活动状态；随后按结果聚合run。
- 某 artifact 的全部对象/文件 prune item 删除并验证不存在后，controller执行单一事务：把artifact CAS为`deleted/artifact_unusable_reason=deleted`；若存在registration，同时冻结完整signed`artifact_deleted` bytes、创建对应external-action，并把`catalog_tombstone` item从`blocked_by_delete`转为`planned`。任一写失败则整个事务回滚，接管者可由对象item终态重做，不允许出现artifact已deleted但没有应有tombstone action的窗口。任一对象/文件 item 失败则该 item 置 `delete_failed`、artifact 置 `delete_failed/artifact_usable=false/artifact_unusable_reason=delete_failed`。聚合真值表固定为：任何不可重试conflict使run为`failed`；存在至少一个已删除对象且仍有任一对象或catalog item失败为`partial_failed`；全部对象item均失败且无成功删除为`failed/artifact_delete_failed`；对象全部成功但任一catalog item失败仍为`partial_failed/catalog_tombstone_failed`；全部必需item成功才为`succeeded`。全过程保留不可变`acceptance_eligible`、数据库记录和逐item结果。管理员通过`POST .../prune-runs/:id/retry`使用新idempotency key、`system_backup.destructive`和新的近期强认证proof创建关联operation；已消费confirmation不重复签发，但strong-auth nonce每次retry必须新建并消费。Retry处理原计划内全部未成功item：先接管遗留deleting，随后把`delete_failed` CAS回`deleting`；已在operation超时收敛为delete_failed的原planned item因此也可重跑。对象item重试时才把对应artifact从`delete_failed` CAS回`deleting`，catalog item重试不得改写已为deleted的artifact。对execute/retry复用旧key只返回该operation已保存响应。
- 每次prune retry在处理artifact首个失败item前，必须在同一事务中重新检查该artifact的manual/promotion hold、活动lease、immutable identity和row version；新增hold或lease返回`state_conflict`并保留原item，不得因计划已冻结而绕过。已成功删除的item不回滚，其余未成功item仍只能沿原计划重试。
- Recovery catalog 和外置evidence ref不作为普通artifact prefix item猜测删除。仅对存在registration的artifact，对象删除成功后controller才通过原计划的`catalog_tombstone` item append已冻结的签名`artifact_deleted` bytes，绑定原`artifact_registered` ID/hash、locator/checksum、prune run/candidate hash、首次deleted时间和首次execute actor；retry actor/operation只进入audit。该record按第9.3节在P0不自动删除，不能套用control metadata retention。Catalog暂时写失败时该item为`delete_failed`、run为`partial_failed/catalog_tombstone_failed`、artifact保持`deleted`且recovery readiness degraded；retry复用同一external-action row和payload、递增dispatch generation，只补该catalog item，不能重删对象。相同record key/相同canonical bytes为成功；不同bytes视为篡改或identity碰撞，run置不可重试`failed/catalog_conflict`并立即critical，必须按catalog provider版本历史runbook恢复正确record，系统不得覆盖或自动追加“修正”记录。
- 超时未提交 prefix 使用独立 orphan-GC。确认 task/attempt/Job/heartbeat 均超过安全窗口且 `_COMMITTED` 缺失后，GC 先把 artifact 从 `staging` CAS 为 `deleting`，再核对 prefix identity/owner marker 与数据库 intent；匹配才执行删除并置 `deleted`，不匹配或查询不确定则不删除、置 `delete_failed/artifact_unusable_reason=delete_failed` 并告警。它不与 retention 混用，任何路径都不能让失败任务永久停在 `staging`。
- artifact health reconcile 和显式 artifact verify 对本地 backup 必须在源 backup 终态后、对 catalog import 必须在 import operation succeeded 后取得 verify lease。后台轻量 reconcile 检查 immutable version、marker/manifest/index、read credential/CA/KMS 及 evidence；读取依赖失败可把本地 `artifact_usable` 置 false。Acceptance 签名/catalog 问题只更新 `acceptance_ready` 所依赖的权威health记录，不关闭 functional readability。Catalog import 必须额外验证 acceptance/registration，并以强一致Stat或版本化不存在证明检查tombstone；普通404只能得到`verification_inconclusive`。有效tombstone永久置`catalog_tombstoned`。Full verify读取全部immutable object version、校验ciphertext、unwrap各part DEK并认证所有GCM chunk；acceptance用途再验证`_ACCEPTANCE`和registration。结构/checksum错误只有在两个不同task/Job UID的full verify上、间隔至少一个provider consistency window、针对相同immutable version得到同一失败码和checksum证据时才可判corrupt；或由version listing的版本化证明直接确认必选对象不存在。单次404、超时、限流、认证/KMS/catalog故障均为暂时或不确定。只有`artifact_state=committed`且unusable reason属于provider/credential/KEK/evidence/verification等暂时原因的本地artifact，才可在相同immutable version完整通过full verify后恢复`artifact_usable=true/reason=none`；已经CAS为`corrupt|deleting|delete_failed|deleted`的artifact不得恢复usable或回到committed。Catalog import恢复true还要求全部签名/catalog依赖健康。两类检查均不改写历史eligibility。
- `control_metadata_retention_seconds`默认一年并按第6.5节统一承载控制记录保留。Controller内部metadata-GC不是backup schedule或artifact自动prune：它只处理已终态、artifact已deleted或从未committed、无hold/lease/promotion/import/retry引用、control metadata保留期已过且audit result已持久化的记录；必须先以同事务写入或确认`system_backup_compact_tombstones`中的原幂等tuple、terminal摘要及被删明细canonical rolling hash，再删除大体积response、Job observation、event、check和attempt。Task/operation主行、strong-auth消费记录、audit和promotion按各自受保护引用至少保留至control metadata cutoff；standard tombstone从自身GC时间再保留一个control metadata周期，destructive tombstone永久保留。二阶段只删除到期standard tombstone，且对应audit/引用不得仍需要原响应。本地catalog scan/record只可在不属于当前catalog ref最新一次succeeded snapshot、未被import/proof/audit引用、对应receipt已过control metadata保留期且存在更新的succeeded snapshot时删除；当前snapshot、全部被引用行及其receipt永久禁止由metadata-GC删除，下一次完整扫描可从外部catalog重新物化其他历史行。除job-log payload的专用规则外，仍受保护evidence不得删除。外置evidence对象只有在registry无任何活动owner/报告/promotion/health引用、`protected_until`及对应retention均已过、精确immutable owner/version可验证时才由独立evidence-GC把`ready|delete_failed` CAS为deleting；job-log使用`available_until`，其他evidence使用`evidence_retention_seconds`。远端删除确认后才能置deleted并移除大字段/typed ref，registry最小envelope仍按control retention保留。pending/write_unknown先按确定性key强Stat收敛；write_failed保留到owner及其重试引用结束后再按相同key检查并清理。未知或失败保留并告警，禁止绕过状态机直接删row。GC逐批有上限、使用row-version CAS并输出容量、最老可清理年龄、last-success及失败指标。
- Inline evidence使用相同owner/reference/protected-until/retention门禁，由evidence-GC以单事务执行`inline -> deleting -> deleted`并清除密文payload；不调用provider。外置`write_failed`在owner及重试引用结束、按确定性key证明远端不存在或完成匹配orphan删除后才可`write_failed -> deleting`。两类deleted行都只保留最小envelope、content hash/size、删除时间和rolling-hash引用至control metadata cutoff。

### 14.2 API 规则

- Admin 路由统一接入 `Auth`、`SetUserInfo`、`NewAdminAuth`。
- Admin 身份之上还必须检查闭集权限：`system_backup.read` 用于查询，`system_backup.operate` 用于 backup/drill/preflight/verify/cancel/cleanup，`system_backup.destructive` 用于 prune confirmation/execute/retry、provider proof registration、finalization/ownership resolution、hold 解除和 promotion revoke，`system_backup.configure` 用于普通 config 与 promotion create；安全边界配置另需同时具备 `system_backup.security_configure`，避免 config admin 自行赋予 destructive 权限。内置 role 映射固定为：viewer=`read`，operator=`read+operate`，config_admin=`read+configure`，security_admin=全部五项权限；内置 role 不可经 API 改名或改权限集合，role binding 只能引用这四个值。只有离线 bootstrap 可首次授予 `security_configure`；任何 API 请求都不能给调用者自身新增 security/destructive 权限，也不能使 security_admin 绑定集合为空。系统必须提供不依赖业务数据库当前role binding的离线break-glass runbook，用安装bootstrap identity恢复至少两名security admin，并强制写外部审计；API不得提供break-glass入口。Prune confirmation/execute/retry、provider proof registration、finalization/ownership resolution 和解除最后恢复点 hold 要求近期强认证。`strong_auth_proof` 绑定 issuer、audience、subject、session、auth time、expiry、method、nonce、endpoint/request hash/idempotency key 并一次性登记；`auth_time` 距数据库当前时间不得超过 `strong_auth_max_age_seconds`，proof expiry 还必须覆盖当前请求事务，允许时钟偏差固定为机器合同中的`strong_auth_clock_skew_seconds`且默认30秒。`method=webauthn|totp|oidc_mfa`，密码单因素不合格，`oidc_mfa` 还必须携带命中 trusted issuer registry 的 ACR/AMR 值。
- Catalog scan/import需要`system_backup.operate`和idempotency key。Scan只允许当前config为`provider_snapshot|inventory_manifest`；API事务只创建pending `catalog_scan` operation/scan行并绑定当前catalog ref version，不在请求线程调用provider。Controller首次claim后才取得新的provider snapshot token或解析已冻结inventory checkpoint，在同一CAS写入identity/expiry并验证其覆盖scan deadline后进入running；list/detail只返回有界scan摘要，catalog-record list按`validation_state|deletion_state|record_type|origin_matrix|seen_time`过滤并使用opaque cursor。Import请求使用`lookup_mode=discovered|known_record`：前者只接受`record_type=artifact_registered AND validation_state=valid AND deletion_state=active`的本地catalog-record `scr_` public ID及expected canonical hash，由服务端取得其外部`sbr_` ID；后者只在config为`known_record_only`或当前完整发现能力不可用时，直接提交已从独立灾备runbook取得的registration ID/hash。API创建`catalog_import` operation，controller从配置catalog读取该精确record，对`tombstones/<registration_id>.json`取得强一致Stat或版本化不存在证明，验签后创建immutable import resource。普通404使operation保持pending/backoff并最终按deadline失败为`catalog_unavailable`，不能创建可用import。请求不得携带自由URI、正文或credential；相同catalog ref version+record hash最多一个import。初始固定`import_usable=false/verification_pending`；有效tombstone固定为永久`catalog_tombstoned`，可证明不存在且full verify成功后才可置true并创建acceptance drill或production-readonly preflight。
- `disaster_bootstrap_registry` 以 catalog 中的 artifact credential identity、CA identity、KEK provider/key ID、acceptance-record signing public-key ID和catalog-record signing public-key ID为相互独立的不可变键，映射到本安装预置的typed credential/CA/KMS auth/public-key ref及version；API只返回identity、状态和redacted version。Catalog import必须逐项精确解析：catalog root/read ref不可达映射`catalog_unavailable`，artifact read credential或CA缺失映射`artifact_unavailable`，KEK auth/key version缺失映射`encryption_key_unavailable`，任一签名public key缺失映射`signing_key_unavailable`，验签失败映射`signature_invalid`；identity/version与record字段冲突才映射`catalog_conflict`。禁止用当前默认credential或一个purpose的key替代历史身份。
- Provider proof registration要求`system_backup.destructive`、近期强认证和idempotency key；请求固定为`target_type=external_action|backup_staging|restore_resource`、匹配public ID、`proof_type=provider_presence|provider_absence|ownership`及最大8 KiB的JWS/COSE/provider-signed bytes，不接受URI或人工文字。合法组合固定为external-action→`provider_presence|provider_absence`，backup-staging/restore-resource→`ownership`；ownership payload中backup-staging只接受`observed_state=absent|present_unsealed|present_sealed`，restore-resource只接受`absent|present_unsealed`，其他target/proof/state组合在登记前返回400 `validation_failed`。三类proof分别登记为`provider_presence_proof|provider_absence_proof|ownership_proof` evidence。Proof payload schema固定只含public ID、provider identity、location/action-key hash、UID/version/checksum/length、observed state及时间，不含原始URI、credential或provider自由错误文本，redaction classification固定为internal、`encryption=none`。因此8 KiB上限保证该同步operation只做单一数据库事务，不引入KMS或未记账外置对象写入。API在事务中校验trusted provider issuer、签名、audience、target/location/action-key hash、UID/version/checksum、issued/expiry time和expected target row version；`issued_at`不得早于数据库当前时间减`provider_proof_max_age_seconds`，`expires_at`不得晚于`issued_at+provider_proof_max_age_seconds`且必须覆盖当前事务。成功后登记不可变inline `sev_`并返回201；无效schema/issuer/expiry为400 `validation_failed`，密码学签名失败为409 `signature_invalid`，已验签payload与target/checksum不匹配为409 `checksum_mismatch`，target row漂移为409 `version_conflict`。登记证明本身不改变resource/action结论。
- Finalization resolution只接受`finalization_unknown` backup、唯一unresolved external-action ID、expected row version和由上一接口登记、owner匹配且未过期的provider proof evidence ID；controller必须从数据库重新读取该不可变evidence并验签，把proof中的action-key/location hash、logical action hash、object/catalog version、content length与checksum同本地完整action逐项核对，不要求live provider同时可达。Presence proof确认provider已持久化的bytes与action完全相同后按第4.1节判断：仅最后一个必需外部action允许成功收敛，存在未发送后续action则只做安全收尾并`failed/deadline_exceeded`；absence proof只有同时满足不存在性能力组且超过consistency window才能按action失败；仅含普通404的材料不能注册为有效absence proof。冲突为`artifact_conflict|catalog_conflict`，验签失败为`signature_invalid`。Staging ownership resolution只接受已登记的`sbs_` resource和同owner `sev_` proof，并严格使用第4.2节staging专属转换`ownership_unknown -> absent|ready|sealed`；restore resource使用`ownership_unknown -> absent|created`，两者均禁止直达deleted。cleanup-staging只能在ownership已解析后新建operation。Resolution mutation均不可用自由URI、人工文本或“强制成功/删除”布尔值。
- Manual hold设为true需要`system_backup.operate`；设为false一律需要`system_backup.destructive`，若涉及最后恢复点再叠加近期强认证。权限判断使用服务端读取的当前值和expected row version，客户端不能通过省略旧值改变分支。
- Config PUT若改变role binding、strong-auth issuer/nonce-HMAC key、trusted provider-proof issuer/public key、signing key、artifact delete、evidence read/write/delete、catalog append credential或disaster bootstrap mapping，除`system_backup.configure+system_backup.security_configure`外还必须要求近期强认证；调用者不得在同一请求中扩大自身权限。降低`retention_seconds|evidence_retention_seconds|control_metadata_retention_seconds|minimum_recovery_points`、把failure-domain从required改为非required、把`alert_profile`从production改为development，或扩大任何自动删除/告警抑制能力，必须额外具备`system_backup.destructive`、近期强认证和请求级非空`change_reason`；该reason只进入audit/config-version metadata，不进入生效配置。服务端在同一事务中按新旧值比较，不能信任客户端声明“非安全变更”。增加保护或只调整不扩大删除面的阈值不额外要求。安全ref轮换必须先验证新版本并保留旧引用，再CAS为新的append-only config version；回滚同样产生新版本并按新旧有效值执行相同降配检查，不能借rollback绕过。
- task create（包括artifact verify）、config PUT/rollback、catalog scan/import、cancel、显式cleanup、provider proof registration、finalization/ownership resolution、manual-hold update、promotion create/revoke、prune dry-run/confirmation/execute/retry必须带`idempotency_key`。Task create、catalog scan/import、prune dry-run和confirmation由各自task/resource或专用operation记录承载幂等，其余mutation由operations承载。Handler在认证/授权后先查询actor scope/endpoint/key，再决定是否校验或消费strong-auth nonce：同key/同hash直接返回已保存响应，不要求新proof也不重复消费nonce；同key/异hash先返回409 `idempotency_conflict`；只有不存在幂等记录的新请求才校验proof，并把nonce消费、目标mutation和audit intent置于同一事务。已消费nonce配新key必定返回401 `strong_auth_replayed`。Config PUT/rollback、provider proof registration、manual hold、finalization/ownership resolution、promotion create/revoke和confirmation分别携带对应expected version/row/public ID；漂移返回`version_conflict`。
- Prune confirmation是同步纯数据库mutation：事务锁定run、复核candidate hash/expiry与strong-auth、写audit intent/result、登记nonce并生成actor-bound `confirmation_id`。同key重放返回相同ID；消费或过期后仍返回ID及状态但不能再次execute。该ID通过普通受认证TLS JSON响应返回，API和controller均不需要prune signing key或专用响应加密key。
- `public_id`固定使用资源前缀加128-bit随机UUID：backup `sbk_`、catalog import `sci_`、catalog scan `scs_`、本地catalog record `scr_`、drill `sdr_`、preflight `spf_`、artifact verify `sav_`、prune run `spr_`、prune item `spi_`、operation `sop_`、external action `sxa_`、staging resource `sbs_`、restore resource `srr_`、evidence `sev_`、promotion `spm_`；外部registration ID使用第9.3节确定生成的`sbr_`，不伪装随机UUID。所有`:id`只接受与路由资源类型匹配的public ID，不接受数据库自增ID。`matrix_key`路由参数只接受第4.3节闭集并由当前安装复核。`idempotency_key`为16..128个ASCII `[A-Za-z0-9._:-]`；request ID为1..128个同字符集ASCII，cursor最大4096字节，failure message最大2048字节，actor提交的reason/note最大512 UTF-8字节且必须redaction，单页默认50/最大500。超限统一在handler层`validation_failed`，不能把未限长值写入DB、log或K8s label。
- 配置 PUT/rollback 均带当前`expected_version`，漂移返回409 `version_conflict`。依赖未就绪返回503 `not_ready`；认证401、授权403、缺失404、其他状态冲突按第4.4节返回明确409 code。
- backup、drill、preflight、artifact verify、prune 和 operation 使用各自 detail DTO；前四类任务只共享基础任务字段，不向 drill/preflight/verify 填充无意义 artifact owner 字段。
- list/events/logs 使用绑定资源类型、排序键、过滤条件、方向和 limit 的 opaque cursor；logs 单页最多 1000 条且编码后不超过 1 MiB，先达到任一上限即返回 next cursor。
- List 默认按 `(created_at DESC,public_id DESC)`，events/logs按 `(created_at ASC,id ASC)`；允许过滤字段只包括机器合同登记的status/task purpose/preflight mode/verification scope/profile/runner/failure category/created time，未知filter或cursor中资源类型、方向、limit、filter hash不匹配均返回 `validation_failed`。只使用task type/purpose/mode/scope/profile/runner/created time等不可变字段时，首个响应把数据库 `created_at` cutoff和最后排序键写入cursor，以keyset pagination保证不受新记录影响。包含status/failure category等可变字段时明确返回 `consistency=eventual`，cursor只防止排序键重复，不承诺跨页快照；Console在刷新时从第一页重新查询。
- events是持久化redacted结构化证据。Job原始stdout/stderr永不持久化：JobObserver按有界chunk读取后逐行redaction，失败行丢弃并写诊断event；通过的内容写`job_log_chunk` evidence及`system_backup_log_chunks`索引，只有`ingest_status=ready`可由logs API返回。Job-log evidence是诊断数据，schema禁止check/report/promotion/dependency-health引用。每chunk未压缩内容最大1 MiB、最多1000行，日志总量达到task snapshot中的bytes/lines上限后停止摄取并写`log_truncated`诊断；`available_until=chunk_created_at+logs_retention_seconds`。GC按available-until删除payload，索引/最小evidence envelope保留至control metadata cutoff；过期或所有chunk均已GC返回`logs_expired`，Console停止轮询并引导查看events。
- K8s label 只使用经过长度/字符集规范化的内部 ID；用户提供的 display name、endpoint、idempotency key 和错误消息不得直接进入 label/name。
- 新错误 envelope 为 `{code,message,details,request_id}`，仅用于系统备份模块；details、runner stderr 和外部工具消息必须先 redaction。
- bounded JSON 的上限按 JCS/UTF-8 编码后计算：config snapshot 256 KiB、单 event details 64 KiB、单 check expected+actual 合计 128 KiB、detail 内 verifier summary 256 KiB、diff report的detail摘要256 KiB、单 resource inventory row details 64 KiB、inventory summary 256 KiB、任何evidence inline payload/envelope bytes统一8 KiB、provider-proof registration完整request 16 KiB（其中signed proof bytes最大8 KiB）、external-action canonical payload 256 KiB。完整diff/verifier/log报告超过8 KiB一律作为外置evidence，detail只返回摘要和`sev_`引用，不存在1 MiB的第二套inline规则。超过inline上限的任务生成证据必须由Job先落入任务专属加密staging并报告content checksum/size，controller按classification应用下一段的固定encryption framing，创建`storage_state=pending` intent；外置key固定为`<evidence-root>/<origin_installation_id>/<owner_type>/<owner_public_id>/<sev_public_id>/<content_sha256>.bin`。事务同时保存content/object checksum/size、chunk rows和key后，才签发仅允许该key/object checksum/content-length的conditional-create grant；成功精确Stat后置ready，响应未知置write_unknown并由同一row判等接管，冲突置write_failed并使任务`failed/checksum_mismatch`，其他确定写失败置write_failed并使任务`failed/evidence_incomplete`。调用者不能提交外置proof或指定目标URI。纯诊断details可截断并写`truncated=true + original_size + content_hash`。非job-log evidence retention不得短于artifact retention，活动promotion引用的evidence不得删除；job-log按上一条独立到期且禁止成为活动引用。`GET .../system-backup-evidence/:id`只接受`storage_state=inline|ready`的已登记`sev_` ID，由服务端解析typed ref并代理精确immutable version，禁止redirect到调用者可修改的URI；pending/write_unknown/write_failed返回409 `state_conflict`，deleting/delete_failed返回503 `artifact_unavailable`，deleted返回404。读取授权按classification固定为public/internal=`system_backup.read`、confidential=`read+operate`、sensitive=`read+security_configure`，并始终叠加owner资源可见性；confidential/sensitive在发送body前写audit intent，结束后写result。每响应最大8 MiB，大对象要求标准单Range读取并返回ETag=content checksum及Content-Range，不支持或多Range返回416 `range_not_satisfiable`。所有响应固定`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`和安全`Content-Disposition`，不得把外部对象URI写入header。服务端必须复核content/object checksum/size、envelope identity和redaction classification；不匹配返回409 `checksum_mismatch`，对象读取不可用返回503 `artifact_unavailable`，evidence KEK不可用返回503 `encryption_key_unavailable`，并使report/promotion health degraded。不得把无界JSON写入数据库。
- Evidence统一按classification加密：public/internal可用`encryption=none`，confidential/sensitive必须`envelope_v1`并使用独立evidence KEK封装随机DEK；inline evidence使用单个AES-GCM frame，数据库只存payload明文的content checksum/size和frame密文。外置evidence按1 MiB plaintext chunk（最后一块可短）独立framing，每chunk以evidence/owner identity、index、content checksum为AAD。逐chunk plaintext SHA-256、ciphertext SHA-256、frame位置和nonce/tag写`system_backup_evidence_chunks`并计算JCS list root；evidence row同时绑定content/object checksum、chunk count及root。Range按plaintext chunk边界向外读取对应object frames，先验证ciphertext hash、再GCM认证并验证plaintext hash，最后只返回请求区间；任何失败在发送响应body前返回409 `checksum_mismatch`。小于等于8 MiB的非Range响应先完整验证再发送；更大对象必须由客户端分页Range读取，不允许未验证的无限流式代理。超过1 GiB的content在生成端即`capacity_exceeded`，不得拆成未登记的多个URI规避上限。
- 创建异步task或operation成功统一返回HTTP 202、detail和`Location`；幂等命中返回首次HTTP metadata。Cancel/cleanup/hold/verify/catalog scan/import/promotion/prune同key不得产生第二动作。只有cleanup可凭resource lifecycle和`retry_of_operation_public_id`重跑未成功资源；prune只能走专用retry；catalog scan仅按第6.2节在同一未终结operation内续扫，终结后必须新建；其他失败operation必须按各自API重新创建完整操作，不能声称通用step resume。Task retry使用原create endpoint、新key和`retry_of_public_id`，由服务端复制原业务请求DTO但固定使用请求时的当前active config生成新的`config_version/config_snapshot`并重新执行全部admission；P0不提供复用旧config的选项。新config不再接受原请求时同步拒绝且不创建task，旧task及其snapshot不变。
- 同步成功状态固定：config PUT/rollback和manual-hold update返回200及新version/detail，provider-proof registration与promotion create返回201及`Location`，promotion revoke和prune confirmation返回200；它们在返回前必须提交目标mutation、terminal operation/幂等响应和audit result，不能先返回再补账。其余会运行controller/provider步骤的create/mutation均按上一条返回202。DELETE路由在P0不存在，不使用含糊的204。
- config GET/overview/detail只返回typed ref和redacted snapshot。PUT是全量替换并写新的append-only config version，先做allowlist、SSRF、TLS、单位/范围/跨字段关系和capability检查；rollback请求只含`rollback_from_version`、当前`expected_version`、idempotency key及适用的strong-auth/change reason，服务端读取历史redacted config、重新解析全部typed refs并执行与PUT完全相同的当前环境校验，再复制成新的单调version，绝不直接激活旧row。两条写路径都以同步`config_update` operation承载幂等结果。仍被artifact、catalog scan/record/import、registered proof或active promotion引用的failure-domain ID、credential/CA/KEK/evidence/signing/catalog/attestation/provider-proof issuer key ref version只能标记inactive，不能删除或改写。P0不实现registry/secret material自动GC；清理由离线审计runbook处理，identity tombstone永久保留且ID不可复用。`expected_version`成功后单调递增，历史版本可查询但不含secret data。
- disaster bootstrap mapping同样只允许inactive，不做P0自动GC；外部catalog可能包含尚未import的历史identity，因此自动证明“无引用”留到P1。
- `SYSTEM_BACKUP_ENABLED`是部署级new-work kill switch，默认false；数据库config `enabled`默认false，唯一有效公式为`effective_enabled = env_enabled AND config.enabled`。官方production模板在P0 GA时另设`SYSTEM_BACKUP_REQUIRED=true`；`backup_monitoring_armed = SYSTEM_BACKUP_REQUIRED OR system_backup_installation_state.first_enabled_at IS NOT NULL`。Controller在首次观察到effective true时只对installation-state行CAS一次`first_enabled_at`，API、config PUT和rollback均不得复制、清空或重新计时。关闭时拒绝创建backup/drill/preflight、promotion、artifact verify、prune dry-run/execute/retry；pending任务不再启动外部动作并标记`kill_switch`，但到达deadline仍可纯数据库终结。已开始任务继续安全终结。为避免kill switch同时破坏灾备发现和安全处置，catalog scan/import、GET、config、cancel、cleanup、finalization/ownership resolution、provider proof registration、hold、promotion revoke、lease recovery、orphan scan和后台health/catalog/evidence reconcile是明确例外并继续可用；scan/import只读外部catalog/artifact且不能创建backup、promotion或生产写。后台检查必须按真实观测同时允许健康变好或变坏，kill switch不得篡改健康事实。Kill switch不等于告警silence：monitoring armed后effective false仍按第15节独立告警。
- `effective_enabled` 从 false 恢复为 true 后，controller 以 row-version CAS 将仍为 pending 且 `pending_reason=kill_switch` 的任务改为 `global_capture_queue`（backup）或 `none`（其他 task），保留原 `created_at` 和幂等身份；超过当前 queue/capability 限制的任务继续 pending，不因开关切换创建新任务或重置 deadline。

### 14.3 Console

独立入口 `/admin/backups` 展示 overview、配置、backup、manifest、drill、preflight/diff 和 prune。Docker Compose/bare-metal/external datasource 仅展示 P1 提示，不显示 agent 配置/token 操作。

轮询默认5秒，连续5次无变化后退避到15秒；服务端返回`Retry-After`时优先采用且加入抖动。Backup/preflight/artifact verify在任务终态后停止detail轮询；drill在任务终态且cleanup settled时停止，cleanup pending/running时继续。`not_started|retained`的drill允许管理员显式发起cleanup：服务端先把cleanup CAS为pending，再按相同安全规则执行。Prune confirmation同步返回`confirmation_id`，Console在确认页面显示candidate hash、数量、bytes和expiry，不轮询token operation。Logs expired后停止日志轮询。页面必须区分execution status、artifact state/readability、acceptance readiness、backup eligibility、catalog registration、cleanup、drill eligibility、promotion health和`backup_recovery_readiness`。

| A | users、AI Gateway | Admin audit/redaction、strong-auth/nonce与权限配置API、Secret bundle、KEK/三类签名key、evidence store adapter/registry/GC、provider-proof与download安全 |

每个公共合同必须由至少一个非实现owner交叉评审。D只拥有协议和集成门禁，不重复实现B的runner/relay或C的provider/catalog；A的安全API和evidence访问同样以冻结接口交付。每阶段开始前只需在项目看板登记A/B/C/D的可验收deliverable、依赖和负责人；人员负载、最大并行项及critical-path调整属于项目管理信息，不进入机器合同或发布正确性门禁，未分配工作也不得默认归D。

阶段顺序如下。每阶段必须有独立feature gate、migration边界和验收报告，允许先在测试安装启用并独立回滚；不得为了等待后续Console、promotion或四矩阵汇总而把前一阶段做成不可验证的大分支。产品P0 GA仍要求五阶段全部通过。

1. **P0-0a 合同冻结**：先完成 provider/CSI/KMS/Redis capability spike，再落盘机器合同、schema object registry、字段/状态/API。合同文件和 parity test 进入仓库后才称为冻结，随后 A/B/C 可并行开发 collector/verifier/provider。
2. **P0-0b 安全基础**：migration、audit/redaction、独立 controller、DB claim、gate/fencing、功能开关和 RBAC。完成后才能端到端创建 Job。
3. **P0a 备份链路**：B交付capture Job-set/checkpoint/staging，C交付artifact/finalizer/external-action/catalog，A交付Secret/KEK/签名/evidence，D只做状态编排和集成；Console页面不是该链路正确性的前置。
4. **P0b 恢复链路**：B交付drill resource/normalizer/cleanup，C交付catalog import和artifact read/verify，A交付只读证据访问，D交付preflight编排/API/Console。只读adapter/verifier可用固定fixture与P0a并行开发，真实集成必须等待committed artifact。
5. **P0c 运维闭环**：C交付prune provider执行/artifact health，A交付告警安全与审计闭环，B交付orphan/resource收敛，D交付promotion、监控汇总和CI/release四矩阵证据。

- route/gate/workload participant registry 未登记即失败。
- 删除 app cluster-admin 后的正/负向 SubjectAccessReview、controller/Job RBAC 分离、Secret resourceName 白名单和 NetworkPolicy 出口矩阵。

### 17.2 并发和故障注入

- 必选capture与secret-capture Job-set全部ready前不得拿gate；分别验证SA/identity、两类phase均可合法`running -> sealed`、preparing/running取消、任一单元读source后整组不得自动新attempt、任一Job失败时整组取消、旧generation command拒绝及聚合certificate只覆盖capture阶段全部Job/staging。镜像拉取/调度超时不造成停写；publish Job不具备live-source、KMS GenerateDataKey或业务Secret读取权限；系统不创建Acceptance Job。
- leader 切换、controller DB claim 过期、锁续租失败、旧 fencing token、capture certificate、absolute hold deadline；mutation lease TTL 到期但旧写入未确认停止时不得进入 strong capture。
- source-writer registry 与实际 MySQL GRANT、Redis client、bucket policy、runtime/workspace writer inventory 不一致时，acceptance 在拿 gate 前失败为 `writer_registry_drift`；显式 functional-test 只能按可观测性得到 bounded/weak，绝不能得到 strong。
- Job 创建后崩溃、source ACK 后崩溃、gate 释放前后崩溃、manifest/commit 前后崩溃、staging cleanup 后/acceptance create 前后崩溃；接管不得覆盖已存在 acceptance record。
- relay command slot 越权、status 伪造/重放/乱序与 controller 重启后持久化游标、旧 generation ACK、participant resume/watchdog、DB 不可用 forced resume 后禁止 seal、attempt 名称冲突、孤儿 Job/PVC/prefix 回收。
- cancel 覆盖各活动阶段，并验证 `can_cancel/commit_started` CAS 胜负、provider request 发出前后、credential 销毁、资源保留和幂等 operation 结果。
- kill switch 分别在 pending、gate held、capture sealed、commit 前后、staging cleanup、acceptance 写入、restore credential 销毁和 prune deleting 中切换；验证 pending 不 claim，活动任务必须到达终态或明确的 `finalization_unknown` 安全稳定状态，且不出现未定义 paused 状态。
- prune 与 publishing/acceptance、drill/preflight/artifact verify、promotion supersede 并发；证明非终态 backup 永不进入 candidate，`prune_guard_version`只因候选相关变化递增、普通health刷新不误伤dry-run，终态检查、lease、hold/promotion 和 `deleting` CAS 形成单一线性化顺序。
- 对达到`minimum_recovery_points`边界的集合分别注入provider、读取credential、KEK、签名、catalog和evidence暂时不可用/unknown/stale；历史终态且eligible、仍为committed的恢复点必须继续受保护，只有corrupt或进入删除状态的artifact才不计入保底集合。
- `_COMMITTED` 或 `_ACCEPTANCE` 已写但 DB CAS/result audit 未写、operation 外部动作已完成但 response 未保存、multipart 已上传但 manifest 未提交时崩溃；接管必须识别相同内容为幂等成功、不同内容为 conflict，不能重复外部动作。
- 覆盖marker已写而artifact committed CAS未写、acceptance已写而registration未写、catalog record已写而terminal CAS未写、promotion CAS成功但响应未保存，以及四类final PUT/catalog append响应丢失并跨过deadline；使用非确定性测试signer证明每个external-action在发送前已持久化并能逐字节重发，同一backup最多一个unresolved、credential envelope续签不改变logical action/payload。普通404不得判absent；分别以“强一致Stat、不支持versioned proof”和“versioned proof、非强一致Stat”两类provider fixture验证能力组任一分支均可收敛。
- Prune在每个item进入planned、deleting、远端已删但本地未CAS、operation deadline到达处注入崩溃；证明接管后所有活动item可收敛为deleted/delete_failed，retry覆盖原计划全部未成功item。Catalog tombstone使用非确定性signer并跨多个retry actor/operation，必须始终复用首次冻结的相同bytes/action key，只递增dispatch generation。
- 并发消费相同strong-auth nonce时只能一个事务成功；同idempotency key/同request hash重放先命中幂等账本并返回原响应，同key/异hash返回`idempotency_conflict`，已消费nonce配新key返回`strong_auth_replayed`。覆盖nonce-HMAC key轮换：验证器必须查询全部仍在保留期的key version，controller/API重启或轮换均不能清空消费记录。
- 覆盖publish credential写final key、candidate credential跨key、finalizer read/delete/final grant越权、provider request写错key/checksum/content-length、credential envelope过期后同逻辑request续签、manifest request写marker/Acceptance、各用途credential越权，以及cancel CAS成功后不得发出request。所有拒绝必须由真实provider能力证明。
- 对manifest/marker/acceptance/catalog四种action分别在deadline后提交presence proof：只有functional marker和catalog registration可成功收敛，其他存在未发送后续finalization写的路径必须安全清理后`failed/deadline_exceeded`且不得补发；absence/conflict按固定映射终结。覆盖task retry复制原DTO但使用当前active config、旧config不再合法时同步拒绝且不改旧task。
- Cluster capture分别注入checkpoint建立前、全部checkpoint验证后的正常resume、加密staging中和seal后的watchdog forced resume，证明只有controller正常resume后的已隔离视图可在gate外继续，而任一forced resume都使当前attempt不能签发或继续使用capture certificate；single-node及secret-capture必须seal后才能正常resume。对external-kms与两种secret KEK variant分别验证最小身份、AES-KW/GenerateDataKey协议、撤销和acceptance上限。

### 17.3 数据和安全

- MySQL engine/DDL/GTID/DEFINER/schema objects，并验证 restore 导入期间 event scheduler 关闭、UDF/plugin/外联权限拒绝和 executable schema 分段；Redis type/TTL/stream/shared-mode；对象 metadata/真实 SHA-256；workspace 特殊文件和恶意 tar。
- 六类 backup/restore/preflight verifier，以及 succeeded/eligibility 独立汇总。
- manifest/events/logs/audit 的嵌套字段、URI 和外部 stderr redaction；低熵 Secret HMAC；验证任何持久卷、文件或失败证据均不存在明文临时数据。
- 在不使用源namespace Secret的隔离环境中按KEK id/version解密eligible artifact；external-kms capture只用task-scoped GenerateDataKey identity，secret型functional fixture只用精确版本的短期read identity和AES-256-KW。任何Kubernetes Secret、PVC、日志和evidence均没有明文DEK/KEK，且两类身份都可到期/撤销。
- AES-GCM framing/nonce崩溃恢复、无持久化明文、manifest无checksum自引用、S3 conditional create和version/delete-marker prune；PVC/local仅运行接口fake测试。
- cleanup权威resource inventory/reserved marker、namespace级联删除、PV/VSC仅观察不直接删除、intent recovery、promotion/manual双重hold、prune candidate漂移、confirmation actor/重放/过期、部分删除和catalog tombstone专用retry、artifact verify/health/prune竞争、artifact corrupt和orphan-GC。
- 覆盖 restore 与 backup staging 两类 creating intent 经权威查询证明不存在后转`absent`、已创建资源删除后转`deleted`、ownership unknown 的人工 proof/row-version CAS、partial cleanup 用同 endpoint+新 key 重试，以及未提交 artifact `staging -> deleting -> deleted|delete_failed` 的数据库与远端收敛。
- 覆盖 mutation lease 与 gate acquisition 竞争、drill/preflight lease 与 prune 竞争、cleanup 创建/登记崩溃窗口、共享 MySQL 裸删除拒绝、DB 不可用时 participant monotonic watchdog。
- 覆盖当前manifest读取、拒绝未知breaking schema、上一compatible fixture及config/Secret ref/attestation漂移；验证最终eligibility不在manifest或`_ACCEPTANCE`内，以匹配`local_acceptance=true`的`artifact_registered` append为唯一灾备线性化点，本地终态CAS只作投影并可崩溃接管。
- 覆盖 endpoint SSRF/私网策略、DNS rebinding、TLS hostname/CA、恶意高压缩比、超量文件/object、重复 key、超长路径和 evidence_ref 损坏/过期。
- 覆盖两种restore target variant及创建前planned-identity、资源创建后observed-identity两道隔离门；逐项/组合测试生产namespace、MySQL database、Redis keyspace、object prefix、workspace root、Service DNS/CIDR和credential权限重叠。Drill Job不得挂载SA token，只能通过status relay上报；任何无法证明隔离的配置必须在首个数据写入前失败。
- 覆盖 artifact credential/CA/KEK/evidence/attestation 历史版本轮换与过期、active promotion hold 延长保留、full verify 全对象读取/DEK unwrap/GCM authentication；后台轻量reconcile只能按真实观测双向更新dependency health，`artifact_usable=false -> true`仅允许相同immutable version的full verify按第13节恢复，kill switch不得改变两类判定。
- 覆盖control metadata达到80%/100%、分批GC中断接管、row-version竞争、compact tombstone创建、standard二阶段删除、destructive永久保留、rolling hash和410幂等过期响应；仍被artifact/import/promotion/retry引用的evidence不得清理，外置evidence删除必须先于registry envelope，pending/write_unknown/write_failed/delete_failed不得丢登记。Provider-proof registration覆盖8 KiB proof/16 KiB request边界、错误issuer/signature/target/version/组合和重放，并证明同步路径不调用外置store/KMS。Evidence覆盖1 GiB上限、content/object双checksum、chunk-list root、envelope_v1逐块GCM/KEK故障、Range owner/size/redaction复核及敏感下载审计。
- 覆盖dependency-health按owner+immutable identity/version选择唯一当前记录、缺行/冲突/过期派生unknown/stale、后台检查在kill switch关闭期间仍可双向更新；catalog scan在controller重启后按持久化claim/checkpoint接管，分别验证pending→running/failed/incomplete、running→succeeded/failed/incomplete、有效incomplete→running、snapshot过期、新scan互斥、固定snapshot只扫描一次且receipt/hash可验。
- Catalog完整发现必须用真实provider snapshot或immutable inventory fixture逐页物化catalog-record，校验EOF时record rows/count/root一致、API能在不知道源installation任务ID时列出未tombstone registration并创建import；普通S3分页、重复稳定扫描、漏页、页后插入和registration/tombstone交错一律不能得到succeeded receipt。
- Redis验证`preserve_absolute|restart_remaining`的过期边界、源/目标时钟偏差和负TTL；对象存储验证gate内冻结key/version清单、resume后新增/删除不污染结果以及无version provider最多bounded。Delete-on-success drill必须验证含明文的PV已回收/重置，否则cleanup settled失败、evidence health degraded并持续告警。日志测试覆盖逐行redaction失败丢弃、chunk幂等、截断、Pod/Job删除后读取、retention到期和evidence-GC。
- 覆盖灾备安装通过catalog-import API仅凭registration、预置bootstrap和artifact完成发现、验签、full verify、读取、解密及acceptance drill/production-readonly preflight；阻断源数据库、源Kubernetes API、源Secret和源网络。分别验证强一致catalog checkpoint全扫描、无该能力时完整发现验收失败、tombstone普通404不算不存在、两个signing purpose独立轮换/撤销，以及catalog/read-credential/CA/KEK/任一signing bootstrap缺失的精确失败映射。
- 恢复副本必须证明 `system_backup_*`、artifact/mutation lease 和 maintenance participant 等控制表无源数据行，control-evidence sidecar 只读且 redacted；新安装无 baseline 时应用/controller readiness 仍通过而 `backup_recovery_readiness=false`。

### 17.4 固定数据集和四矩阵

- 基础 smoke 覆盖六类业务、admin/普通用户、实例/workspace、Team/ledger、Skill object、AI Gateway 和资源审计。
- `large-smoke.v1` 最低固定为：2 GiB 分片 workspace、10,000 个 Skill 对象、100,000 条 Team/审计事件、100,000 个 Redis key；若产品声明的支持规模更大，另以声明上限的代表性比例运行 capacity fixture，不能把 large-smoke 当作生产上限证明。Fixture 版本、实际资源、峰值 CPU/内存、各阶段耗时和配置 deadline 写入证据；必须在 config snapshot 的容量、停写和总 deadline 内完成，不允许空库替代。
- k8s cluster、k3s cluster、k8s single-node、k3s single-node 使用机器合同锁定的 Kubernetes/k3s、CSI、S3、KMS 和 MySQL/MariaDB 版本矩阵，分别在独立安装中以外部 artifact target和源集群外可恢复 KEK完成 eligible backup + eligible drill + 当前 matrix promotion。灾后验证必须阻断源集群网络和凭据，不能只是不挂 source namespace Secret。四份 redacted evidence 由 CI/release 汇总签名；缺任一矩阵只能记录功能性验证，不能完成 P0 发布验收。

### 17.5 测试清理

只使用仓库已有 Go、K8s fake client、Playwright 和已提供集群，不自行安装依赖。测试 harness 必须在开始前记录既有路径/资源，只删除本次 run 创建且具备 run ID/owner marker 的 `frontend/dist`、`e2e/playwright-report`、`e2e/test-results`、临时 binary、明文/密文 staging、namespace、Job、PVC、snapshot 和 object prefix；开始前已存在或 ownership 无法证明的内容不得删除。仓库证据只保留 redacted 摘要、测试命令、资源标识和清理结果。

## 18. P0 验收标准

- P0-0a、P0-0b、P0a、P0b、P0c 顺序通过；后续阶段不能补交前置安全合同。
- 四套官方部署已移除 app `cluster-admin`；负向权限测试证明 API 进程不能创建备份资源，独立 controller 和 Job 均有可验证的最小权限边界。
- 六个必选 part、六类业务 verifier、控制面 verifier、manifest/index/marker/签名 acceptance、外部 recovery catalog 两类 record 和 KEK 灾后解密全部通过；provider能力证明分别覆盖candidate精确读/删、final/Acceptance精确conditional-create、不存在性能力组和完整发现能力组。负向测试证明upload/candidate-read-delete/finalize/read/delete/catalog credential相互不可越权；只有commit CAS后由controller provider adapter发出的、已在external-action持久化的精确bytes request可提交final/Acceptance key。
- backup execution、artifact state/usability、backup terminal eligibility、catalog registration/import、cleanup、drill eligibility和promotion health七类结论在数据库/API/Console中明确分离；manifest不伪装包含后置形成的最终eligibility。
- schema objects 全部 covered 或有 explicit excluded reason；repository 不在构造时建表。
- 四个独立测试安装均完成自身 matrix 的 eligible backup + 严格隔离 drill + promotion，并由 CI/release 汇总证据；普通安装只要求与自身 matrix 匹配的健康 baseline。Single-node 无法停止 runtime 或在 hold deadline 内 staging 时不得冒充 strong。
- prune部分失败不会留下“健康succeeded artifact”的假象；保底恢复点和活动引用不会被删除；对象已删除但catalog tombstone失败时有持久化item、degraded readiness、告警和只补tombstone的retry路径。
- backup staging、external action和evidence均有独立权威记录，可在controller重启、凭据envelope轮换和provider响应丢失后接管；普通404或重复List不能伪造不存在/完整性证明。
- Strong-auth nonce、dependency health、catalog scan receipt、installation first-enabled和compact tombstone均有数据库权威记录；config轮换、controller/API重启和GC中断不得重置安全或监控状态。
- P0 不存在 agent 管理/回调、schedule 或生产 restore execute API。
- 证据链可通过 installation/task/job/request/controller/lock/fence 关联，且无明文 Secret 或临时测试产物残留。

## 19. P1 进入条件

- P0 artifact、manifest、verifier、controller claim、审计和四矩阵证据稳定。
- backup-agent 协议重新评审后再新增 agent 表、token、回调和外部 runner，不复用 P0 占位 API。
- 系统 schedule 和自动 prune 复用 P0 任务与 artifact lifecycle。
- 生产恢复必须先交付独立 control database/journal，再实现 `preflight -> diff -> explicit-confirm -> execute -> verify -> finalize`；失败不自动回滚，并保留可审计 runbook。
